## 第一部分 · 代码审查

### 🔴 高：明确的功能错误或凭据/数据风险

#### C-01 采集框一次页面会话只能提交一次，第二次静默失败

**位置**：`web_static/js/capture.js:182,227,236`

`submitCapture()` 用模块级 `submitting` 做互斥：`if (submitting) return; submitting = true;`，但全函数**没有任何一处把 `submitting` 复位**（`git log -S "submitting = false;"` 只命中引入它的 `3167d63`，从未存在过复位代码）。函数末尾只恢复了按钮的 `disabled`/`busy`（`:317-319`），视觉上看起来「可以再用」，实际下一次点击在 `:227` 直接 return。

**实测**：dev 环境连调两次 `submitCapture()`（中间换文本），`/v1/captures` 只发出 1 次请求，第二次的输入文本留在框里不清空。提交成功后不刷新页面（`app.js:160` 只 `refreshItems()`），所以真实用户从第二次采集起就卡死。

**次生问题**：部分成功分支（`:296-302`）在 `toast` 后 `return`，跳过 `:317-319`，把提交钮永久留在 `disabled` + 转圈态。

**建议**：`submitting` 的复位放进 `finally`；`:300` 的 `return` 改成 `throw`/走同一收尾路径。

#### C-02 小红书登录态可被发往任意主机，域名白名单是死代码

**位置**：`domain/platform_sessions.py:41,94`、`extractors/xiaohongshu.py:125-129,249-257`、`extractors/fetch_base.py:113-117`

`PlatformSessionProfile.cookie_send_domains` 声明了「登录态只允许发往的精确一方域名」（docs/18 §7.2 规则 4），但 `rg cookie_send_domains` 全仓**只有定义处，无任何读取方**——白名单实际未实现。

带 Cookie 重试用的是页面里解析出的 `note_url`，而 `note_url` 来自 `redirectPath` 参数，只判了 `raw.startsWith("http")`（`http://` 也放行）。`fetch_base` 把 Cookie 挂在本次调用的首跳，`safe_fetch` 只校验「本次 URL 的 host」，不做归属校验。

**影响**：用户提交 `https://www.xiaohongshu.com/login?redirectPath=<攻击者主机>`（伪装成普通笔记链接即可），服务器就带着该用户的小红书 Cookie 去请求攻击者主机。这是本项目「每人自己的凭据只用于自己」的硬约束被绕过。

**建议**：带 Cookie 前校验 `urlparse(url).hostname` 命中该平台的 `cookie_send_domains` 且 scheme 为 `https`，否则匿名请求并如实标降级；`redirectPath` 只接受同域。

#### C-03 知乎适配器成功路径必然抛 AttributeError，知乎实际不可用

**位置**：`workers/worker.py:671,701-703` 对 `extractors/zhihu.py:64-110`

共享归档路径无条件读 `ext.images` 与 `ext.missing_materials`。用 `dataclasses.fields` 核对了四个结果结构：

| 结构 | `images` | `missing_materials` |
|---|---|---|
| `WebpageExtraction` / `XiaohongshuExtraction` / `ChannelsExtraction` | 有 | 有 |
| `ZhihuExtraction` | **无**（只有 `image_urls`） | **无** |

任何 200 且解析成功的知乎页面（含 `question_only`）都会在归档后崩掉 → 顶层 `retry_or_fail` 最多重跑 5 次抓取（`worker.py:121-133`，对平台是重试风暴）→ 条目停在 failed。现有测试只覆盖 403 降级路径（`test_platform_sources.py:154-178`），所以没暴露。

注意：设置页里知乎 `enabled=false` 只是不露出登录态配置（`js/settings.js:339`），**链接本身仍可提交**，缺陷对用户是活的。

**建议**：三个 Extraction 补齐共同字段（`images`/`missing_materials` 给空默认值），worker 只依赖共同协议。

#### C-04 设备授权页把未净化的服务端数据写进 innerHTML

**位置**：`web_static/authorize.html:110-116,134`

```javascript
setState('<div class="devinfo">设备名称　<b>' + info.device_name + '</b><br>当前账号　<b>' +
  (body.central_username || ...) + '</b>...');
```

`device_name` 是用户可自由填写的 ≤120 字符串（`api/routes_auth.py:135,180` 只截断不净化），`info.error?.message` 同样原样拼入。`esc()` 在收件箱侧是共用的，这个页面是独立脚本、没走它。

**可达性**：`GET /v1/auth/device/info`（`routes_auth.py:197`）**不要求登录**，只凭 `request_id` 返回 `device_name`。攻击者用自己插件发起一条授权请求拿到 request_id，把 `/authorize?request_id=...` 发给受害者（话术就是「帮我点一下授权」），受害者浏览器在已登录的 kb 域里渲染攻击者控制的 HTML → 脚本在受害者会话下执行，而这一页本身带着「登录此插件」的批准动作。120 字符足够 `<img src=x onerror=...>`。

这一页的正文正是「确认这是你本人操作」的安全提示，注入直接废掉这道确认。

**建议**：`device_name`、`central_username`、`error.message` 全部走 `textContent` 或补 `esc()`；顺带把 U-05 提到的一起做（该页与收件箱共用一份小工具）。

### 🟠 中高：正确性偏差 / 用户可感知的体验缺陷

#### C-05 限流器非线程安全，且活跃键泄漏未根除（9/11 C-06 的修复引入）

`api/rate_limit.py` 把四处限流收敛成 `SlidingWindowLimiter`，方向是对的，但：

1. 这些端点都是同步 `def`，跑在 anyio 线程池里，是真并发。`_sweep()` 在 `self._attempts.items()` 迭代期间，另一线程 `setdefault(key, [])` 插入新键可触发 `RuntimeError: dictionary changed size during iteration`；`/v1/auth/*`、`/v1/pairing` 是未鉴权端点，攻击者变换源 IP 就能放大概率。建议加 `threading.Lock`。
2. `check()` 修剪出的窗口不回写（`:29`），`_sweep` 只摘「最后一个时间戳已过窗」的键（`:45-46`）。持续活跃但始终未超限的键（企业 NAT / 运营商 CGNAT 出口 IP 打 `/v1/auth/device/poll`）时间戳列表按窗口累加、永不清空——原报告的慢速泄漏被削弱，没消除。
3. `check()`/`record()` 分离不是原子的，limit=1 的场景可被并发穿透。

#### C-06 列表轮询比 9/11 更密，且详情页打开时仍在拉

`js/item-list.js:212-222` 注释写「有活跃任务 4s；否则 30s」，实现是两个 `setInterval` **都常驻**（4s 与 30s 各一个，互不相关），可见状态下等效于每 4s 一次 `fetchAll()`（50 条 + WorkflowView 计算）。同时 `js/item-detail.js:167-170` 详情页自己还有一个 4s 轮询，此时底下的列表并不可见。

9/11 报告的基线是 30s，现在读放大了约 7 倍；`document.visibilityState` 闸门是有的（实测隐藏页 9 秒 0 请求），所以主要是「前台阅读时白拉」。建议：按 `workflow.overall_state === 'working'` 决定 4s 还是 30s，详情打开时暂停列表轮询。

#### C-07 HTTP ≥ 400 一律判「内容已删除」，风控被终态化

`extractors/xiaohongshu.py:136-137`、`wechat_channels.py:156-157` 直接 `status_code >= 400 → PlatformError("deleted")`，而 `safe_fetch` 不校验状态码。429/503 会被写成「笔记已删除或不可见」，既不重试也不与 blocked 区分，违反 docs/18 §7.3 的 deleted/blocked 分离，用户被推去手抄正文。建议按 404/410→deleted、401/403→login_required、429/5xx→blocked/network_error 分流。

#### C-08 coverage 虚高：标题、简介、盐选摘要被当全文

`xiaohongshu.py:188` 把 title 与 desc 拼成 segments，而 `coverage` 只看 segments 非空（`:84-86`）——只拿到标题、或兜底只取到 `og:description`（`:399-407`）也标 `full_text` + `origin=platform_content`；`zhihu.py:287-290` 盐选只存 excerpt，coverage 仍走 full_text，docs 要求的 `partial_text` 全仓无人产出。

后果是 AI 拿标题当原文加工、Obsidian 显示「已取得全文」。这直接违反 AGENTS.md「不用标题、简介或模型猜测冒充原文」。建议只有命中笔记/回答正文容器才 full_text。

#### C-09 批量图片下载会突破任务租约并抬高内存峰值

`extractors/fetch_base.py:146-170` 串行下载，每图 `timeout=20.0`、单图上限 20MB、单条 24 张，字节全部先攒在 `ext.images` 再回 `worker.py:671-676` 逐个落盘；extract 阶段没有续租，而 `config.py:89` 租约 120s、`worker.py:1009-1013` 每 60s 回收过期租约。

8 张慢图即超租约 → 同一 job 被重领二次执行，两边都按 `source.revision + 1` 写版本，撞 `uq_source_rev`（`models.py:244`）导致 IntegrityError 与 attempt 计数错乱。内存最坏约 480MB 常驻，2GB 机器上会挤垮同机服务。建议边下边写、加单条总字节/总时长上限，图片归档拆成可续租的独立任务。

#### C-10 共用弹窗模块会被 200ms 定时器关掉紧接着打开的下一个弹窗

`js/api.js:115-124`：`closeModal` 用 `setTimeout(..., 200)` 延迟 `ov.hidden = true` 与清空 `#modalBox`，而 `modalResolve` 在同步路径就 resolve 了。`confirmModal(...)` 的 `.then()` 里再开一个弹窗（确认 → 输入、确认 → 确认的链式交互）时，新弹窗会在 200ms 后被这次延迟任务清空并隐藏。

`admin.html:233-240` 已经用 `modalGen` 世代号修掉了同一个问题，收件箱侧的共用模块没跟上——同一 bug 的两份实现漂移。建议把 admin 的世代号方案搬进 `api.js`。

### 🟠 中高

说明：重叠与「顶部无收起钮」是截图直接观察到的；具体是层序问题还是 clip 区域问题，我这轮用 `elementFromPoint` 的验证脚本没跑完，**未确证**。建议按走查习惯真机点一下确认，再决定是「展开后隐藏拉手」还是「拉手让位给采集框」。

#### U-03 收件箱恒暗色，管理页与授权页跟随系统 → 同一次跳转里换肤
