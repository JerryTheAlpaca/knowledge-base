#### C-01 share_runner 的 Chromium 沙箱实际是关闭的，注释与镜像声明相反

**位置**：`apps/share-renderer/src/browser.mjs:12-19`、`apps/share-renderer/Dockerfile:4-5,34`

`launchChromium()` 只传了 `handleSIGINT: false`，没有传 `chromiumSandbox`。本机 `playwright-core@1.60.0` 的 bundle 实测：默认值为 `chromiumSandbox: false`，且判定式是 `chromiumSandbox !== true` 时向启动参数追加 `--no-sandbox`。也就是说浏览器以**无沙箱**起跑。

而 `browser.mjs:17-18` 写的是「沙箱内以非 root 运行，Chromium 自带的 sandbox 保持开启……不用 `--no-sandbox` 蒙过去」，`Dockerfile:4-5` 同样声明保持开启，理由引用的是 Playwright 关于 root 运行的说明。容器确实已经是 `USER pwuser`（`Dockerfile:35`），但非 root 并不改变 Playwright 的默认值——这条边界从来没被打开过。

**影响**：模型生成的页面脚本在唯一可写交接卷所在的容器里以无沙箱 renderer 执行，直接对上 C-02。`Dockerfile:24-25` 注释说"浏览器能否以非 root + sandbox 起跑由部署后 `share_runner doctor` 实测"，但 `doctor` 只跑 `checkOnly`（`cli.mjs:88-93`），验不到沙箱开关。

**建议**：`chromium.launch({ chromiumSandbox: true, handleSIGINT: false })`，并让 `doctor` 输出实际生效的浏览器启动参数；若开启后 512m 内存限额撑不住（C-01 的次生风险），要么调限额要么在 docs/21 撤回"沙箱保持开启"这句。

#### C-02 交接卷 0777 + `umask 0`，而 `input_hash` 只是完整性自检

**位置**：`workers/share.py:660-666`（每个 spool 子目录 `chmod 0o777`）、`src/cli.mjs:84-85`（`process.umask(0o000)`）、`Dockerfile:28-32`（`chmod -R 0777 /spool`）、`src/build.mjs:86-89`

`build.mjs:86-89` 的 `INPUT_HASH_MISMATCH` 检查里，`task.json` 的 `input_hash` 由服务端在 `share.py:712` 现算后写进同一份信封，构建期再对同一目录重算比对——它能挡住"快照被改坏"，挡不住"同时改掉 `input/page_source.json` 和 `task.json`"。它不是授权判定。

**建议**：两端固定同一 **gid**（compose 里给 worker 与 share_runner 都写 `user: "<uid>:<gid>"`，或 `group_add`），目录 `0770`，替代 `0777` 与 `umask 0`。开 C-01 的沙箱 + 收这一条即可闭环，**不要**给 spool 加签名信封或内容加密层。

#### C-05 分享产物回收条件写错，私有存储只增不减

**位置**：`workers/share_retention.py:85`、`:98-102`、`:125-136`；`api/routes_shares.py:777-781`；迁移 `f1d3b5c7e9a2:184-186`

#### C-08 退出后那颗凭据仍可能被在飞响应种回浏览器

**位置**：`kbserver/app.py:47-68`、`api/routes_auth.py:118-146`、`security/central_auth.py:20-25`、`api/deps.py:145-160`

`deps.py:149` 每次请求都查 `is_revoked`、没有任何 TTL 正向缓存，这一半是对的（符合"下一个请求即失效"）。缺口在中间件：`app.py:52-63` 无条件把 `request.state.central_renewal` 写回浏览器，而 logout 只把**当次请求**的 `central_renewal` 置 None（`routes_auth.py:126`）。退出前已经发出的请求（中心校验要一个公网 RTT）落地更晚，就会把刚 `delete_cookie` 掉的 `__Secure-jerry_session` 又按父域种回去。KB 侧靠自己那张 5 分钟的撤销表挡得住，但这颗 Cookie 对 auth 站及同域其他应用仍是活钥匙。

叠加两点：`_revoked` 是进程内存（`central_auth.py:22-25` 的注释已自省），而每次 push 都重建 api 容器 → 窗口远不到 5 分钟就清零；`logout` 依赖 `current_principal`，中心不可达时先 503（`deps.py:155-156`），handler 根本进不去，既不 `remember_revoked` 也不清 Cookie，前端 `app.js` 吞掉异常照样 `showLogin`——中心重启那一两秒点退出＝静默没退出。

**建议**：中间件写 Cookie 之前再查一次 `is_revoked`（一处）；logout 改成本地清理与通知中心解耦（先清，尽力通知）。撤销表落不落库不必动，当前单 worker 前提下内存表够用。

#### C-09 runner 没有整任务墙钟，一个卡死页面停摆整条串行队列

**位置**：`src/runner.mjs:121-138`、`src/browser.mjs:155`、`:166`、`src/checks.mjs` 的交互声明

`runSpool` 是串行循环，`processTask` 里只有 build 段有 `try/catch`（`runner.mjs:55-68`），检查阶段的异常会一路上抛、把整个 runner 进程带走（`restart: unless-stopped` 会拉起，但当前任务的处理半途而废）。更要紧的是 `frame.evaluate(structureChecks)`（`browser.mjs:155`）与交互执行都没有超时——模型页面一个死循环就永久占住唯一的 runner。

服务端侧其实已有兜底：`share.py:769-777` 到 `runner_deadline` 后判 `runner_timeout` 并 `cleanup_runner_task`。所以后果不是任务卡住，而是**后续所有用户的任务排在一个已经没人管的 runner 上**，各自等到自己的 deadline；`cleanup_runner_task` 只删目录，不会让 runner 里那个循环停下来。

**建议**：`processTask` 外层加墙钟（复用 `share_render_timeout_seconds` 的量级，`config.py:141` 默认 60s）+ `runSpool` 循环加 try/catch 记 failed。不需要新的错误框架。

## 第二部分 · UI 审查

### 先说结论

本轮 UI 的**转义纪律没有破口**：前端所有 innerHTML 写入点（`shares.js:323/505/520/637`、`item-list.js:122/130`、`capture.js:93/98/104`、`item-detail.js:53/372/550`、`workflow.js:61-98`）逐个看过，插进去的动态值都过了 `esc`，用户消息先转义再换 `<br>`（`shares.js:358`）；预览 iframe 是 `sandbox="allow-scripts"` 且**不给** `allow-same-origin`（`shares.js:432`），不透明源读不到 `localStorage`/`document.cookie`，也拿不到 `kb_csrf`（`api.js:28-31`），会话 Cookie 是 HttpOnly+Lax（`app.py:59`）。真正的站外风险在第一部分（C-03 的外层注入、C-04 的 key 外发），不在前端渲染。

多选态的实现方向也符合"整张卡片发光、不往卡里塞控件"的偏好，文案没踩雷（需要你处理／待发布／已完成／清空／完成／制作 HTML／下载原文／上一个问题都是日常词）。但**选中态是易失的**，这条直接废掉了整卡发光的设计意图。

### 🟠 中高

#### U-01 多选点亮态与计数分家，会被列表刷新抹掉

**位置**：`js/shares.js:49-59`（`setSelectMode`）、`:62-73`（`toggleItem`/`syncRowMarks`）、`js/item-list.js:122,130`（`li.innerHTML = rowInner(it)`）、`:264-272`（`visibilitychange` 立刻 `refreshItems`）、`inbox.css:673`

`selected` 存 localStorage，`.picked` 只在 `toggleItem → syncRowMarks` 写；`setSelectMode` 不调 `syncRowMarks`，列表重渲染也没人补。多选态**没有**停列表轮询（`setListPollPaused` 只在舞台/对话列表打开时生效，`shares.js:216-222`）。

**用户会看到什么**：勾 3 篇 → 切到别的标签页复制一段话 → 回来（`item-list.js:264-272` 触发刷新）→ 卡片金色全灭，底部条仍写着"已选 3 篇"，点"完成"照样按那 3 篇开工。反向也错：`inbox.css:673` 的发光没限定在 `body.share-selecting` 作用域下，退出多选后旧点亮还挂在卡片上，直到下一次重渲染。

**建议**：`setSelectMode` 里补一次 `syncRowMarks`，并在列表重渲染出口调一次（`item-list.js` 已有 `scheduleRefresh` 之类的接缝）；退出多选时清 `.picked`，或把 CSS 收到 `body.share-selecting` 下。

#### U-02 "打开链接"刷新之后是死链

**位置**：`shares.js:434`（`href="#"`）、`:724-726`（只在发布成功当场填 url）、`api/routes_shares.py:334-338`（GET 只回 `has_link`，不回链接）

发布成功后不刷新页面时能点；刷新一次、或从顶栏三横线重新进来，"打开链接"就是一张空白锚点，用户以为链接坏了。

**建议**：已发布状态下由 `GET /v1/shares/{id}` 返回 url（作者本人本来就有权限读），前端 `:434` 直接用；服务端不返回就别渲染这个按钮，改成"重新生成链接"。

### 🟡 中

#### U-03 离开舞台后仍在那篇上轮询

`showConvList`（`shares.js:232-237`）只 `stopPolling()`，没清 `activeShareId`；`tick`（`:906-913`）进函数第一件事把 `pollTimer` 归零，于是一个**在飞**的 `refreshWork()` 返回后照样续排 3 秒。表现：生成中点顶栏三横线回到对话记录页，后台每 3 秒仍拉那篇，一旦断网就在列表页弹一条无关的 toast。修法是 tick 续排前判一下舞台是否还开着，或给轮询加代际号。

#### U-04 幂等键每次新生成，超时重试等于第二次创作

`shares.js:594-600` 的 `POST /v1/shares` 用 `newKey("share")`（`:621-622`，每次调用现造）。请求超时后用户再按一次回车，就是一把新键 → 建两个作品、扣两份预算。`startGeneration`（`:852-866`）则少了 `onSend`（`:797-806`）那道 `sending` 互斥，连点第二次会被服务端 `expected_conversation_version` 挡回，用户看到"刚才没有完成"这类误导性报错。两处都是前端小改：进入 draft 时生成一次键并复用；给 `startGeneration` 上同一把锁。

#### U-05 多选态没有键盘路径，Esc 层级还剩两处

`shares.js:93-101` 只在捕获阶段处理 click，`item-list.js:303-309` 的 Enter/Space 仍走 `openDetail` → 键盘用户在选择模式下按回车是跳详情，不是勾选。`95c64ff` 用"给这次按键打个记号"解决了菜单与抽屉抢同一次 Esc，但这个记号**只有抽屉那条读**（`item-list.js:367` 判 `!e.kbEscTaken`），于是同一类还剩两处：

- 舞台上开着账号菜单按一次 Esc，`shares.js:963-966`（捕获阶段）先退舞台，气泡阶段的 `app.js:174 closeMenus()` 不读记号、照旧执行 → **一次按键同时收掉了菜单和舞台**，和 95c64ff 修掉的是同一个毛病。
- 详情页"更多操作"菜单开着按 Esc **谁都不收**：`item-detail.js` 全文没有任何 keydown 监听（菜单只在 `:676-680` 的 click 里切换），而 `app.js:101-103` 的 `closeMenus()` 只关 `#userMenu`。
切澄清题时 `renderThread` 整块重写 innerHTML（`shares.js:323,487-489`），焦点掉回 body，每切一题要从头 Tab；"已选 N 篇"也没有 `aria-live`。

#### U-06 两处按钮位置要盯（其中一处只有窄屏才跳）

`shares.js:526` 在 draft 进入 work 那一刻把 `$("stageDelete").hidden` 打开。这一栏的排布是「标题 · `.spacer`(flex:1) · 删除钮 · ✕」（`inbox.html:956-962`），所以两种情况要分开说：标题短、spacer 还有余量时 ✕ 钉在右缘不动，只是左边多冒出一个按钮；标题长或窄屏把 spacer 压到 0，✕ 就会被"删除这次对话"往左挤。**后者才是不能接受的横向跳**，需要真机在窄屏 + 长标题下确认一次（我没有实机走查，这一条是读码推断）。

另外"完成"菜单是 `main` 下的 fixed 层（`inbox.css:666`，CSS 里的 `bottom: 88px` 只是兜底），真正的位置由 `showSelMenu` 每次打开时按多选条上沿现算（`shares.js:130-137`）——**打开之后不再重算**。多选条在小屏换行长高、或抽屉收起后条子位移，菜单就会和它错开。`.seltext` 的 `min-width: 92px`（`inbox.css:657`）对"点卡片勾选材料"这 7 个字几乎顶满，换字体或改文案会截字（未实测宽度）。
