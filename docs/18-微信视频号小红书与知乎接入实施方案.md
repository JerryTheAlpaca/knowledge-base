# 微信视频号、小红书与知乎接入实施方案

版本：v1.0 · 2026-09-16  
状态：待实施；先做真实样本验证，再按本文分阶段开发。

## 1. 目标与交付口径

本轮把微信视频号、小红书和知乎接入现有的“可靠接收 → 来源提取 → 云端加工 → Obsidian 发布”链路，不另建一套采集系统。

这里的“支持”按三个层次定义，避免把不稳定的平台访问写成无条件成功：

1. **可靠接收**：分享文字、链接和用户上传的截图/文件先持久化；即使平台页面无法读取，材料也不丢。
2. **自动提取**：只读取用户明确提交的单条内容；能公开取得时保存正文、标题、作者、发布时间和必要图片，并记录实际覆盖范围。
3. **清楚降级**：登录墙、风控、内容删除或页面结构变化时，不把标题、分享摘要或模型猜测冒充全文；转为补充正文、截图、字幕或音频的流程。

首版不承诺自动下载微信视频号或小红书原视频。三类平台均允许用户**按自己的账号托管登录态**，像现有 B 站 SESSDATA 一样仅用于云端读取该用户提交的内容；仍不代替用户自动登录，不绕过验证码，不使用抓包注入、客户端代理或常驻浏览器。

## 3. 首版范围

### 3.1 支持矩阵

| 来源 | 首版自动处理对象 | 自动取得目标 | 无法自动取得时 | 首版明确不做 |
| --- | --- | --- | --- | --- |
| 小红书 | 单篇图文笔记、单篇视频笔记的分享链接 | 分享短链展开、笔记 ID、标题/正文、作者、发布时间；图文笔记可访问的原图；视频笔记的封面和文字说明；必要时使用该用户托管登录态 | 登录态缺失/失效时提示连接或更新；仍失败则保留分享包并补充截图/正文 | 评论区、推荐流、搜索结果、批量采集、跨用户共享登录态、自动下载原视频 |
| 微信视频号 | 单条视频号内容的分享链接/分享文字 | 链接归一、登录后可读取的标题/作者/发布时间/说明；有稳定页面时保存页面响应 | 登录态缺失/失效时提示连接或更新；仍失败则保留分享包并补充截图、字幕、音频或摘录 | 直播、评论、账号主页批量采集、跨用户共享登录态、抓包代理、自动下载原视频 |
| 知乎 | 单篇回答、单篇专栏文章 | 标题、作者、发布时间/更新时间、正文、正文图片、问题标题与回答定位；必要时使用该用户托管登录态 | 登录态缺失/失效时提示连接或更新；仍失败则保留链接并补充正文/截图 | 整个问题下全部回答、评论区、想法、盐选越权读取、知乎视频、站内批量搜索 |

知乎“问题页但未指向具体回答”的首版行为是保存问题元数据并要求用户选择/补充目标回答，不自动抓取整条讨论。

### 3.2 推荐的产品取舍

- 小红书图文中的图片是正文的一部分，适配器成功解析后默认保存可访问的笔记图片；不沿用普通网页“默认不保存配图”的语义。
- 视频号和小红书视频先保存文字说明、封面与定位信息；只有用户主动补充字幕、音频或文字摘录时，才进入已有文字稿或转写路径。
- 知乎首版优先公共页面和用户登录态的单条回答/文章适配器。官方数据开放平台作为验证项：只有确认能按精确 URL/内容 ID 获取原文、授权允许个人归档、成本可接受后才接入，不让平台申请阻塞基础版本。
- 三个平台都不要求用户先“连接账号”才能采集；系统先可靠接收，匿名访问不足时再提示连接。登录态连接是可跳过的初始化项，也可在条目详情按需触发。
- 每个用户只能使用自己的平台登录态；不回退到管理员或其他用户的 Cookie，不把同一账号默认共享给多人。

## 4. 平台事实与实施前提

实施前需要保留两条边界：

1. 小红书当前公开的账号开放接口主要是 OAuth、Token 和最小用户信息，已公开的接口目录未提供任意笔记正文读取能力。因此官方 OAuth 不能替代网页登录态；需要登录的笔记走用户自行提交、加密托管的会话 Cookie。参考：[小红书开放平台 API 参考](https://openaccount.xiaohongshu.com/docs/api-reference)。
2. 知乎当前有数据开放平台和内容/用户数据能力，但处于需要申请访问、具体计费需沟通的阶段。接入前需确认精确内容读取、授权范围、归档权利和费用。参考：[知乎数据开放平台](https://developer.zhihu.com/)。

微信视频号是否存在可供本项目使用的公开单条内容接口，本轮尚未得到足以落地的官方依据。首阶段必须用真实分享样本和用户自有登录态确认链接形态、最小 Cookie 集与服务器可见内容，不能先按第三方抓包方案设计生产实现。

## 5. 第一阶段：真实样本与技术探测（必须先做）

### 5.1 样本集

每个平台收集 8–12 条用户日常真实样本。样本内容本身不提交到公开仓库，只保留脱敏后的结构 fixture。

| 平台 | 至少覆盖 |
| --- | --- |
| 小红书 | `xhslink.com` 短链、完整链接；图文/视频；公开/要求登录/已删除；正文长短不同；多图；作者本人和非本人内容 |
| 微信视频号 | 从 iOS 微信“分享/复制链接”得到的不同文本形态；公开/仅微信内可见；有无标题说明；有无字幕；转发卡片与复制链接 |
| 知乎 | 回答直链、问题链接、专栏文章；长文、代码块、引用、图片；匿名回答；登录墙/已删除/盐选内容 |

### 5.2 每条样本记录

- App 实际给分享面板的文字、URL 和附件类型。
- 短链的每一跳与最终域名；最终内容 ID 能否稳定提取。
- 腾讯云服务器匿名请求是否可见正文、元数据、图片地址或媒体引用。
- 页面是否必须执行 JavaScript；静态 HTML、JSON-LD 或内嵌状态中有哪些可用字段。
- 图片/封面链接是否有时效、Referer 或签名要求。
- 匿名访问与登录访问分别能取得什么；登录所需的最小 Cookie 名称、允许域名、有效期和失效信号。
- 登录态是否绑定设备指纹或动态签名；若仅复制 Cookie 仍不能稳定使用，就不把该路径写成已支持。
- 失败属于 `login_required`、`blocked`、`deleted`、`empty_content`、`unsupported_type` 还是临时网络错误。

### 5.3 进入开发的门槛

每个平台至少有一条可重复的匿名路径或**用户自有登录态路径**，才实现其自动适配器。登录态路径必须确认最小 Cookie 集、目标域名白名单、失效判定和撤销行为；仅在本机抓包环境偶发成功、必须绕过验证码或依赖无法解释的设备注入时，不进入生产实现。验证不通过的平台仍交付可靠接收、正确分类、补充材料和后续加工闭环。

## 6. 数据与来源语义

继续使用 `SourceRevision.metadata_json`，本轮不为平台元数据新建独立表。建议字段如下：

```json
{
  "platform": "xiaohongshu | wechat_channels | zhihu",
  "media_kind": "text | video",
  "source_type": "xiaohongshu | wechat_channels | zhihu",
  "source_label": "小红书 | 微信视频号 | 知乎",
  "original_url": "用户提交的链接",
  "canonical_url": "展开并校验后的内容链接",
  "source_locator": {
    "type": "xiaohongshu_note | wechat_channels_post | zhihu_answer | zhihu_article",
    "content_id": "经真实样本确认的稳定 ID",
    "question_id": "仅知乎回答可选",
    "answer_id": "仅知乎回答可选",
    "article_id": "仅知乎文章可选"
  },
  "coverage": "full_text | partial_text | metadata_only | screenshots_only | transcript_only",
  "content_scope": "caption | article | answer | image_post | video_post",
  "original_media_retained": false,
  "login_state_used": true,
  "images_archived": 0,
  "missing_materials": ["main_content", "post_images", "ocr_text", "transcript", "video_content"]
}
```

约束：

- `wechat_channels` 与公众号 `wechat_mp` 是两个来源，不能只因为都来自微信而合并。
- 小红书图文继续用 `media_kind=text`，通过 `content_scope=image_post` 区分；小红书视频用 `media_kind=video`。
- `source_type` 由服务端根据 `platform + media_kind` 派生，客户端 `source_hint` 仍只作采集提示，不能决定来源身份。
- `original_media_retained=true` 只表示相应原件确实进入 Bundle。保存页面 HTML、封面或截图，不等于保存了原视频。
- `login_state_used` 只记录本次是否使用了该用户会话，不记录 Cookie 名称、值、账号 ID 或凭据版本；Manifest/Obsidian 可省略该内部审计字段。
- 分享文案、平台正文、图片 OCR、用户备注、机器转写分别记录 origin，不拼成无法追溯的一段“原文”。

任务：

2. 增加三个来源的 `source_type/source_label/icon_key`，保留小红书现有兼容。
3. 把 Worker 的硬编码 `B 站 / 普通网页 / 其他` 分发扩为明确的平台分支；仍保持正文补充和字幕上传优先。
4. 为每个平台增加简单的任务级请求间隔；临时网络失败有限重试，登录墙/不支持类型不无限重试。

不要先搭通用插件框架。三个适配器返回相同的最小结果字段即可，共享代码只抽取已出现的 URL 归一、图片登记和 segment 生成逻辑。

### 7.2 每用户平台登录态托管

复用现有 `ProviderProfile + Credential` 信封加密，但把 B 站路由中的通用生命周期抽成小型服务，B 站现有接口保持兼容。新增：

- `xiaohongshu_session`
- `wechat_channels_session`
- `zhihu_session`

`wechat_channels_session` 超过 `ProviderProfile.kind` 当前的 20 字符限制，因此需要 Alembic 迁移把该列扩到 40，并同步模型声明；不能依赖 SQLite 不强制长度的偶然行为。

建议接口：

| 接口 | 语义 |
| --- | --- |
| `GET /v1/platform-sessions/{platform}` | 只返回 configured、verification、更新时间和脱敏检测结果 |
| `PUT /v1/platform-sessions/{platform}` | 用户提交 Cookie；服务端清洗、加密、替换旧版本并定向重排队 |
| `POST /v1/platform-sessions/{platform}/test` | 发起只读的账号/会话检测，不读取或修改用户内容 |
| `DELETE /v1/platform-sessions/{platform}` | 撤销活跃凭据；后续回到匿名提取或补充材料 |

其中 `{platform}` 必须是固定枚举，不能由请求方提供任意 endpoint。B 站 `/v1/bilibili-session` 暂不强制迁移到新 URL，避免破坏现有客户端。

登录态写入与使用规则：

1. 接受完整 Cookie 文本便于用户粘贴，但按 P0 实测结果只保留该平台确实需要的最小 Cookie 名称；其余字段立即丢弃。若平台必须保留多字段，规范化为确定性 secret JSON 后整体加密。
2. 拒绝 CR/LF、重复 Cookie 名、超长字段和非目标平台字段；输入上限只用于防滥用，不把原文回显到错误信息。
3. 每次更新创建新 Credential version 并撤销旧版；AES-256-GCM AAD 继续绑定 `user_id/profile_id/version`，任何 GET、事件和日志都不返回明文。
4. 认证 Cookie 只允许发往实测确认的**精确一方域名白名单**。每次重定向重新判断，跨域时删除 Cookie；图片、视频、字幕 CDN 默认不带登录态。
5. 匿名请求明确返回登录墙后才用该用户会话重试一次；`invalid` 不做网络退避，直接提示更新登录态；`blocked/network_error` 才按各自语义处理。
6. 检测接口只保存 `valid/invalid/blocked/network_error`、检测时间和必要的脱敏账号提示；不保存页面正文、Set-Cookie 或响应头。
7. 更新登录态只重排同用户、同平台、因登录原因等待且没有人工补充正文的条目；不能像全量 refetch 一样重跑所有内容。
8. 撤销后不再发起新的认证请求；正在执行的单次提取可能完成，结果仍只能写入该用户条目。文档和 UI 如实说明这一并发边界。
9. 平台登录态仅在服务端使用，不下发到 Obsidian、不允许本机绑定、不写入 Bundle/capture.json/SourceRevision/事件 payload。
10. 首版由用户给自己的账号配置，不增加管理员把同一 Cookie 批量代配给多人；如果以后需要试用代配，另做明确授权和风险评审。

兼容与轮换注意：

- 现有密文的 AAD 已使用固定 purpose 字符串。此次只扩展用途说明，不直接修改 `AAD_PURPOSE` 或 AAD 格式，否则历史 LLM/B 站凭据会全部无法解密；若以后要按凭据类型区分 purpose，必须做显式密文迁移与回滚验证。
- 默认忽略平台响应中的 `Set-Cookie`。如果 P0 证明某个平台必须轮换会话字段，只允许合并预先列入白名单的 Cookie 名，并以新 Credential version 重新加密；不得保存任意响应 Cookie。
- PUT/DELETE/test 继续要求 `profiles:manage`，Web 写操作沿用 CSRF 与 Origin 校验；会话表单不进入前端持久缓存。

适配器不直接查询 Credential 表。新增一个按 `user_id + platform` 读取、解密并返回短生命周期内存值的服务；调用结束后不缓存到进程全局，也不记录请求头。

### 7.3 小红书适配器

新增：`apps/server/kbserver/extractors/xiaohongshu.py`

P0 真实样本已确认（2026-09-17）：

- 短链有两种域：`xhslink.com` 与 `xhslink.cn/o/{token}`（App 分享）。
- `xhslink.cn` 短链 302 展开落在 `/login?redirectPath=<编码的笔记地址>`；
  redirectPath 里携带真实笔记地址（`/discovery/item/{note_id}?...&xsec_token=...`）。
  `xsec_token` 是分享授权凭证（尾随 `=`），匿名访问 `explore`/`discovery` 形态
  （带或不带 token）都会被 302 到登录页或 `/404/sec_*`（300031）——匿名路径
  确认不可用，自动读取依赖托管会话。
- 适配器（`xiaohongshu_note-1.1.0`）展开后若落在登录页，从 redirectPath 解出
  真实笔记地址，托管会话对它重试一次；成功页面按 `__INITIAL_STATE__`
  noteDetailMap 提取标题/正文/作者/发布时间。

处理顺序：

1. 从 `original_url/share_text` 取第一条受支持 URL（`xhslink.com`/`xhslink.cn`）。
2. 通过 `safe_fetch` 展开短链；每一跳继续做 SSRF、大小、超时和重定向校验。
3. 落在登录页时从 redirectPath 解出真实笔记地址；先匿名读取，明确遇到登录
   限制时才加载该用户 `xiaohongshu_session` 对真实地址重试。
4. 优先读取稳定的结构化数据；结构不存在时可读取明确的正文容器，但不把导航、推荐流或评论混入正文。
5. 图文笔记按页面顺序保存可访问原图，记录每张图片的来源 URL、顺序、摘要和下载失败；图片数和单图大小沿用现有限额。
6. 视频笔记保存文字说明、封面和媒体存在性，不默认拉取原视频。能取得稳定音频引用也先记录能力，是否接入 ASR 由单独样本结论决定。
7. 原始页面或结构化响应保存到 `originals/xiaohongshu/{note_id}/`；生成 `normalized.md`、`readable.md`、`segments.json`。

失败语义：

- `login_required`：页面明确要求登录（登录页落点、登录标记或 sec 风控墙）。
- `blocked`：访问被风控或拒绝。
- `deleted`：内容已删除/不可见。
- `structure_changed`：页面可访问但已知结构全部失效；按终态进入补充材料并记录适配器版本，不用网络重试掩盖结构问题。
- `unsupported_type`：直播、合集、账号页等不在首版范围。

### 7.4 微信视频号适配器

新增：`apps/server/kbserver/extractors/wechat_channels.py`

P0 真实样本已确认（2026-09-17）并按其实现：

- URL 形态：短链 `weixin.qq.com/sph/{id}` 302 展开到
  `channels.weixin.qq.com/finder-preview/pages/sph?id={id}`；sph 短 id 即稳定内容 ID
  （接口返回的 `dynamicExportId` 带过期时间，不用作 ID）。
- finder-preview 播放壳是纯 JS 渲染，HTML 无元数据；页面自身调用公开 Web 接口
  `POST /finder-preview/api/feed/get_feed_info`（body `{"baseReq":{"generalToken":""},"shortUri":id}`）
  返回 feedInfo/authorInfo 元数据。该接口匿名可读（HTTP 201），但强校验同源
  `Origin` + `Referer`（缺任一返回 401 permission verification failed）；
  `fetch_base.post_json` 统一按目标 URL 补 Origin、调用方传来源页 Referer。
- 无需托管登录态即可取得：作者昵称、说明文字、发布时间（createtime 秒级时间戳）、
  封面图 URL 与互动计数。

适配器行为（`wechat_channels_page-1.1.0`）：

1. 保留完整分享文字，并从中分离 URL、平台给出的标题/作者提示；分享文字只标记为 `share_text`，不是视频全文。
2. 展开分享链接，保存最终 URL、原始 HTML 和 sph 稳定内容 ID；匿名访问不足时使用该用户 `wechat_channels_session` 重试，Cookie 仍只发往实测白名单域名。
3. 能解析出 sph id 时调上述公开接口读取元数据，`coverage=metadata_only`；说明文字进入规范正文并明确标注"不是视频转写"；封面图按 include_images 开关下载；原视频不下载，写入 `missing_materials`。
4. 接口失败或无 sph id 时退回页面 og 元数据解析；登录/环境墙如实进入补充材料；纯播放壳标记 `shell_only`，不冒充已取得视频内容。
5. 不实现基于非公开接口的下载器；字幕/音频由用户补充走现有路径（字幕文件、上传录音与 ASR、正文摘录生成新 SourceRevision）。

当接口不可用时，视频号仍做到：来源显示正确、链接和分享包可在 Obsidian 中打开、用户能直接补材料、状态文案说明"视频号未提供可读取的文字内容"，而不是显示笼统的"适配器缺失"。

### 7.5 知乎适配器

新增：`apps/server/kbserver/extractors/zhihu.py`

处理对象分为：

- `zhihu_answer`：从 URL 固定 `question_id + answer_id`，只提取该回答。
- `zhihu_article`：从专栏 URL 固定 `article_id`，只提取该文章。
- 只有 `question_id`：保存问题标题和链接，进入“请选择或补充具体回答”。

正文解析要求：

1. 优先评估官方数据开放平台，但必须先通过“精确 URL/ID 读取、授权与归档、费用”门槛；未通过时使用页面适配。
2. 页面适配先匿名读取，遇到明确登录限制时使用该用户 `zhihu_session`；从稳定结构化数据或明确正文容器提取，保留标题层级、段落、引用、列表、代码块和图片顺序。
3. 过滤相关推荐、其他回答、评论和页脚。
4. 盐选或折叠内容只保存实际公开可见部分，`coverage=partial_text`，缺失项写入 `missing_materials`。
5. 原始响应保存到 `originals/zhihu/{content_type}/{id}/`；正文片段 locator 至少包含内容类型、ID 和段落序号。

如果接入知乎官方 API，新增管理员级 `zhihu_content_api` 配置，不使用用户的模型 Key，也不把 Access Secret 下发到浏览器或 Obsidian。它不得混入模型配置或模型用量语义；若平台产生费用，先在管理员侧单独确认接入和限额，不为此恢复已移除的用户费用模块。

### 7.6 图片 OCR 与用户补充

这是小红书真正可用的关键路径，不能只完成 URL 识别后就称为支持。

建议新增 `ocr` Job stage（或语义等价的独立持久化任务），而不是在 Capture 请求中同步调用视觉模型：

1. 输入是用户上传截图和已归档的小红书笔记图片；每张图保留文件 ID、顺序和 SHA-256。
2. 使用当前用户配置的 `vision_ocr` Provider；没有配置时原图仍成功入库，状态为“图片已保存，尚未识别文字”。
3. OCR 输出逐图保存原始 JSON 和规范文字，segment locator 指向图片文件与图序。
4. 低置信度、空结果和图片说明分别记录；OCR 文本不得覆盖平台原有正文。
5. OCR 完成后生成新的不可变 SourceRevision，再触发 enrich；迟到的旧 OCR/AI 结果不能覆盖更新后的材料。
6. OCR 失败只影响文字识别，不删除图片、不把整个条目标成丢失。

需要同步扩展用户补充接口/UI，使一次补充可以带正文、截图和字幕/音频，并明确显示各类材料实际是否已保存。

### 7.7 Web、WorkflowView 与 Obsidian

Web：

- 采集框识别三类链接并显示正确来源；仍允许用户直接提交，不要求先连接平台账号。
- 设置页增加“小红书 / 微信视频号 / 知乎登录态”卡片，统一提供保存、检测和撤销；保存成功后清空输入框，永不回填 Cookie。
- 登录态帮助文案说明用途、风险和建议使用可单独退出的账号；不承诺平台会话永久有效，也不把 Cookie 复制教程伪装成官方授权。
- 小红书图文提示“会同时保存可取得的笔记图片”；视频号/小红书视频不显示误导性的“将保存原视频”。
- 详情页按 `available_actions` 提供“补充正文”“上传截图”“上传字幕/音频”“重新提取”。
- 原因码映射为用户语言，不直接显示 `login_required`、`structure_changed`、内部 revision 或异常堆栈。

`WorkflowView`：

- 小红书/视频号/知乎登录墙且未配置会话时，给出“连接该平台”操作；会话失效时给出“更新登录信息”；已经配置仍不可读时再提示补充截图或文字。
- 知乎问题页使用“请选择具体回答，或粘贴要保存的正文”。
- OCR 有确定总图片数时才显示百分比；没有总数时只显示“正在识别图片文字”。
- “已发布到 Obsidian”仍以当前 Bundle 的有效 Receipt 为准，不因云端生成 Bundle 就提前完成。

Obsidian 插件：

- `KbSource` 类型增加可选 `source_type/source_label/icon_key/media_kind`，兼容旧 Manifest。
- `kb_source_type` 写派生 `source_type`，另写 `kb_source_platform` 与 `kb_media_kind`。
- Source 正文用 `source_label` 展示“微信视频号 / 小红书 / 知乎”，不显示内部枚举。
- 图片、原始 HTML/JSON、OCR 结果和字幕按角色链接；明确“已保存页面/封面”不等于“已保存原视频”。
- 继续保护用户人工区和用户改过的正文，不因重新提取覆盖。

## 8. 验证与测试

### 8.1 自动化测试

新增平台级 fixture 和集成测试，网络全部用脱敏响应替身：

- 短链展开、域名识别、内容 ID 和 canonical URL。
- 小红书图文/视频、知乎回答/文章、视频号公开页的成功结果。
- 页面登录墙、已删除、风控、结构变化、网络超时和重试边界。
- 只提取目标内容：不混入推荐、其他回答、评论或分享摘要。
- 图片顺序、数量上限、下载失败、原件 SHA、OCR locator。
- `platform/source_type/media_kind/source_label` 从 Item、Manifest、列表到 Obsidian 一致。
- 补充材料产生新 SourceRevision，旧任务结果不覆盖新版本。
- 凭据、平台 Cookie、页面私有内容不进入日志、事件或 Bundle。
- A 用户的登录态绝不用于 B 用户；Cookie 只发送到平台精确白名单，跨域重定向和 CDN 请求均不携带。
- 登录态新增、更新、检测、撤销与定向重排队；无关平台和已人工补充条目不被重跑。
- 当前 Bundle 有回执前不得显示“已发布到 Obsidian”。

优先扩展 `tests/integration/test_m4_web.py` 的来源路由覆盖；三家适配器的复杂 fixture 可各自拆文件，避免继续把所有 M4 测试堆进一个大文件。

### 8.2 真实样本验收

在本地和腾讯云各跑一次样本矩阵，记录“自动全文 / 部分材料 / 需补充 / 临时失败”，不以单个成功样本代替成功率。

最低验收：

1. 三个平台分享链接都能在手机提交并立即显示正确来源。
2. 每个平台至少一条可自动路径能生成可定位的 `normalized.md` 并进入 AI 加工。
3. 匿名访问受限时能用当前用户的有效登录态继续；登录态缺失、失效或仍被拒绝时，链接、分享文字和用户上传原件仍可在 Obsidian 获取。
4. 小红书截图 OCR 可追溯到具体图片，失败不丢原图。
5. 知乎回答不会混入同题其他回答；文章保留标题层级、引用和代码块。
6. 视频号没有文字内容时不会用标题生成摘要；补充字幕/音频后可继续加工。

## 10. 完成定义

满足以下条件才称为“三个平台已接入”：

- 链接识别、来源标签、过滤和 Obsidian frontmatter 全链一致。
- 自动取得的每段正文、每张图片和每份 OCR/字幕都有来源定位和原件证据。
- 无法访问时有明确、可执行的补充入口，不显示原始错误或泛化的“处理失败”。
- 用户可以自愿托管自己的平台 Cookie；凭据按用户加密、只进不出、可检测和撤销，绝不跨用户回退，也不进入 Bundle、日志、Obsidian、跨域重定向或 CDN 请求。
- 不使用抓包、验证码绕过、自动登录或常驻浏览器；Cookie 本身不足以稳定读取的平台如实降级。
- 页面结构变化不会把错误页面、推荐流、标题或 AI 生成内容发布成“原文”。
- 生产前完成真实样本矩阵，并在文档中公布各平台当期实际成功范围与限制。

以下不属于本轮完成条件：平台账号搜索、批量导入、评论归档、直播、原视频长期存档，以及对所有公开视频的全文/字幕获取保证。
