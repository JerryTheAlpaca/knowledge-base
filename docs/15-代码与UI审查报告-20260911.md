#### C-01 本地整理的 `localHash` 读错分区标记，且字段为死代码

**具体表现**
`apps/obsidian-plugin/src/knowledge/organize.ts:247`：

```typescript
const cloud = extractPartition(text, CLOUD_DIGEST_START, CLOUD_DIGEST_END);
const local = extractPartition(text, KNOWLEDGE_START, KNOWLEDGE_END);   // ← 应为 LOCAL_ORGANIZE_*
...
localHash: local === null ? null : await sha256Hex(local),              // ← 无任何消费者
```

`DigestInput.localHash` 的注释是「本地整理区当前哈希；用于判断是否已整理过」，但取的是 **Knowledge 分区标记**（`kb:knowledge`）。Digest 笔记实际只有 `kb:cloud-digest` 与 `kb:local-organize` 两个分区（见 `template.ts:396-402`），因此 `local` 恒为 `null`，`localHash` 恒为 `null`。

经 `rg "localHash" apps/obsidian-plugin/src` 全量搜索，该字段**只有定义处（`organize.ts:99`）与赋值处（`:312`）两处**，没有任何读取方。真正用于基线判断的是 `cloudHash`（`organize.ts:524` 与 `task.digest_cloud_hash` 比对）和 `base_hash`（`apply()` 里对 Knowledge 正文重算）。模板层已经提供了正确的三分区哈希函数 `partitionHashes()`（`template.ts:100-113`），但未被 `readDigestInput()` 使用。

**影响范围**
- 当前无实际功能异常（因为 `localHash` 未被消费），属**潜伏缺陷**：一旦后续给「已整理过则跳过」加缓存判断，就会基于恒 `null` 的值做出错误决策。
- 更实质的问题是**重复实现**：`organize.ts` 手写分区哈希，`template.ts` 已提供 `partitionHashes()`，两套逻辑并存，未来改标记命名时极易漏改一处。

**可执行改进建议**
1. 若短期不做本地整理区缓存，直接删除 `DigestInput.localHash` 字段与 `organize.ts:247/312` 两行，减少无效代码与误读风险。
2. 若要保留，改为 `extractPartition(text, LOCAL_ORGANIZE_START, LOCAL_ORGANIZE_END)`，并让 `readDigestInput()` 复用 `template.ts` 的 `partitionHashes()`，删除重复逻辑。

#### C-02 同步引擎 `status` getter 恒返回占位值

**具体表现**
`apps/obsidian-plugin/src/sync/engine.ts:110-120`：

```typescript
get status(): EngineStatus {
  return {
    running: this.running,
    cursor: 0,          // ← 恒为 0
    pendingCount: 0,    // ← 恒为 0
    lastRunAt: null,    // ← 恒为 null
    ...
  };
}
```

`SyncEngine` 不缓存 `SyncState`（状态每次经 `deps.loadState()` 从 `data.json` 读，见 `engine.ts:145/160`；`EngineDeps` 中无 `state` 字段）。真实值只在 `runOnce()` 内通过 `deps.onStatus({...})` 推送，而 `main.ts:140-147` 把推送结果存进 `plugin.lastStatus`。

`main.ts` 中 `StatusView.render()`（`:57-83`）的读取方式混用了两个来源：

```typescript
["待入库", String(st?.pendingCount ?? 0)],                    // st = lastStatus，正确
["接上", st?.lastRunAt ? new Date(st.lastRunAt).toLocaleString() : "—"],
["游标", String(this.plugin.syncState?.cursor ?? 0)],         // 另一来源
```

其中 `st` 来自 `lastStatus`、走 `onStatus` 推送路径，`pendingCount` 与 `lastRunAt` 基本正确；但 **`get status` 这个公开 getter 本身是坏的**——任何调用 `engine.status` 的代码（包括未来新增的调用方、或调试时在控制台取值）都会拿到 `cursor: 0 / pendingCount: 0 / lastRunAt: null` 的假数据。同时 `StatusView` 5 秒重绘一次（`main.ts:54`），若某次同步尚未运行过（插件刚加载、自动同步未触发），`lastStatus` 为 `null`，「上次同步」会一直显示 `—`，即使用户此前已同步成功过（因为该值不从 `data.json` 的 `syncState.lastRunAt` 兜底）。

**影响范围**
- 状态面板的「上次同步 / 待入库」在部分时序下显示占位值，用户无法判断同步是否正常。
- `engine.status` 作为公开 API 返回错误信息，是明确的逻辑缺陷，会误导后续调用方。

**可执行改进建议**
1. 在 `SyncEngine` 内维护 `private state: SyncState | null`，`runOnce()` 中 `loadState()` 后写入，`status` getter 优先返回缓存的真实值，未加载时再回退占位。
2. `StatusView.render()` 的 `lastRunAt` / `cursor` 统一改为「`lastStatus` 优先，回退 `plugin.syncState`」，避免两条数据源不一致。

#### C-04 模型直连传输层把「响应超时」误判为「连接未建立」，存在重复计费风险

**具体表现**
`apps/obsidian-plugin/src/providers/transport.ts:28-36`：

```typescript
const message = err instanceof Error ? `${err.name}: ${err.message}` : String(err);
// 连接阶段失败（DNS/拒绝连接）→ 请求未发出，可安全重试；
// 其余（读超时等）→ 可能已送达并计费，标记结果未知。
if (/ECONNREFUSED|ENOTFOUND|EAI_AGAIN|ECONNRESET|Connect|connect/i.test(message)) {
  return { status: 0, text: "", connectFailed: true };
}
return { status: 0, text: "", timedOut: true };
```

正则末段的 `Connect|connect` **没有词边界约束**，会匹配任何含子串 "connect" 的报错文案，典型如 `Error: connect ETIMEDOUT 1.2.3.4:443`、`Cannot connect to ... after timeout`、`connect timeout`。

而上层 `local.ts:305-310` 对两者的处理语义**截然相反**：

```typescript
if (res.connectFailed) {
  throw new LocalModelError("连接模型服务失败（请求未发出，可重试）。", "retryable");   // → 会被自动重试
}
if (res.timedOut) {
  throw new LocalModelError("模型服务响应超时（结果未知，不自动重发）。", "unknown_outcome");
}
```

`retryable` 在 `organize.ts:452-470` 的 `runBatch` 中会被下一次批量运行**自动重试**，而 `unknown_outcome` 会停在任务态等用户显式点按（`organize.ts:446-449`）。这正是 `docs/08 §8.2` 设计的「不盲目重发以防重复计费」保护。

**影响范围**
- 真实场景：TCP 连接已建立、请求体已送达供应商、后续读超时——报错文案若含 "connect"，会被标为 `retryable`；下一次自动批量就会**重发同一次模型调用**，导致同一篇 Digest 被计费两次，并可能产生两份语义略有差异的晋升判断互相覆盖。
- 这与「已送达但超时需标 `unknown_outcome`」的严格语义直接冲突，是本项目商业约束（用户自付 API 费用）下的正确性问题。

**可执行改进建议**
收紧判定，只认明确的连接建立失败信号：
```typescript
if (/ECONNREFUSED|ENOTFOUND|EAI_AGAIN|ECONNRESET|ENETUNREACH|EHOSTUNREACH|ERR_CONNECTION_REFUSED/i.test(message)) {
  return { status: 0, text: "", connectFailed: true };
}
```
同时把 `timedOut` 判定显式化（Obsidian `requestUrl` 的超时文案通常含 `timeout` / `Timeout`），并在两分支都保留 `message` 原文用于日志排查。

### 🟠 中高：正确性偏差 / 用户可感知的体验缺陷

#### C-05 引用注入只处理首个 `[claim_id]`，同一观点重复出现时后续无依据

**具体表现**
`apps/obsidian-plugin/src/knowledge/citations.ts:121-127`：

```typescript
const marker = `[${claimId}]`;
const at = out.indexOf(marker);          // ← 只取首个匹配
if (at === -1) continue;
const tail = out.slice(at, at + marker.length + 24);
if (tail.includes("依据：")) continue;
out = `${out.slice(0, at + marker.length)}${citation}${out.slice(at + marker.length)}`;
```

`indexOf` 只返回第一处位置。若同一 `claim_id` 在受管理正文里出现两次（例如「## 核心认知」引用一次、「## 相关联系」再次引用同一观点），只有第一处会被注入「依据：」链接。

**影响范围**
- 证据链完整性被削弱：`docs/08 §6.1` 要求「每个结论可两跳回到当时原文」，重复引用的位置成为断链点，用户点击时无依据可跳。
- 对同 ID 多处的设计意图（多处引用同一观点）没有覆盖。

**可执行改进建议**
改为 `while` 循环匹配全部出现位置，每处独立判断 24 字符窗口，已注入的跳过：
```typescript
let from = 0;
while (true) {
  const at = out.indexOf(marker, from);
  if (at === -1) break;
  const tail = out.slice(at, at + marker.length + 24);
  if (!tail.includes("依据：")) {
    out = `${out.slice(0, at + marker.length)}${citation}${out.slice(at + marker.length)}`;
    from = at + marker.length + citation.length;
  } else {
    from = at + marker.length;
  }
}
```

#### C-06 进程内内存限流：多进程/重启失效，且字典无上限会持续增长

**具体表现**
四处限流全部是模块级内存字典，无过期清理：

| 文件 | 变量 | 键 | 窗口 |
|---|---|---|---|
| `api/routes_auth.py:45` | `_attempts: dict[str, list]` | IP | 10 分钟 / 30 次 |
| `api/routes_pairing.py:26` | `_attempts: dict[str, list[datetime]]` | IP | 同窗口 |
| `api/routes_items.py:555` | `_REFETCH_LAST_AT: dict[tuple[str,str], float]` | (user_id, item_id) | 600 秒 |
| `api/routes_profiles.py:56` | `_TEST_LAST_AT: dict[tuple[str,str], float]` | (user_id, profile_id) | — |

以 `routes_auth._check_rate` 为例：

```python
def _check_rate(request: Request) -> None:
    ip = request.client.host if request.client else "unknown"
    now = utcnow()
    window = [t for t in _attempts.get(ip, []) if now - t < _RATE_WINDOW]
    if len(window) >= _RATE_LIMIT:
        raise ApiError("RATE_LIMITED", "尝试过于频繁，请稍后再试", status_code=429)
    window.append(now)
    _attempts[ip] = window
```

**影响范围（三条独立问题）**
1. **重启即清零**：容器重启、部署滚动更新后限流窗口全部失效，攻击者可利用重启窗口重置配额。
2. **多进程不共享**：若将来 `uvicorn --workers N > 1`，实际限流阈值变成 `N × 30`；`_REFETCH_LAST_AT` 的「每条目 10 分钟限一次」也会被放大为 N 倍。
3. **内存只增不减**：`ip → list` 的键（IP）与 `(user_id, item_id)` 键**永不删除**；即使列表被修剪成空，键仍留在字典中。长期运行下被扫描的 IP 空间有多大，字典就有多大——是**明确的慢速内存泄漏**。`routes_auth` / `routes_pairing` 是未鉴权端点，攻击者可主动放大这点。

**可执行改进建议**
项目当前是单进程 SQLite 架构（`AGENTS.md` 明确不引入 Redis），因此**不必上分布式限流**，但应消除泄漏与重启失效：
- 内存方案加固：把 `dict[str, list]` 换成 `dict[str, tuple[float, int]]`（窗口起点 + 计数），或定期（如每 5 分钟）清空 `len(window) == 0` 的键；对 `_REFETCH_LAST_AT` / `_TEST_LAST_AT` 增加「超过 2× 窗口即 `pop`」的惰性清理。
- 若要在意重启失效，改为落表（`RateLimit(kind, key, window_start, count)`，复用现有 SQLite 与清理任务 `retention_sweep`），代价可控且与现有架构一致。

#### C-07 `list_items` 的逐条 N+1 查询

**具体表现**
`apps/server/kbserver/api/routes_items.py:189-196`：

```python
for it in items:
    src = db.query(SourceRevision).filter(
        SourceRevision.item_id == it.id, SourceRevision.revision == it.source_revision
    ).one_or_none()
    if src:
        outs.append(_item_out(it, src, db))       # ← _item_out 内部又调 _analysis_bundle()
```

而 `_analysis_bundle()`（`:98-109`）是一次独立查询：

```python
return (db.query(BundleRevision).filter(...).order_by(BundleRevision.revision.desc()).first())
```

即 **每个列表项产生 2 次查询**（SourceRevision 1 次 + 最新 Bundle 1 次）。列表接口 `limit` 上限 200（`:187`），最坏情况 400 次查询。

**影响范围**
- 收件箱首屏与 30 秒轮询（`inbox.html` 底部 `setInterval`）每次都触发全量 N+1，是**最热的读路径**。
- 服务器为 2 核 2GB 且 SQLite 单写者（`BEGIN IMMEDIATE` 领取任务），读放大直接与 Worker 争数据库锁，表现为列表加载变慢、同步期间页面卡顿。

**可执行改进建议**
把两段循环查询改为两条批量查询 + 内存 join：
```python
# 1) 一次取回本页所有 SourceRevision
srcs = {(s.item_id, s.revision): s for s in db.query(SourceRevision).filter(
    SourceRevision.item_id.in_([it.id for it in items]))}
# 2) 一次取回本页所有候选 Bundle，按 item 取 revision 最大者
bundles: dict[str, BundleRevision] = {}
for b in db.query(BundleRevision).filter(
        BundleRevision.item_id.in_([it.id for it in items]),
        BundleRevision.processing_state.in_(["ready", "failed"]),
    ).order_by(BundleRevision.revision.asc()):
    bundles[b.item_id] = b            # 升序遍历，后者覆盖前者 = 最大 revision
```
再让 `_item_out()` 接受可选的 `analysis_bundle` 参数复用结果。

`apps/server/kbserver/workers/worker.py:666-702`：

#### C-09 服务端 `MAX` 上限与提示词约束不一致

**具体表现**
`apps/server/kbserver/domain/analysis.py:18-24`：

```python
LIMITS = {"key_points": 12, "excerpts": 12, "methods": 10, "insights": 5, "limitations": 10}
```

`apps/server/kbserver/domain/templates.py:163`（以及 `:232` 的第二个变体）：

```
"key_points 最多 7 条，excerpts 最多 7 条，methods 最多 5 条，insights 最多 3 条。"
```

校验阈值普遍是提示词的 **1.5～2 倍**（`key_points` 12 vs 7、`insights` 5 vs 3）。校验层只拒绝 `> LIMITS`，因此模型即使输出 8 条 `key_points` 也会通过校验并入库。

**影响范围**
- 提示词与校验器的约束理应同源（`templates.py:58-66` 的 `EXCERPT_RULES` 就是这个设计意图：「提示词与校验共用同一套表述」），此处偏离会导致**实际输出条数不稳定**。
- 下游影响：`organize.ts` 的晋升判断按 claim 逐条调模型，`key_points` 越多，单次晋升提示越长、成本越高；前端 `renderDigestPane` 渲染的观点列表长度也随之波动。

**可执行改进建议**
不要手工对齐两个数字，而是让提示词从 `LIMITS` 派生。例如在 `templates.py` 中：

```python
from .analysis import LIMITS
PROMPT_LIMITS = {   # 提示词用更保守的引导值，校验用宽松上限
    "key_points": 7, "excerpts": 7, "methods": 5, "insights": 3,
}
```
并在构造提示词时用 f-string 注入，同时在文件头注释写明「引导值 < 校验值」是有意为之（留出模型溢出的容错空间）。若两者本应相等，则把 `LIMITS` 直接下调到提示词数值。

#### C-10 `safe_fetch` 全文读入内存后才校验大小

**具体表现** `security/safe_fetch.py:196-204`：

```python
declared = resp.headers.get("content-length")
if declared and int(declared) > limit:
    raise SafeFetchError("PAYLOAD_TOO_LARGE", ...)
content = resp.content          # ← 全量进内存
if len(content) > limit:
    raise SafeFetchError("PAYLOAD_TOO_LARGE", ...)
```

**影响范围**：`limit` 默认 5MB（`config.py:29`），最坏情况一次分配 5MB+；当存在多个并发网页提取时对 2GB 内存的服务器构成压力。攻击者可不发 `content-length`（chunked）绕过第一道检查，从而必然走到 `resp.content` 的全量读。

**改进建议**：本模块已有正确的流式实现 `stream_to_sink()`（`:215-272`，逐块计数并在超限时抛 `PAYLOAD_TOO_LARGE`）。让 `safe_fetch()` 复用它把内容写入 `io.BytesIO`，或直接在有界流上累积，彻底去掉 `resp.content` 路径。

#### C-11 段落分组存在 O(n²) 文本长度重算

**具体表现** `domain/` 下段落分组函数（`_group_timed()` / `_group_article()`）在每段循环内重复计算累计长度 `sum(len(...))`。

**影响范围**：ASR 长转写（20 分钟音频可产生数千个 cue）走这条路径时，复杂度从 `O(n)` 退化为 `O(n²)`，是流水线中较重的 CPU 消耗点。

**改进建议**：循环外维护增量游标 `cursor += len(seg)`，或先做一次前缀和数组再按索引取差。

#### C-12 `webpages` 提取的重复 DOM 遍历

**具体表现** `extractors/webpages.py` 的 `_content_root()` / `_text_of()` 在候选根节点上重复遍历，且每次遍历都重新拼接字符串。

**影响范围**：网页提取是 Worker 单线程内执行，重复遍历与字符串重算直接拉长单条任务的占用时间，挤占其他排队的提取任务。

**改进建议**：先做一次遍历把「候选根 → 文本 + 长度」算好缓存，再在候选间比较；避免在比较循环里调用会重算文本的函数。

#### C-13 `bilibili.extract()` 用 `time.sleep` 阻塞 Worker

**具体表现** `extractors/bilibili.py` 中三处 `time.sleep(_REQUEST_GAP_S)`。

**影响范围**：Worker 是**单线程串行执行**（`worker.py` 主循环），`sleep` 期间无法处理其他任务。多用户同时提交 B 站链接时，每个请求都要串行等待限速间隔，队列延迟叠加。

**改进建议**：这不是缺陷而是 B 站反爬的必要节流，但应改为**让出式等待**——在 sleep 前后检查取消/让出信号（参照 `asr.py` 的 `_pause_run()` 忙碌让出模式），使 Worker 在等待期间能领其他阶段的任务，而不是纯粹空转。

#### C-14 `idle.AsrGate` 状态为进程内内存，且非 Linux 恒不空闲

**具体表现** `workers/idle.py`：`sample_host()` 读 `/proc/stat` 与 `/proc/meminfo`，非 Linux 或读取失败返回 `None`；`AsrGate._samples` 是进程内 `deque`。

**影响范围**
- 开发环境（Windows）下 `metrics_available()` 为假，`can_start()` 命中 `metrics_unavailable` 分支 → **ASR 永远不启动**，本地无法端到端调试转写链路。
- 若将来多 Worker 并行，各进程的 `_samples` 互不可见，空闲判定会各自为政。

**改进建议**：保留「读不到指标时保守不启动」的安全默认（这是对的），但在 `metrics_unavailable` 时增加一个显式配置开关（如 `ASR_IGNORE_IDLE_GATE=1`）供本地开发；并在日志里明确打出跳过原因，避免开发者误判为 ASR 故障。

#### C-15 `asr.py` 生产代码使用 `assert`

**具体表现** `workers/asr.py:1105`：

```python
assert source is not None  # _load_context 语义：发布前已确认存在
```

**影响范围**：Python `-O` 会剥离 `assert`；且断言失败抛 `AssertionError`，会被上层通用异常处理当作「未知错误」记录，丢失语义。若上下文确实保证存在，这里就是多余的运行期检查；若不保证，`assert` 是错误的表达方式。

**改进建议**：改为显式分支——若不变量成立就删掉这行；若需要防御，抛 `RuntimeError` 并附上下文（item_id / source_revision），让错误信息可用于排查。

#### C-16 若干接口存在无意义的重复 `commit`

**具体表现** `routes_profiles.py:257-263`（写凭据后）与 `:570-578`（连接测试）等处，在紧邻的语句间连续 `db.commit()`。

### 🟠 中高：用户可感知的体验缺陷

#### U-01 小按钮触控目标低于 44×44px 规范

**具体表现**
`inbox.html:61` 与 `admin.html:43`：


或对列表行内按钮改用 44px 高度、靠内边距压缩视觉重量。

#### U-02 确认弹窗未做焦点管理（焦点陷阱 / 返回焦点）

#### U-03 列表内联 `onclick` 拼接存在破损与注入风险

**具体表现** `inbox.html:1076-1077`：

```javascript
(failed ? '<button class="small danger" onclick="event.stopPropagation();reprocessItem(\'' +
  esc(it.item_id) + '\')">重试</button>' : "")
```

`esc()` 只转义 HTML 实体（`& < > " '`），在**单引号 JS 字符串**上下文里，`&#39;` 会被 HTML 解析器还原成 `'`，从而闭合字符串。`item_id` 当前是服务端生成的 ULID 类字符串（安全），但这是**依赖数据格式的隐式契约**。

**影响范围**：一旦 item_id 来源变化（如引入用户可影响的标识），立即变成脚本注入；同时该写法与页面其它地方的事件委托模式（`data-key` / `data-ids` + `addEventListener`）不一致，维护时容易漏改。

**可执行改进建议**：改为 `data-item-id` 属性 + 在 `itemList` 上做事件委托，与 `evidenceButtons` / `jumpEvidence` 的现有模式统一。这同时消除了 `event.stopPropagation()` 打补丁的必要。

#### U-04 状态面板部分字段显示占位值

### 🟡 中：视觉一致性与可维护性

#### U-05 两个页面的样式大面积重复定义

**具体表现**：`admin.html` 的 `<style>`（`:8-116`）与 `inbox.html` 的 `<style>` 存在大量逐字重复的规则——`.brand`、`.spacer`、`button` / `.btn` 全家、`.badge` 与状态色类、`.overlay` / `.modal` / `.modal-title` / `.modal-body` / `.modal-foot`、`#toasts` / `.toast`、`.spin` / `@keyframes rot`。`authorize.html` 也重定义了 `button` / `button.primary`。

**影响范围**
- 改一处按钮圆角或 toast 位置需要同步改三处；`tokens.css` 已经统一了**变量**，但**组件规则**仍在各自复制。
- 实际已经出现漂移：`inbox.html:61` 是 `button.small, .btn.small`（两个选择器），`admin.html:43` 只有 `button.small`——同一设计意图、不同覆盖面。

**可执行改进建议**
在 `tokens.css` 之后新增 `components.css`（或直接扩入 `tokens.css`），把 `button` / `.btn` / `.badge` / `.modal` / `.toast` / `.card` 这些**三页共用**的组件规则集中一处，页面内 `<style>` 只保留该页独有的布局规则。这是本次审查中**收益最高的 UI 改进项**。

---

#### U-06 深色模式下存在硬编码的浅色值

**具体表现**：`inbox.html:308` 的 `background: #fff; box-shadow: 0 1px 3px rgb(0 0 0 / 0.25);`（switch 滑块）。以及三页共 6 处 `color: #fff`（`inbox.html:55/125/238`、`admin.html:38`、`authorize.html:22`）。

**影响范围**
- `#fff` 用在 accent / ok / warn 背景上的**按钮文字**，深色模式下这些背景色变浅（`--accent: #E08A67`），白字对比度下降到约 2.3:1，**低于 WCAG AA 的 4.5:1**。
- `:308` 的滑块是深色模式下最明显的一处硬编码：浅色底 `#fff` 配深色轨道，视觉突兀。

**可执行改进建议**
- 按钮文字改用 `--surface`（深色模式下自动变深）或新增 `--on-accent` 令牌并在两套主题里各给一个保证 ≥4.5:1 的值。
- `:308` 的 `#fff` 换成 `var(--surface)`。

---

#### U-07 三页视觉语言存在细微差异

**具体表现**
- **卡片内边距**：`inbox.html:397` 在 720px 档把 `.card` 内边距压到 18px，`admin.html:110` 同样处理，但 `authorize.html` 的 `.card` 固定 `28px 26px`（`:16`），三档断点下均不调整。
- **主按钮 hover**：`inbox.html` 用 `--accent-hover`（符合 tokens 注释「hover 加深（替代 opacity）」），`admin.html:39` 也用 `--accent-hover`，`authorize.html:23` 同样——这一项是一致的；但 `button:hover` 的边框色，`inbox.html` 是 `--text-2`，`admin.html:37` 也是 `--text-2`，`authorize.html` **没有定义 hover 边框**。
- **边框语义**：`authorize.html` 内部用 `--border`（`:15`），而 `inbox.html` 的输入框用 `--border-strong`（`:70`）；`admin.html` 的 `.pwrow input` 用 `--border-strong`（`:102`）。表单控件的边框令牌在不同页面不统一。

**影响范围**：品牌感与「同一产品」的认知一致性受损；在新页面里「该用哪个令牌」需要重新判断。

**可执行改进建议**：明确约定「容器边框 = `--border`，可交互控件边框 = `--border-strong`」，写进 `tokens.css` 注释，并让三页遵守。

#### U-08 弹窗遮罩色未走令牌，深色模式下偏重

**具体表现**：`inbox.html:384` 与 `admin.html:89` 均为 `background: rgba(31, 30, 27, .45)`——固定值，与 `--text` 的浅色值（`#1F1E1B`）同源但不随主题变化。

**影响范围**：深色模式下（页面底色 `#21201C`）45% 的浅色遮罩叠上去，对比不足，弹窗与背景的分层感弱于浅色模式。

**可执行改进建议**：抽出 `--overlay` 令牌，深色模式调到 `.60`～`.65`。

### 响应式适配小结

| 断点 | `inbox.html` | `admin.html` | `authorize.html` |
|---|---|---|---|
| 720px | ✅ 内边距收紧、`.grid2` 单列、列表行内距调整 | ✅ 内边距收紧、卡片内距收紧 | ❌ 无断点 |

| 360px | ✅ 隐藏非激活段文字（stepper 兜底） | ❌ 无 | ❌ 无 |
| `pointer: coarse` | ✅ 表单字号 16px | ❌ | ❌ |

**结论**：`inbox.html` 的响应式是三页中最完整的（有 M1–M8 走查支撑）；`admin.html` 只覆盖了基础内边距与 toast；`authorize.html` **完全没有响应式处理**。考虑到授权页会在手机上打开（登录跳转回来时），建议至少补 520px 档：收窄 `main` 内边距、卡片内距从 `28px 26px` 降到 `18px`、`10vh` 上边距改为 `clamp()`。
