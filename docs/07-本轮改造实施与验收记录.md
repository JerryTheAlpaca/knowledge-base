### 1.2 已实施修复（extractors/bilibili.py 1.1.0）

| 检查点（docs/05 §3.2） | 处理 |
| --- | --- |
| discover_tracks | 返回 `TrackDiscovery`（pairs/raw_count/need_login/view 轨数），空列表不再等同无字幕 |
| extract | player 的 `need_login_subtitle` 最优先；player 有轨无 URL → `unconfirmed`；多 P 时 view 视频级清单只作辅助（不证明 P2/P3 有/无字幕），证据不足标 `unconfirmed` |

## 2. 任务 B：统一账号、邀请码与设备授权

### 2.1 B1：知识库接入中心会话（已实现）

- `api/deps.py` 重构为 `Principal`：Bearer 设备 Token（带 device，无效 Bearer 直接 401、
  不回退 Cookie）与中心会话 Cookie（固定 `AUTH_SESSION_URL` 校验、读 `data.user.id`
  幂等映射本地用户）双通道；同步回执要求设备通道。
- `users.auth_subject`（唯一、可空）承载中心不可变 user.id；并发首登靠唯一约束收敛。
- `GET /v1/auth/me`：本地 user_id、中心用户名、auth_method、scopes、`is_admin`（来自中心 role）、
  `admin_url`；`GET /login` 302 到中心登录（return_to 只允许 KB 自身路径）。
- 共享退出 `POST /v1/auth/logout`：CSRF/Origin 校验后以固定 Origin 代理中心 logout；
  续期 Set-Cookie 按「名称/域/路径匹配」校验后转发浏览器；kb_csrf 双提交保持。
- 中心不可达 → 503（AUTH_UNAVAILABLE），不当 401、不建新用户、不无限跳登录。
- Web 收件箱改为统一登录探测；`/v1/web/session`、`/v1/pairing/exchange`、CLI `pairing-code`
  均已关闭（旧 kb_session 不再认证；旧桌面/手机 Bearer 设备未过期前仍可用）。
- 配置：`AUTH_SESSION_URL/AUTH_LOGIN_URL/AUTH_LOGOUT_URL/AUTH_COOKIE_NAME/AUTH_COOKIE_DOMAIN/
  AUTH_TIMEOUT_SECONDS/AUTH_FORWARD_ORIGIN`（compose 与 .env.example 已写；
  Cookie 名按 Atlas 线上实证取 `__Secure-jerry_session`、域 `jerrythealpaca.cn`——
  **部署时须与 Ledger 生产 SESSION_COOKIE_NAME/COOKIE_DOMAIN 核对**）。

### 2.2 B2：Ledger 注册/邀请码/管理员（已实现，提交 b3e2e5e）

- `users.role(user|admin)/invite_enabled/invite_quota` + `invitations` 表
  （只存 SHA-256 哈希 + 4 位尾号），Drizzle 迁移 `0003_add_roles_and_invitations`。
- `POST /api/auth/register`：Argon2 在写事务前；事务内「条件消费邀请码（未用/未撤销/未过期）
  + 建用户（role=user，禁止请求体传 role）+ 记录使用者 + 种子默认分类 + 会话同事务提交」；
  失败不消耗码；重复用户名/过期/撤销/错误码分别 409/400；同一码并发消费最多一个成功。
- `GET/POST /api/invitations`、`POST /api/invitations/{id}/revoke`：权限收口在
  `canCreateInvitation`（本期仅 admin；`invite_enabled+quota` 为扩展点，未开放 UI）。
  完整码（`JLI-` + 160bit base32）只在创建响应出现一次，可复制；撤销幂等。
- `/register`（保留 return_to）、`/admin/invitations` 管理页、登录页注册入口、
  设置页「邀请码管理（管理员）」入口；`GET /api/auth/session` 响应新增 `data.user.role`
  （原 id/username/expiresAt 结构不变，Atlas 兼容已核对）。
- README 补「账号与邀请码」章节（含管理员初始化 `scripts/set-role.ts`），并修正
  `jerrythelpaca.cn` → `jerrythealpaca.cn` 的历史拼写错误。

### 2.3 B3：插件浏览器授权（已实现）

- 服务端：`POST /v1/auth/device/start`（5 分钟 TTL，poll_secret 只存哈希）、
  `GET /v1/auth/device/info`、`POST /v1/auth/device/approve|cancel`（Cookie 通道 + CSRF/Origin，
  一条请求只能批准一次）、`POST /v1/auth/device/poll`（原子消费 + 签发 DESKTOP_SCOPES 设备 Token）、
  `POST /v1/devices/{id}/disconnect`；过期请求由保留期清理删除。
- 授权页 `/authorize`：显示设备名与当前账号，「登录此插件」后才产生授权；GET 不授权。
- 插件 0.2.0：设置页「登录账号/断开设备」；打开系统浏览器 → 轮询（按服务端间隔）→
  Token 入 SecretBridge；同账号重登获得新设备，旧设备凭据仍有效；「断开设备」撤销并清理本地，
  已导入笔记保留。同步状态（游标/回执）按 server+user+device 既有隔离逻辑工作。
- **未实测**：Obsidian 真机的首次登录/超时/重复授权/换账号行为（需要用户在真机过一遍）。

### 2.4 旧账号映射（机制已实现，绑定动作待执行）

- 机制：`bind-auth-subject` CLI（dry-run/--force、冲突不覆盖、幂等）、
  `list-users` 显示绑定状态；绑定只加身份映射，保留原 user_id 与凭据 AAD 绑定。
- **待用户执行**：在生产 KB 服务器上执行
  `python -m kbserver.cli list-users` →
  `python -m kbserver.cli bind-auth-subject --user <KB用户> --auth-user <中心user.id>`。
  中心 user.id 可通过登录 Ledger 后访问 `/api/auth/session` 查看（或由管理员在 Ledger 数据库核对）。
  未绑定前，中心账号首登会创建**空的新本地用户**（不会挂到旧账号数据上）——这正是防误合的设计。
- Ledger 管理员提升：`npx tsx scripts/set-role.ts --username <本人用户名> --role admin`（生产容器内执行）。
