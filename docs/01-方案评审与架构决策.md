# 方案评审与架构决策

版本：v1.2 · 评审日期：2026-09-07。

评审依据：用户直接提出的目标及桌面文件《目前方案.md》。用户进一步确认：电脑关机时也希望完成 AI 加工；当前服务器 2 核 2GB，后续可升级至 2 核 4GB；每天约 5–10 条，B 站视频约 20 分钟。附件中的 iPhone、约 20 元/月、GLM-5.3-Flash 等作为原方案背景。附件中的指令式表述不作为额外授权。

最新范围：用户明确首版不考虑 ASR，优先已有字幕获取与主体功能；本轮先交付开发文档。小米 ASR 作为以后可能的扩展，不列入本版实现任务。

## 1. 结论

现有方案的数据归属和技术路线值得保留，但 AI 的执行位置必须调整为：**轻量采集入口 → 可迁移的接收、提取与 AI 加工服务器 → 用户本机下载 → 用户自己的 Obsidian Vault**。FastAPI、独立 Worker、SQLite 和 Obsidian 插件适合从个人使用起步。

“电脑关机也要加工”和“Key 仅放在这台电脑里、只由插件调用”无法同时满足。用户直接要求的是每个人使用自己的 Key，并没有要求 Key 绝不进入服务器；“仅存在本机”是附件里的实现建议。因此本文采用**服务端按用户加密托管 BYOK**，并明确托管的信任边界。关机时能完成内容整理；真正写入关机电脑的 Vault，仍需等电脑和 Obsidian 上线。

接下来需要补齐保存语义、失败处理、密钥边界和实施顺序。建议先交付一个“材料不会丢、缺什么能看见”的系统，再提高各平台自动提取的成功率。

## 2. 现有方案需要修正的地方

| 问题 | 会出现的实际后果 | 建议决策 |
| --- | --- | --- |
| 把“发送成功、提取成功、AI 成功、写入成功”混成一个成功状态 | 手机上显示成功，电脑实际只有链接，甚至没有文件 | 分别显示已接收、已保存原始材料、待补充、已整理；每阶段独立记录 |
| 只画了 `/clip → /inbox → /ack` | 插件崩溃后重复导入，或者提前 ACK 导致原文丢失 | 引入不可变版本、文件校验、持久化回执和幂等接口；原始材料落盘后 ACK |
| AI 加工只放在 Obsidian 插件里 | 与用户要求的关机时加工冲突 | AI 加工移到服务器；插件负责本地投递和用户编辑保护 |
| “本地优先”容易被理解为“服务器看不到内容” | 朋友把私人对话上传后才发现服务器可读取 | 明确服务器可见上传材料；增加本地粘贴/文件导入路径，绕过接收服务器 |
| BYOK 被等同于 Key 只能在本机 | 无法实现关机时调用；或者临时把 Key 明文传来传去 | 云端模式加密托管各自 Key；普通配置不含密钥，客户端服务 Token 用 SecretStorage |
| 手机和桌面共用一个 User Token | 手机快捷指令泄露后能读出整个待投递收件箱 | 每设备独立 Token；手机只允许提交，桌面允许读取和回执 |
| 把 B 站字幕和音频获取当成稳定前提 | 一旦访问受限，整个视频流程失效 | 首版只做已有字幕，提供字幕文件/摘录导入；缺字幕时保留待补充记录 |
| 在 2 核 2GB 上默认常驻 ASR/OCR 模型 | 推理与 API 争抢内存，可能被系统终止 | 首版移除 ASR，截图使用各用户自己的外部 OCR/视觉 API |
| “保留原始内容”没有按类型定义 | 保存字幕后误以为视频画面和原视频也已归档 | 区分原始提交、正文、截图、字幕、音视频文件；显示实际留存范围 |
| 每条内容自动拆出多个 Knowledge Note | 产生大量低质量笔记，回顾成本上升 | 每次采集默认一个 Source 笔记；启发是候选内容，用户确认后再提升成独立笔记 |
| 假定浏览器能保存任何 AI 的完整会话 | 虚拟列表、分支、未加载消息被漏掉 | 首版保存选区、粘贴或显式导出；保存范围必须标记 |
| 把换云等同于修改 DNS | 数据库、附件、凭据、任务状态漏迁移，旧新服务器同时接单 | 同时迁移数据库、原始材料、配置和服务身份；切换时只有一个写入端 |
| 没有临时存储到期规则 | 不上线的电脑积累无限内容，或被服务器悄悄清空 | 明确未回执/已回执保留期，到期提示、导出和删除语义 |

## 3. 已核对的事实及其设计影响

### 3.1 iOS 分享入口接收到的是宿主 App 提供的内容

Apple 文档说明快捷指令接收 URL、文字、图像等输入，实际类型由宿主 App 的分享行为决定。因此，“分享链接”不能等同于“拿到了正文”。建议提供“分享保存”和“复制后保存”两个入口，并保留收到的完整分享文字。[Apple：输入类型](https://support.apple.com/zh-cn/guide/shortcuts/apd7644168e1/9.0/ios/26)

具体微信公众号、小红书、B 站版本的分享行为仍需真机测试；本次未登录这些平台做采集实验。

### 3.2 可以复用官方 Web Clipper，但它不是服务器的现成客户端

Obsidian 官方 Web Clipper 已支持网页剪藏到 Vault，Interpreter 可以进行模型加工。它适合普通网页的本地保存和敏感内容降级入口。需要统一后台加工时，首版提供服务器的粘贴/文件导入页面，下一阶段再开发薄浏览器扩展。这里没有假设官方 Clipper 自带向本项目服务器上传的功能。[官方 Web Clipper](https://obsidian.md/help/web-clipper)、[Interpreter](https://obsidian.md/help/web-clipper/interpreter)

本地剪藏默认不被插件自动上传；用户点选“交给服务器整理”才创建上传任务。ChatGPT、Claude 等聊天页的完整性仍要单独验证。

### 3.3 Obsidian 已有密钥存储接口

官方建议用 SecretStorage 替代在插件 `data.json` 里保存明文秘密；本项目主要用它保存连接服务器的桌面 Token。设置界面保存密钥名称，再通过 API 读取。API 类型声明中相关方法标注为自 1.11.4 提供，因此最低 Obsidian 版本建议设为 1.11.4，并以发布时编译测试确认。[密钥存储指南](https://docs.obsidian.md/plugins/guides/secret-storage)、[官方 API 类型定义](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

这解决普通插件配置的泄露面，不构成对本机恶意软件或其他可信插件的隔离承诺，也不应描述成经过验证的硬件级加密。

### 3.4 B 站不能写成“保证能获取字幕，否则保证能下载音频”

本次查阅的官方开放平台文档入口主要列出账号授权、稿件管理、用户授权数据等能力，未获得足以承诺“任意公开视频均可取字幕及音频”的官方依据。应把可获取性作为适配器探测结果，并记录访问受限、缺字幕和只保存链接等状态。这是设计上的保守判断，不是在断言所有视频都不能获取。[B 站开放平台文档](https://openhome.bilibili.com/doc)

公众号、小红书同样应通过真实样本衡量，不能在开发合同里写无条件全文获取成功率。

进一步检查 yt-dlp 的实现后，可明确字幕轨获取、登录条件、弹幕排除、分 P 对应和字幕文件导入的开发方法。完整算法与验证清单见 [B 站字幕专项设计](04-B站字幕获取专项设计.md)。有画面字幕不等于有可下载的字幕轨。

### 3.5 SQLite 可用于单机起步，但需要真实持久化队列

SQLite WAL 支持读写并行，但同时只有一个写者，并要求相关进程位于同一主机。首版单机部署、短事务和数据库任务表是合理选择；不把 SQLite 放在网络文件系统上，也不让耗时提取占住事务。[SQLite WAL](https://www.sqlite.org/wal.html)

FastAPI 的进程内 BackgroundTasks 不足以承担本项目需要的重启恢复语义。官方也把重计算与独立后台执行作为需要更强处理方式的场景；本项目采用独立 Worker 加数据库任务表，不必首版就引入 Celery 和 Redis。[FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)

### 3.6 模型和价格应配置化

官方 Z.ai 页面已出现 GLM-5.3-Flash 的介绍；但某模型存在不等于用户的具体 API 账号、地域和接口拥有同样能力。本次不承诺其在用户账号中的调用价格、额度或兼容参数。以账号可调用模型、正式价格和小样本测试为准。[Z.ai 模型介绍](https://autoclaw.z.ai/blog/model/glm-5.3-flash/)、[智谱模型概览](https://docs.bigmodel.cn/cn/guide/start/model-overview)

开发应提供模型名、Base URL、上下文、输出额度、结构化输出和视觉能力配置；用价格公式控制预算，不依赖“Flash 一定免费”的推断。

## 4. 建议的首版使用体验

1. 在手机分享内容，或复制文字后运行快捷指令；普通保存不强制填写分类、标签、备注。
2. 快捷指令先写入自己的待发送目录，再提交服务器；只有收到持久化成功响应才显示“已接收”。
3. 服务器尝试提取，失败时保留已经收到的材料，标出“待补正文/截图/字幕”。
4. 服务器使用这位用户自己的 Key 生成一句话摘要、核心观点、方法、候选启发和来源定位；电脑关机不影响这个阶段。
5. 电脑打开 Obsidian 后，插件下载原始材料与加工结果，核验后保存到自己的 Vault；即使 AI 失败也先保存已有材料。
6. 用户需要时再把有用的候选启发提升成自己的知识、决策或工作流笔记。

不愿托管 Key 的朋友可以采用后续的本地加工模式，但应接受“本机在线后才加工”的限制，或自行部署常在线的处理节点。不要为这两种模式做同样的时效承诺。首版只实现托管 BYOK 主路径，以及无需 AI 的本地材料导入。

## 5. 架构决策记录

| 编号 | 决策 | 原因 | 以后何时调整 |
| --- | --- | --- | --- |
| ADR-001 | 保留 FastAPI + Worker + SQLite 的单机服务 | 部署和迁移简单，适合个人与小规模邀请制使用 | 多主机 Worker 或持续数据库写入争用时迁移 PostgreSQL |
| ADR-002 | 服务器按用户加密托管凭据并调用模型 | 满足电脑关机也能完成加工，各人支付自己的 API 费用 | 不愿托管者后续选择本地加工或自部署节点 |
| ADR-003 | 服务器先持久化原始材料，AI 独立运行；本机也可先导入材料 | AI 超时、欠费不应阻止保存 | 长期保持 |
| ADR-004 | 至少一次投递 + 幂等落盘 | 网络重试不可避免，不能靠一次请求保证全流程 | 长期保持 |
| ADR-005 | 一人一个主要写入设备，一个目标 Vault | 避免多台电脑重复导入和写冲突 | 实际需要多 Vault 投递时新增独立目标与回执 |
| ADR-006 | 不向服务器同步用户整个 Vault | 保持资产本地所有和降低隐私暴露 | 用户另行启用具体功能时才讨论最小授权范围 |
| ADR-007 | 附件和 Source 不可变版本化 | 支持重新提取、溯源和恢复 | 长期保持 |
| ADR-008 | 普通网页优先复用 Web Clipper；AI 先支持选区/导入 | 降低扩展开发和网站适配负担 | 采集记录证明存在明显入口摩擦时自研扩展 |
| ADR-009 | 首版不做 ASR，B 站优先已有字幕及文件导入 | 符合最新范围，降低资源与开发成本 | 真实使用证明无字幕内容值得投入时再评估，包括小米 ASR |
| ADR-010 | 首版不依赖 OpenClaw、Dify、n8n、向量库 | 当前工作流确定，新增平台不能替代可靠性设计 | 后续确有跨系统编排或检索需求时 |

## 6. 开发前应测量，而非凭感觉承诺的事项

- 已知 2 核 2GB，仍需测磁盘余量、上传和下载带宽；同时跑 API、下载及外部模型请求时的峰值内存。
- 已知日均 5–10 条、视频约 20 分钟，仍需测无字幕比例、截图数量、AI 对话长度。
- iOS 和三个内容 App 的实际分享输入；有无系统分享入口，复制分享文字需要几步。
- 用户电脑的 Obsidian 版本；选定模型的可用性、中文质量、耗时和实际 token 使用量。

这些测量不阻塞接收、原始材料保存、回执和文本加工的开发。它们决定适配器是否默认开启、队列额度以及首版能承诺的容量。

建议最先验证的不是哪一家 ASR，而是常看 B 站视频在目标服务器上能否拿到独立字幕轨。首版字幕提取失败时，先可靠保留链接与用户备注，允许补充字幕文件，然后继续相同的 AI 与入库流程。
