# 多来源音频接入与 10 小时转写开发方案

日期：2026-09-10。状态：待实施开发文档，可直接交接给执行 Agent。

用户已确认现有 ASR 可用。本次在已有实现上扩展来源与上传入口，复用音频准备、识别、检查点、整理与投递流程，不重新建设 ASR。本文核对了当前本地代码；生产可用性沿用用户确认，本轮未重新连接服务器验证。

## 1. 本次目标与确定范围

1. 来源适配器负责从页面或直链解析可读取的音频 URL 及来源信息；统一交给 `prepare_audio` 和现有 ASR。
2. 会议录音等用户上传音频直接存入现有 object store，经本地文件输入进入同一 `prepare_audio`，后续转写完全共用。
3. B 站、普通网页音频、上传录音必须有不同的来源标签和图标；“机器转写”是处理方式，不是来源。
4. 所有音频入口统一支持 **10 小时，含恰好 10 小时，即 36,000 秒**。同步调整字节限制、磁盘预算和长任务恢复，不能只改时长配置。

保持当前部署的模型和空闲调度策略。当前本地 Compose 的模型为 `sense_voice`、空闲可用内存门槛为 384MiB（2026-09-19 按满载峰值实测校准，见 docs/11 §6.2）；不要用旧 docs/11 的初始默认值覆盖它们。整套知识库约 1GB、单 Worker、单识别进程的约束继续生效，延长音频不会增加识别并发或常驻模型数。

本次完成 B 站、通用音频直链、可静态解析的网页音频、文件上传四种输入。后续特殊网站只增加适配器。不引入浏览器录音、ASR 新模型、说话人分离、声纹、人名自动识别或直播常驻采集；会议录音首先提供转写与现有整理能力，不承诺分辨每位参会者。

## 3. 共用处理架构

```text
B 站页面 ── BilibiliAudioAdapter ─────┐
音频直链 ── DirectAudioAdapter ──────┤ → RemoteAudioInput
普通网页 ── WebAudioAdapter ─────────┘         │
                                              ▼
录音文件 → 上传完成 → object store → StoredAudioInput
                                              │
                  prepare_audio(input, limits, monitor)
                  ├─ 远程：受限 HTTP → 本次 attempt 临时文件 → FFmpeg
                  └─ 对象：已授权的本地对象路径 → FFmpeg
                                              │
                          相同 PreparedAudio / PCM 清单
                                              │
                  现有 asr_transcribe / 20 秒段 / 检查点
                                              │
                  来源版本 → 文字稿 → enrich → Bundle → Obsidian
```

建议模块分布：

- 新增 `audio/types.py`：输入、来源描述、准备结果及通用错误。
- 新增 `audio/prepare.py`：迁移现有准备实现，支持远程流与对象文件两种输入，复用同一套解码、切段、摘要、时长和取消逻辑。
- 新增 `extractors/audio_sources.py`：简单顺序分发和直链/网页解析；复用现有 HTML 解析依赖。没有必要先建可动态安装的插件注册系统。
- 保留 `extractors/bilibili_audio.py` 的 B 站解析函数，作为对应适配器。
- 保留 `workers/asr.py` 的主任务执行、识别、合并、发布和恢复。修改输入与来源传播，不复制成 `web_asr.py`、`upload_asr.py` 三套 Worker。

最小接口建议如下，名称可顺应现有代码，但语义必须一致：

```python
resolve_audio_source(capture_context, selection=None) -> ResolvedAudioSource
prepare_audio(audio_input, attempt_dir, *, limits, monitor) -> PreparedAudio
```

`ResolvedAudioSource` 分为两部分：

| 部分 | 必要字段 | 生命周期 |
| --- | --- | --- |
| `source` | platform、media_kind、adapter_id/version、original_url、canonical_url、title、author、source_locator、duration_hint | 来源事实可持久化，冻结在本次 run 对应输入中 |
| `input` | `kind=remote` 的 URL/备选地址/受控请求策略，或 `kind=object` 的已授权原件引用 | URL/headers 只用于本次获取；对象引用持久有效 |

远程流 ID 改成可选字符串，不要求非 B 站站点提供 cid、整数 stream_id 或 bandwidth。`expected_duration` 允许为空；未知时长必须依实际解码采样数执行 10 小时上限。对象输入只接受服务端从数据库解析出的引用；客户端不能传 storage_key、本机路径或任意请求 headers。

来源描述不包含模型/转写结果。转写清单保留 `input_fingerprint`：B 站由 BV/cid/音轨等稳定标识组成，网页由页面与选中媒体标识组成，上传由原件 SHA-256 组成；再绑定 user/item/source_revision。带时效签名的 URL 不用作永久身份或幂等键。

## 4. 来源适配器职责与网页边界

### 4.1 B 站

保留现有 BV/分 P/cid、字幕优先、登录态、WBI/buvid3、音轨选择和防串号规则。只将其输出包装为通用输入。不改变已经可用的提取路径，不重新选模型。

适配器产生受限请求策略：B 站 API 使用当前用户自己的凭据，媒体 CDN 使用已验证的 UA/Referer。通用准备层不得默认给所有站点附 B 站 Referer，也不能把 B 站 Cookie 传播到普通网页域名。

### 4.2 音频直链

接受 HTTP(S) 可有限读取的音频资源。URL 后缀仅作提示，以响应 MIME、格式探测与实际解码确认；支持常见 MP3、M4A/AAC、WAV、FLAC、OGG/Opus。没有后缀的签名 URL 也应能够解析。

`original_url` 保留采集定位，经过重定向只更新最终解析地址，不把 CDN 主机当作者/内容平台。请求均走现有受限 HTTP 工具，大小、重定向、DNS/IP、超时和凭据边界继续生效。失效地址记录 network/access 错误，不报“无字幕”。

### 4.3 普通网页

首轮解析静态 HTML 中的 `<audio src>`、`<audio><source>`、`og:audio`、JSON-LD `AudioObject.contentUrl` 等明确音频信息；相对地址用页面最终 URL 解析。候选去重后，只有一个逻辑音频则可直接采用；同一 audio 元素下的不同格式是同一音频的候选编码，不误当多个节目。

同页有多条独立音频时返回选择列表：标题、预计时长（可为空）、格式及服务端候选 ID。用户选一次后才转写，不能默认合并所有播放器或抓广告音频。服务端保存候选的稳定定位；到实际准备时重新解析并核对选择，不信任客户端直接提交新的媒体 URL。

常规网页采集继续提取正文，不因页面恰好有音频就自动改变原工作流。用户在采集模式选择“音频”，或在详情点击“转写页面音频”，才调用音频适配器。页面正文和转写是两种材料，保留各自范围，不把提取标题/简介当转写原文。

无静态可取音频、需要动态脚本或特殊平台解析时返回 `audio_source_unsupported`，允许后续增加该站适配器。首轮不承诺支持任意网页、HLS/DASH 播放清单、DRM 或无限直播；B 站既有 DASH 独立音频文件路径保留。不要把 m3u8 当 MP3 直接喂给只读 pipe 的解码器。

## 5. 来源标签与图标：必须独立于 ASR

采用以下映射，服务端返回统一展示字段，Web 与插件不得分别用 URL 正则猜标签：

| 来源 | 持久 platform | media_kind | 派生 source_type | 展示标签 | 图标 |
| --- | --- | --- | --- | --- | --- |
| B 站字幕或视频音频转写 | `bilibili` | `video` | `bilibili` | B 站 | 📺 |
| 普通网页解析的音频、普通音频直链 | `web` | `audio` | `web_audio` | 网页音频 | 🎧 |
| 用户上传录音，包括会议录音 | `audio_upload` | `audio` | `audio_upload` | 上传录音 | 🎙️ |
| 普通网页正文 | `web` | `text` | `web` | 网页 | 🌐 |

如产品已有 B 站专用 SVG，保留它；其他来源必须使用不同图形，不能全部回落到同一个播放图标。标签文字同时显示，不能只靠表情或颜色区分。ASR 完成后额外显示“机器转写”，不替换来源标签。

实现规则：

1. `platform/media_kind/source_locator` 写入 SourceRevision，发布、重新提取、enrich 与 Bundle 都继承它们；去掉 ASR 发布中的 `platform=bilibili` 和固定 `bilibili_asr`。`extractor` 表示实际来源适配器；模型仍位于 `asr` 元数据。
2. `source_hint=web_inbox` 是采集渠道，不是平台。增加/使用 `capture_channel` 保存渠道，最终来源由服务端输入/适配器确认；不得信任客户端 hint 把上传录音伪装成 B 站。
3. 网页的音频托管于 CDN，仍是网页音频。上传的文件名包含 BV 号也仍是上传录音。B 站字幕文件补充到已有 B 站条目时不改变该条来源。
4. 新建上传音频条目一律 `audio_upload`；给已有条目补充音频只增加材料来源 `uploaded_audio`，保留条目的原平台，详情明确“来源：B 站；本次转写材料：用户上传”，不能悄悄改整个条目的来源。
5. 会议用途可用现有用户标签添加“会议”，不强制所有上传音频都是会议，不增加必填会议成员/时间字段。
6. 列表、详情、搜索过滤、来源统计、转写状态、Bundle `source`、Obsidian frontmatter/正文统一更新。插件现有 `kb_source_type` 按派生 source_type 写入，并保留 `kb_source_platform` 及 media_kind；已有笔记通过原有受控生成区更新，不覆盖用户修改。

`source_type/label/icon_key` 是由 platform/media_kind 派生的展示字段，不另建一张来源标签表。旧记录缺 media_kind 时，B 站按 video，普通已提取网页按 text；无法确认是否音频的旧 web 记录保持网页，不根据 `asr` 字样或文件名强行回填。

## 6. 录音上传：原件入 object store，再走同一套准备

### 6.1 持久化与路由

上传完毕后复用现有 `Upload` 完成结果：upload_id、SHA-256、bytes、filename、mime。采集使用已有 `upload_ids`，新增可选 `primary_audio_upload_id` 明确作为本次转写主体的一个文件；第一版一条音频任务绑定一个主体录音，多文件分别建条目，不自行拼接。

新建音频条目使用 `input_kind=file`、`processing_intent=transcribe_audio`；Web 普通附件上传继续沿用旧行为。服务器原子关联音频原件、Capture、SourceRevision 后排入已有 `asr_prepare`。上传录音和用户主动提交音频链接即为本次转写请求，不要求再去打开 B 站的 `auto_when_no_track` 开关；部署 ASR 关闭时照常保留原件并显示等待启用。

本地对象输入由 `ObjectStore.object_path()` 解析并校验权限/引用。FFmpeg 直接读取这份已落盘的对象，不再通过自身 HTTP 下载接口绕一圈，也不把整文件读成 bytes。远程输入也先整条落到本次 attempt 的临时文件再解码，两个分支因此同样可 seek、同样兼容 moov 在尾部的常见 M4A；解不了的容器仍如实报不支持，不再把「不可 seek」当格式不支持。

两种输入只在“提供音频字节/本地可 seek 路径”处不同，输出 `PreparedAudio` 完全一致。metadata 的 `acquisition` 分别为 `player_audio_stream`、`web_audio_stream`、`uploaded_audio`，按真实来源赋值。

### 6.2 长录音的大文件上传

不能仅把现有 multipart 上限提高后就称作完成。FastAPI 的 UploadFile 会使用可溢写磁盘的暂存文件；上传后再经 ObjectStore 写入时可能同时占两份原件大小。应明确临时盘位置和处理并发。[FastAPI 文件上传说明](https://fastapi.tiangolo.com/tutorial/request-files/)。

为避免几小时上传中断后重传整个文件，本轮音频入口增加最小串行分块续传，复用已有对象落盘/摘要逻辑，不建设通用上传服务：

- `POST /v1/audio-uploads`：声明 filename、总 bytes、mime，创建当前用户的会话；返回 session_id、固定块大小（建议 16MiB）、当前 offset、过期时间。先检查音频额度和可用磁盘。
- `GET /v1/audio-uploads/{id}`：返回当前可恢复 offset/state；仅本人可见。
- `PUT /v1/audio-uploads/{id}/chunks`：原始二进制请求体，包含 offset、块 SHA-256；一次一个块。服务端按块流式校验写入受控 staging 文件，原子推进已确认 offset。同一 offset 同一摘要重传幂等，不同摘要冲突，不接受跳段/重叠覆盖已确认内容。
- `POST /v1/audio-uploads/{id}/complete`：总长度一致后分块计算整文件 SHA-256，使用 ObjectStore 新增的“已有同卷 staging 文件原子收纳”方法完成对象化，返回标准 UploadResult。完成操作幂等；尚未完成的会话不可被 Capture 引用。
- `DELETE /v1/audio-uploads/{id}`：取消未完成会话，释放临时占用；已完成对象按引用规则处理，不能直接删除共享内容对象。

每块写盘与会话 offset 更新之间发生崩溃时，恢复按最后确认 offset 校验并截去未提交尾部，再重传该块；不对整个上传持有数据库事务。完成阶段计算摘要也在事务外执行；进程中断可重试完成，不能生成两个 Upload 或丢失已有对象。落盘文件名不使用用户路径。会话 24 小时无活动过期，持续上传会续期；临时输入不是 object store 中的“已完成原件”。

HTTP 分块是上传传输机制，与 ASR 的 20 秒音频片段无关。前端显示上传进度和可重试状态，上传未完成不能显示“已接收待转写”。反向代理只需允许单块及少量头部余量；核对路由的请求大小/空闲超时，不能仅调整应用内部字节数。无需浏览器 Buffer 读取整个文件。

### 6.3 原件保留与自动投递

用户上传的是原始材料，不能像远程流生成的临时 PCM 一样在 ASR 成功后删除。新增音频原件引用记录 `AudioAsset`（或语义相同的字段/表）：user_id、item_id、source_revision、upload_id、stored_file_id、sha256、bytes、retention 状态。注册原件时复用已有对象，不重复复制。

原件默认随有效条目保留；用户删除条目/原件时才按现有删除流程解除引用和清理。ASR 取消、模型报错、空间等待、文字稿已投递，都不解除原件引用。未被采集引用的已完成上传仍采用现有 24 小时策略。

**大录音默认不随 Bundle 自动同步到 Vault**。原件登记为独立 `original_audio` 角色并提供鉴权流式下载，Bundle 自动投递文字稿、片段与模型原始输出，来源元数据注明原件在服务器保留。用户可在详情下载原件；本轮不要求插件自动下载 GB 级文件。`original_media_retained=true` 只用于实际留存的上传原件，远程未留原件为 false；不要让 `audio_retained` 与真实存储状态矛盾。

必须同步改 `retention_sweep`：引用集取所有存续 Bundle + AudioAsset + 未完成上传会话/已完成待引用上传 + 需保留的运行任务对象。内容寻址对象在全局无引用后才可删除，不能因某用户删除同内容条目而删掉另一用户的对象。现有 `one_or_none()` 对同 storage_key 多条 StoredFile 的判断应改为存在性查询。

新增原件下载接口建议 `GET /v1/items/{id}/audio-original`，先校验用户/条目/原件引用，再以文件流响应，不调用返回整对象 bytes 的读取方法。采用现有认证与删除状态，响应不暴露服务器路径。原件不进 Bundle 的设计和留存行为须在 UI、Manifest 与文档一致展示。

## 7. 10 小时限制与资源预算

### 7.1 配置调整

| 配置/约束 | 新值或处理 |
| --- | --- |
| `ASR_MAX_DURATION_SECONDS` | **36000**；API/Worker 使用一致配置，修改 Settings 定义与 get_settings 初始化两处 |
| `ASR_MAX_INPUT_BYTES` | 建议 **8GiB = 8589934592 字节**，所有音频准备输入上限 |
| 新增 `MAX_AUDIO_UPLOAD_BYTES` | 同为 8GiB，单个主体音频；普通附件原有限额不放宽 |
| 普通 `MAX_SINGLE_FILE_BYTES/MAX_CAPTURE_TOTAL_BYTES` | 保留原值；音频主体按独立额度，其他附件仍按普通额度计总和 |
| `ASR_CHUNK_SECONDS` | 保持 20；10 小时约 1800 段，不随总时长增大片段 |
| `ASR_CHUNK_TIMEOUT_SECONDS` | 保持单段超时；不得换成整条音频只能执行 15 分钟 |
| CPU/内存/模型/空闲门槛 | 继承当前已验证部署，不因 10h 自动增加并发或恢复旧模型配置 |

8GiB 为本方案给出的实现默认，可配置；**10 小时与 8GiB 同时限制**。不保证任意无损/高采样率录音都能上传；UI 同时显示“最长 10 小时，单文件最大 8GiB”。10 小时 48kHz、双声道、16-bit PCM 数据约 6.912GB，8GiB 可覆盖该常见规格；更高规格超字节限额需先转成压缩音频。

时长约束必须三层落实：已知可信 metadata 可提前拒绝；解码过程中按实际输出采样数监测；最终提交再次校验。没有 duration 的输入不能无限解码。可让解码最多多产生少量探测帧以发现超限，超限即终止并报告 `audio_too_long`，**不能截掉 10 小时之后的内容再宣称完整转写**。恰好 36,000 秒按采样精度接收，不用四舍五入成分钟做判断。

当前准备实现主要检查 `stream.duration_s`，最终用 expected_duration 对齐；本次补实际总时长硬限制。保持“无法确认完整性”与“已完成全文”区分。上游声明时长误差与 10 小时硬上限分开判断，不能利用百分比容差放行超长音频。

### 7.2 磁盘和运行时间

16kHz、mono、s16 的 10 小时 PCM 为 **1,152,000,000 字节，约 1.073GiB**，外加 WAV 头、清单和结果。采用磁盘片段，不读成整段 ndarray，不依赖 tmpfs。内存上限保持现有配置，模型一次只读取当前 20 秒及少量上下文。

上传原件可能达 8GiB；使用 staging 原子收纳可避免完整复制。按“原件/上传预留 + 本次约 1.1GiB PCM + 结果与 1GiB 余量”检查磁盘，并扣除其他已预留上传会话。原件最大时，工作盘可用空间通常需 **至少约 11GiB**；这是单条新增占用，不含现有库。若实现仍保留两份完整上传副本，要按近 19GiB 预算，不能沿用 11GiB。

有限字节输入并不保证解码后足够小，未知时长先按最坏 10h PCM 预留；准备期间继续检查磁盘。空间不足使用 `paused/disk_space`，保留原件和已经提交的转写结果，释放未提交 attempt，再等待清理出空间；不删除其他条目以腾空间。

一台机器同一时间只保留一个正在推进的 ASR PCM 工作集，普通任务仍优先。准备重试必须清理自己失效的 attempt，不能每次暂停额外留下 1GiB；当前主地址读到一半失败后换备地址时，需**重新启动 FFmpeg 和新的 attempt**，禁止把两次流串进同一个 stdin。

只限制网络无进展的读取时间，不把 `30s read timeout` 误当整条音频期限；若设置总准备时限，应按实际速率/业务允许等待程度制定，并可续期。准备读流/本地解码、等待子进程收尾、合并发布均需持续响应取消/续租/资源让出，不能只依赖收到网络字节时的回调。

### 7.3 长任务恢复和后续整理

已有 manifest 与逐段检查点继续复用。20 秒段的 1800 个结果顺序合并，避免把 PCM 或不必要的原始调试数组一次性加载。合并/生成文件在事务外进行，最后短事务复核租约、输入版本和删除状态后发布。

排队/忙碌暂停可能超过 24 小时，不能由 `ASR_TMP_TTL_HOURS=24` 删除可恢复任务的 PCM/已提交结果。清理依据 run 生命周期与是否可恢复，活跃/等待空闲任务保持引用；终态未引用的 attempt 才按 TTL 清理。超过现有 Job 最大生命周期时必须显示任务超时并保留原件/文字稿，不悄悄清空进度；长音频试运行要验证寿命设置是否覆盖真实等待。

当前 enrich 已有分块能力，继续复用，检查 10h 文字稿对应的分块摘要合并是否仍落在上下文内；必要时逐层合并并保留 segment_id 证据链。不把几十万字一次性塞进单次模型请求。LLM 失败只影响整理，转写原稿仍可投递，重试 enrich 不重新运行 ASR；沿用现有 unknown_outcome 与用户自己的 Key。

UI 时间采用 `HH:MM:SS`，SRT 小时位及原音频绝对定位正确；片段分页/分批渲染，进度只按已提交音频秒数计算。不得因总段数较大把浏览器、插件或 API 一次性装满音频数据。

## 8. API 与数据迁移

保持已有 ASR 四个接口路径和 run 幂等语义，移除“只有 B 站条目支持”限制。触发依据可用的 audio input；状态与取消依据已有 run 和条目所有权，不要求此刻来源网址仍可访问。

在现有 Capture Schema 增加可选字段 `processing_intent=default|transcribe_audio`、`primary_audio_upload_id`。旧请求默认为 default，原 B 站 `auto_when_no_track` 含义不变。显式音频请求经 extract 路由适配器/上传主体后进入 asr_prepare，不误当用户备注是完整原文。

页面多候选时，新增 `GET /v1/items/{id}/audio-sources`，首次解析由 Worker 执行并缓存非秘密候选；接口返回 pending/ready/unsupported 与候选 ID。扩展现有 `POST /v1/items/{id}/asr` 的可选 `audio_candidate_id` 选择音频；选择不同媒体产生新来源输入版本，不能继续旧的部分结果。

Item/Manifest 新增 `media_kind`、派生 `source_type`、展示 label/icon_key 和可选音频原件状态；保留 platform 字段兼容旧客户端。状态响应增加可选总音频秒数、来源类型、可重试/暂停原因，前端按 `asr_supported` 等能力字段显示按钮，去掉 B 站 URL 正则作为唯一入口。

新增迁移：音频上传会话、AudioAsset，以及需要持久绑定的 `AsrRun.input_json/input_fingerprint`。后者只存来源稳定定位或对象引用，不存敏感 headers/签名 URL。旧 B 站 run 缺输入字段时从原 SourceRevision/locator 读取，兼容旧 manifest schema；本次写新 schema，保留旧读取路径直到旧任务结束。迁移不得重置 `next_chunk_index`、覆盖不可变来源版本或批量重新识别历史条目。

新输入选择/上传主体改变时递增输入来源版本，使旧 run 按原有失效检查取消。单纯更新展示标签不要触发全量 ASR。来源读取错误统一成通用 AudioSourceError/AudioPrepareError，原 B 站错误在适配器边界转换，避免通用层继续依赖 BilibiliAudioError。

## 9. 实施顺序和验收清单

### 实施顺序

1. 抽出通用输入与 `prepare_audio`，接回现有 B 站，先验证同样输入结果和恢复语义一致。
2. 补来源传播与所有标签/图标映射；修改 run 输入冻结、发布元数据和 API 能力判断。
3. 接通直链、静态网页候选解析与选择，复用现有 ASR。
4. 实现录音上传、对象原件引用、文件 prepare 分支、上传进度与下载；同步清理和 Bundle 过滤。
5. 将 10h、音频字节额度、磁盘/超限控制、长任务续租与分页一起完成；补迁移、OpenAPI、部署说明和相关文档。

### 必须覆盖的验证

| 场景 | 验收要求 |
| --- | --- |
| 同一段音频来自直链与上传 | 共用 PreparedAudio schema 和同一识别执行函数；文本/时间在允许的解码差异内一致，来源标签不同 |
| B 站 P2、字幕优先与原自动开关 | 无回归，来源仍为 B 站；本轮不改变现有可用模型 |
| 静态网页、相对 URL、签名直链、多个音频 | 正确解析或提供选择；不会合并多个节目/把 CDN 判成 B 站 |
| 网页仅正文、上传普通附件 | 沿用旧流程，不自动进入 ASR |
| 上传录音/网页音频/B 站 | 列表、详情、过滤、来源统计、Bundle、Obsidian 图标/标签一致且三者不同 |
| 35999 秒、36000 秒、36001 秒，含缺失/虚假 duration | 前两者可进入处理，超限明确失败；不截断成成功；真实采样数验证 |
| 超 128MiB 远程音频、超 100MiB 上传 | 音频新额度生效，Capture 也接受；普通附件额度不被放宽 |
| 上传断网、重复块、偏移冲突、完成时崩溃 | 续传和完成幂等，没有尾部损坏、双重对象登记或整个文件内存读取 |
| 准备中断/备地址切换/忙碌暂停 | 新 attempt/解码器，不拼接两次字节流；取消无孤儿进程 |
| 超过 24h 等待、Worker 重启、旧 run 跨升级 | 清单与已提交段可恢复，未被 TTL 清掉或因新 schema 被强制从零开始 |
| 录音已转写、模型失败、取消、Bundle 到期 | 上传原件继续受引用保护，远程临时 PCM 可清理 |
| 同内容两用户/两条目、删除其中一条 | 对象不被误删，凭据/原件下载不能跨用户访问 |
| 输入被替换、条目删除、旧租约提交 | 旧结果不能覆盖新材料；用户笔记修改受保护 |
| 10h 后续整理失败 | 已完成转写可访问/投递，整理重试不重新 ASR，不把部分摘要当全篇 |

在受控环境构造 10h 音频验证上传/解码/1800 段清单、时长边界、磁盘和生命周期；可用固定引擎输出测调度恢复，但必须标明 mock。另用真实模型识别真实语音片段和至少一份较长录音，分别报告解析、准备、识别、整理的验证结果。10h 全程真实识别未跑就明确写未跑，不能仅凭短片段测试宣称 10h 全链路实测通过。

按风险集中运行 ASR、上传、对象清理、来源展示相关测试，必要的服务端检查和 Web/插件构建。文档本轮不跑业务测试。不要因为现有 ASR 已稳定而重复全量模型选型，也不要把新增多来源逻辑的 mock 测试计为网站真实成功率。
