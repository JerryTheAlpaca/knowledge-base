# 音视频原件转写后清理——实施记录（2026-10-05）

## 1. 要解决的问题

服务器根盘 50G 反复被顶满。归因不是垃圾文件，而是 docs/13 §6.3 的旧口径：用户上传的音视频
原件一旦登记 `AudioAsset`，就随有效条目长期保留，只有删除条目才释放——生产上那条 1.91G 的
`video/mp4` 就是这么留下的。文字稿、片段和模型输出在发布时已经是各自的对象，转写完成后原件
不再被任何后续加工需要。

用户本轮定的口径：**转写成功立刻删**，上传入口**加磁盘水位检查但不下调 8GiB 单文件上限**。

## 2. 改了什么

| 位置 | 改动 |
| --- | --- |
| `domain/pipeline.py` | `release_original_media` 解除原件引用（`AudioAsset→released`、删原件的 `StoredFile` 登记、`Upload→expired`）并返回候选 key；`reclaim_original_media` 逐 key 复查 `StoredFile`/未过期 `Upload`/`ShareArtifact` 引用后才删物理对象。`original_media_file_ids` + `without_original_media` 把原件从 Bundle 文件列表中剔除。采集首版清单不再 append 原件登记。 |
| `workers/publish.py`、`workers/enrich.py` | `bundle_files` 与 `_base_bundle_files` 过滤原件登记，后续每个版本都不列大文件；普通小附件照常投递。 |
| `workers/asr.py` | `_finish_if_complete` 在发布文字稿的同一事务里解除引用，提交成功后再回收对象；发布元数据如实写 `original_media_retained=false`、`asr.audio_retained=false`；`asr/original_audio.json` 改为「原件只用于本次转写，已清理」的说明，不再留下载入口。转写失败、取消、结果作废的分支不动，原件保留。 |
| `workers/worker.py` | 新增 `release_finished_originals`，挂在 `retention_sweep` 最前面：释放「当前来源版本已有转写结果但原件仍在」的历史条目，并按 `AudioAsset.sha256` 兜回收崩溃残留的对象。判据不能比 `AsrRun.source_revision == Item.source_revision`——ASR 发布会新起一版来源，run 记的是上一版，生产 27 条这样一条都匹配不上（`a305d22` 首轮实测释放 0）。`_unreceived_bundle_listing_media` + `_prune_media_entry`：最新一版清单从没被取走过时，先摘掉其中的原件条目再释放。 |
| `api/routes_items.py` | `audio_original_retained` 改为按 `AudioAsset` 实时状态判定（原先读冻结的采集元数据，释放后会说谎）；新增 `audio_original_released`。 |
| `api/routes_audio_uploads.py` | 会话创建时扣除其他仍在写入会话已声明的剩余字节；每个块写入前复查剩余空间，不足返回 507 且会话保持可续传。8GiB 上限不变。原件已清理时 `audio-original` 返回 404 并说明原因。 |
| `api/routes_sync.py` | `GET /items/{id}/bundles/{rev}/files/{file_id}` 改为 `FileResponse` 文件流，不再 `read_object` 整份进内存。 |
| `extractors/audio_sources.py` | 无可用原件的说明改为「原件在转写完成后会从服务器清理，重新转写请重新上传」。 |
| `web_static/js/item-detail.js` | 原件已清理时，更多操作菜单显示禁用的「录音/视频原件已在转写完成后清理」，不再给死链。 |
| 文档 | docs/13 §6.3 改口径、docs/14 相应条目与磁盘控制、docs/02 §5.2 与 §14.3、docs/07 §5.6、README。 |

## 3. 保留下来的边界

- **转写不成功就不删**：失败、取消、停在等待启用/等待空间的条目原件照旧保留，材料留着重试。
- **跨用户不串**：内容寻址对象可被另一用户的同内容上传持有，复查引用后仍无人引用才删物理文件。
- **不把客户端晾在原地**：历史条目的清单里可能仍列着原件（旧代码会写进 `files`）。那一版没被
  Obsidian 回执、也没在网页下载过原文时，清理任务先把原件条目从这份没人下载过的清单里摘掉
  （版本号不变，`manifest_key`/`manifest_sha256` 一起更新，旧那份清单随之回收）再释放原件；
  已经取走过的那版不动。新条目的清单从一开始就不含原件，用不上这条。
- **先落库再删文件**：引用解除与文字稿发布同事务提交，物理回收在提交之后；中途崩溃只会留下
  待回收的对象，由清理任务按 `sha256` 复查后补删，不会出现「转写没保存而原件已删」。

## 5. 生产磁盘归因与实测（2026-10-05）

- 部署前 `df -h /`：50G 用 42G（89%，部署的 DISK GUARD 在 90% 触发过一轮 prune）。数据卷
  `deploy_data` = **23G**（2026-09-28 量的是 2.5G）：`objects` 19G、`tmp` 4.3G、`db` 18M，
  `deletions` 空的（4K）。
- `objects` 里 6 个大文件占掉绝大部分：4.59G / 4.26G / 4.02G / 2.38G / 1.91G / 1.68G，全是
  用户上传的 `video/mp4`（古法悬灸系列、手机屏幕录制）。库里 `audio_assets` 27 条 `retained`
  合计 **13.76 GiB**；`files` 表 `original_submission` 161 行 13.85 GiB。
- 这 5 条最大的视频详情都写着「转写完成，共 149/145/103/125/66 段」——文字稿早就发布了、原件
  却还留着，正是本轮要修的形态。另 10 条 mp3 停在 `waiting_key`，合计 0.22 GiB。
- 三轮部署实测：
  - `a305d22`：`originals_released: 0`——历史判据写成了比较 `AsrRun.source_revision` 与
    `Item.source_revision`，而 ASR 发布会新起一版来源、run 记的是上一版，27 条一条都不匹配。
  - `16c6251`（判据改为看当前来源版本的转写结果）：释放 19 条、回收约 2.16 GiB，
    `objects` 19G→17G，`df` 89%→86%；但 8 条停在 `awaiting_sync`，含 4 条最大的视频 11.48 GiB。
  - `2705453`（等待门槛只看最新存续版本）后仍然 8 条不动：那一版清单从没被任何设备取走过，
    而插件每个条目只取最新一版，捕获首版永远不会回执，「等客户端取走」等于永远等。
  - `66229ff`（先摘掉那份没人下载过的清单里的原件条目再释放）：**释放 8 条、回收
    `12,436,375,126` 字节（约 11.58 GiB），8 份清单被摘改**。`objects` 17G→4.5G，
    `df` 从 87% 降到 **64%**，可用从 6.2G 回到 **18G**。库里 27 条原件全部 `released`，
    `bundle_revisions` 仍 471 行未少，`/health/ready` 200，worker 日志无异常。
- `tmp/audio-uploads/up-c392b9ee….part` 单文件 **4.3G**（10-04 起）本轮没动：它对应一条还在
  `receiving` 的上传会话（声明 5.44 GiB、已写 4.22 GiB，`expires_at` = UTC 10-05 08:52，即本地
  16:52）。会话按既有的 24 小时无活动过期机制走，过期后由 `cleanup_audio_upload_sessions`
  调 `discard_staging` 删除，最迟下一轮 6 小时清理生效——不是新泄漏，也不该绕过会话状态手删。
