## 1. 需求与交付边界

### 1.1 用户已明确的要求

1. 用户反馈 B 站视频字幕现在都抓不到，当前只有微信公众号能成功整理。应定位实际失败原因，修复“已有字幕 → 原始字幕留存 → AI 整理 → Obsidian 入库”链路。
2. 取消日常使用中的手动配对码，使用注册、登录；知识库与 `jerrythealpaca.cn` 下的 Ledger、Atlas 共用现有登录界面和登录态。当前统一登录由 Ledger 提供。
3. 新用户注册必须填写邀请码。用户本人是管理员；**目前没有管理员界面，需要在其账号操作界面增加入口及管理员页面**，页面上有“生成邀请码”按钮。
4. 未来可能允许普通用户生成邀请码，本轮预留创建者、权限和额度扩展点；本期仅管理员可生成。
5. 不再统计模型 API 用量、价格和估算费用。移除相关设置、页面、接口与执行依赖，供应商账单由用户在供应商平台查看。

### 1.2 本轮实现选择

- 注册只建在现有中心认证服务中，知识库不另建密码库或第二个登录表单。可先完成共享登录，再补邀请码注册，但完整需求交付须包含注册闭环。
- 将“取消统计”落实为同时取消知识库的金额预算阻塞和计费对账；不能留着 `waiting_budget` 卡住任务。**Ledger 自身的记账、月预算、财务统计完全不属于删除范围。**
- B 站仍使用每个用户自己的可选登录凭据，不用管理员的 B 站账号代替其他用户。网站统一登录、B 站 SESSDATA、模型 API Key 是三套独立凭据。
- 保留已有字幕上传、粘贴正文的降级；不增加 ASR、音频下载、原视频归档或常驻浏览器。
- 保留原始材料、用户隔离、任务恢复、同步回执、笔记编辑保护。去掉计费不意味着去掉模型调用的执行状态记录。
- 默认由一个 Agent 按阶段完成；本文不要求自动创建其他任务或并行 Agent。

### 1.3 本次检查的限制

本次只编写交接文档，没有修改业务代码，没有用用户实际失败视频、SESSDATA 或生产服务器重新跑字幕提取，也没有验证线上共享 Cookie 的实际配置。旧 `docs/04` 的本地/云端实测记录是历史资料，不代表本次确认，更不能由两个历史成功样本推出现在一定可用。

## 3. 任务 A：修复 B 站字幕链路

### 3.1 先复现，不把已有功能重新开发一遍

先选用户真实失败的 3–5 条视频，至少包含一条在用户正常登录浏览器中确实存在可开关字幕的样本；覆盖一个分 P 链接或短链。检查部署版本、API 与 Worker 是否都更新，主密钥是否同源、凭据是否属于该条目的知识库用户。

每个样本顺序检查：

1. 分享文字/短链解析后的 BV/aid、显式 p、最终 cid。
2. view / player 请求的 HTTP 状态、平台 code、登录提示字段、轨道总数与有下载地址的轨道数。
3. 当前凭据是否配置、是否被 Worker 实际使用、能否由平台响应确认有效；“已加密保存”不等于“可用”。
4. 字幕地址下载的 HTTP 状态、MIME、JSON 结构与有效片段数。
5. 来源文件落盘、来源版本发布、AI 排队、Bundle 发布与客户端同步分别是否成功。

同一条样本尽量在本机与目标服务器各验证一次，区分平台接口变化、登录态问题和服务器网络差异。仅在本机成功不能关闭线上问题。

建议把脱敏记录写进本仓库的新验收记录文件，例如 `docs/06-本轮改造验收记录.md`：日期、提交号、环境、样本代号、p/cid、阶段、状态码、是否使用登录态、轨道/片段数、实际产物。真实凭据、完整请求头、带签名字幕 URL、私人原文不得放入记录。

### 3.2 从代码已发现的具体检查点

这些是静态检查结果或排查方向，**不是已证明的线上总根因**。

| 位置 | 当前行为 | 修改要求 |
| --- | --- | --- |

### 3.3 目标接口和界面行为

复用 `GET/PUT/DELETE /v1/bilibili-session`。建议补充“检测登录态”操作，例如新增 `POST /v1/bilibili-session/test`；路径为建议，尚未实现。

- 状态至少能区分：未配置、已保存但未验证、最近验证有效、已失效/被拒、检测受网络影响。成功保存不能显示“字幕获取正常”。
- 检测仅使用当前用户的凭据，返回可解释状态、检测时间与脱敏原因；不要触发所有条目重抓。
- 提取失败保存机器可读的 `stage`、`discovery_status` / 错误码，并向 UI 提供下一步：“更新 B 站登录态”“重新提取”“上传字幕/粘贴文字”。
- `login_required`、凭据失效、`no_track`、`blocked`、`network_error`、分 P 不存在、字幕结构变化分别处理。证据不足时明确未确认，不猜测。
- 成功必须保存实际拿到的原始字幕 JSON、规范 SRT 和带片段定位的文字稿，再接 AI。只生成标题、简介或待补充条目不算字幕成功。
- 更新凭据后对符合条件的旧 B 站条目去重排队；已就绪条目不重跑，已有手动正文优先保留。无法仅凭历史数据判断的条目可提供单条重试，不批量猜测。

真实平台验收至少包括：登录态可取字幕、未配置/失效凭据、无独立字幕、P2/P3、短链，以及上传字幕后完成加工。能取得的样本须在服务器走到 Obsidian；受平台限制的样本须有真实原因与可用降级。不得承诺所有 B 站视频都有可下载字幕。

## 4. 任务 B：统一登录、邀请码注册与管理员界面

### 4.1 沿用现有中心会话

已读中心接口：

- 登录页面的跳转参数是 `return_to`，登录 POST JSON 使用 `returnTo`，由现有表单转换；接入时保持一致。
- `GET /api/auth/session` 接收已配置的共享会话 Cookie，返回：
  `{ data: { user: { id, username }, expiresAt } }`。
- Cookie 名称、父域、有效期由 `SESSION_COOKIE_NAME`、`COOKIE_DOMAIN`、`SESSION_TTL_DAYS` 配置；当前实现为 HttpOnly、生产 Secure、SameSite=Lax、Path=/，会话令牌只存哈希。
- 校验接口可能附带滑动续期 `Set-Cookie`；Atlas 已处理这条返回链路。
- Ledger 部分 README/AGENTS 示例把域名拼成 `jerrythelpaca.cn`，少了一个 a；用户明确域名是 **`jerrythealpaca.cn`**。实施前核对实际 `AUTH_ORIGIN`、Cookie Domain、Caddy 与允许返回地址，不照抄错误示例。

知识库采用“服务端校验中心会话”的现有模式：

1. 打开 kb，前端通过知识库同源的当前账号接口获取会话状态。
2. 无会话时前往已有中心 `/login?return_to=...`；浏览器已登录 Ledger/Atlas 时直接进入，不要求再次输入配对码或密码。
3. 知识库服务端只提取指定中心 Cookie，发给固定配置的中心会话校验接口，读取其真实返回的用户 ID；不转发整串 Cookie。
4. 校验成功后映射到知识库本地用户；正常业务查询继续按本地 user_id 隔离。
5. 需要续期时，处理来自固定中心服务、匹配预期名称/域/路径的续期 Cookie，确保浏览器也更新有效期。不能仅延长中心数据库时间而漏掉浏览器续期。
6. 中心明确返回未登录则 KB 返回 401；中心超时/异常返回可恢复的 503，不当作无账号、不创建新用户，也不无限循环跳登录。
7. 页面接口可跳转登录，业务 JSON API 继续返回 JSON 401/503，不把登录 HTML 当 API 数据。

新配置可采用 `AUTH_LOGIN_URL`、`AUTH_SESSION_URL`、`AUTH_LOGOUT_URL`、`AUTH_COOKIE_NAME` 等明确名称，最终写入 config、Compose、环境示例。中心 HTTP 调用超时有限，目标固定，禁跟随未知重定向；容器内地址由实际部署网络确定。不要为了连内网认证服务放宽抓取器的公网限制，使用独立、固定目标的认证客户端。

共享 Cookie 的 Domain 决定子域接收范围，浏览器携带 Cookie 不代表应用已验证身份。[MDN Cookie 作用域说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)  
本期沿用用户已有的受信任子域方案，不引入另一套 OAuth/OIDC 服务，不把中心令牌放入 localStorage。

### 4.2 服务端身份和权限改造

- `api/deps.py` 支持两条明确通道：Web 中心会话；插件/已授权采集设备的本地 Bearer Token。显式传入无效 Bearer 时直接拒绝，不再悄悄使用浏览器 Cookie 换一个身份。
- 可新增知识库同源 `GET /v1/auth/me`，返回本地 user_id、中心账号显示名、认证方式和必要权限，作为页面初始化与管理员入口的依据。中心会话响应增加服务端计算的角色/权限字段时保留现有 `data.user.id`、`data.user.username`、`expiresAt` 结构，保证 Atlas 和 Ledger 既有调用继续可用。
- 当前依赖为 `(user, device, token)`。中心会话不必伪造数据库 Token；可改成一个小型 Principal，承载本地用户、固定业务 scopes、认证方式和可选设备。同步回执只允许有合法设备的通道，继续校验 consumer_epoch。
- Web scopes 由服务端决定；管理员是额外权限，不能把所有 `profiles:manage` 用户视为管理员。
- Cookie 写操作继续有 CSRF Token 与精确 Origin 校验；子域同站不等于同源。将 KB 加入中心需要的 Origin / return_to 白名单，避免通配任意子域或任意外部跳转。
- 共享退出应撤销当前中心会话并清除正确 Domain/Path 的 Cookie。中心 logout 接口需要 Origin，KB 代理时只在本地通过 CSRF/Origin 校验后使用固定允许 Origin 转发。
- 退出这条响应不能再回写中心的滑动续期 Cookie：`GET /api/auth/session` 每次校验都带一颗，按 §4.1 第 5 条原样转发会把刚清掉的凭据重新种回浏览器；删除也要带上与写入时一致的 Domain 与 Secure，否则浏览器视作另一条 Cookie，父域上的会话凭据留下来（表现为退出后按返回键仍是登录态）。
- 默认不缓存中心鉴权结果，确保中心会话撤销后下一次 Web 请求即失效。本期的插件 Token 是可撤销设备凭据，浏览器退出不自动撤销插件；在界面区分“退出网站”和“断开插件设备”。

### 4.3 旧账号与数据映射

**不能按用户名相同就把两个账号自动合并，也不能在用户首次 SSO 登录时把旧材料挂到一个空的新账号下。**

在知识库本地用户上增加可空的 `auth_subject`（中心不可变 user.id）及唯一约束；单一认证源不需要泛化身份平台。新用户首次进入 KB 时幂等创建本地用户；并发首次访问靠唯一约束收敛到一行。

账号中心由 `jerrythealpaca.cn` 各子域名共用，因此「进过 KB 才有本地用户」不足以支撑管理页：管理员打开用户列表时先代理中心 `GET /api/admin/users`，把只注册、尚未进过 KB 的账号也幂等映射进本地 `users`，注册时间以中心为准。中心不可达时列表退回只含本地用户，响应以 `central_available=false` 标记，管理页据此提示可能缺失新账号。

已有用户先建立可审阅的一对一清单：`kb_user_id ↔ auth_user_id`。管理员本人对应的两个实际 ID 由现有数据核实；无法唯一确定时向用户确认这项映射，不能猜。

- 绑定仅增加身份映射，**保留知识库原 user_id**。Item、Capture、Profile、Credential、Device、文件、回执仍归原 ID。
- 现有凭据加密 AAD 绑定 user_id/profile_id/version；直接更换所有 user_id 会导致解密失败，因此不要通过改主键完成统一账号。
- 映射前后验证旧条目数量、原始材料可下载、模型 Key 与 B 站凭据仍可解密、已有插件设备归属不变。
- 未匹配旧账号暂保留，列出待处理项。迁移脚本提供 dry-run、重复运行无副作用、冲突不覆盖。

中心注册不复制任何用户数据。新中心账号首次进入 Ledger 时应获得自己的初始分类（复用现有创建用户/种子逻辑）；首次进入 KB 时得到空的个人空间和自己的模型设置。

### 4.4 注册、邀请码与管理员权限

**中心服务拥有账号、管理员权限和邀请码。** 管理员入口同时可从 Ledger 的账号/设置区域和 KB 的账号区域进入同一个中心管理页面；不分别维护两份邀请码表。

建议中心新增：

| 路径（建议，尚未实现） | 功能 |
| --- | --- |
| `/register` | 与现有登录页同一认证站点，表单只需用户名、密码、邀请码；保留 return_to |
| `POST /api/auth/register` | 校验邀请码并创建账号，随后建立现有会话并返回白名单内 redirectTo |
| `/admin/invitations` | 管理员邀请码页面；账号操作区域显示“管理员”入口 |
| `GET /api/invitations` | 本期管理员查看自己生成的邀请码元数据 |
| `POST /api/invitations` | 服务端检查生成权限后生成邀请码 |
| `POST /api/invitations/{id}/revoke` | 撤销未使用邀请码；重复撤销幂等 |

管理员身份建议给中心 users 增加 `role=user|admin`，默认 user；把已核实的用户本人中心 ID 提升为 admin。禁止“首个注册者自动管理员”、按任意用户名硬编码、信任前端 isAdmin 或允许注册体提交 role。已有账号正常登录不需要补填邀请码；邀请码只约束新注册。

为后续普通用户邀请预留最小模型：

| 表/字段 | 本期语义 |
| --- | --- |
| users.role | 普通账号 / 管理员身份 |
| users.invite_enabled | 普通用户未来能否生成；默认 false，本期不开放开关 |
| users.invite_quota | 普通用户累计可生成数量；默认 0，不实现月度重置等系统 |
| invitations.id / code_hash | 随机 ID；邀请码用高熵随机值，只保存 SHA-256 哈希和可展示尾号 |
| invitations.created_by_user_id | 实际创建者；服务端从中心会话写入，不能由请求体指定 |
| invitations.created_at / expires_at / revoked_at | 创建、过期和撤销状态；建议默认 7 天过期 |
| invitations.used_by_user_id / used_at | 本期每码单次注册；记录实际被邀请用户与时间 |

权限收口为一个服务端判断函数：本期仅 admin 允许；未来可在这里启用 invite_enabled + invite_quota。记录创建者能计算已生成数、控制归属，无需搭建复杂角色权限平台。预留不等于现在给普通用户显示按钮或开放生成 API；不要用“允许邀请”冒充管理员权限。

交互：管理员进入页面点击“生成邀请码”，默认生成一个单次、7 天有效的邀请码，立即展示并可复制；列表显示尾号、创建时间、有效期、未使用/已使用/已撤销/已过期与使用者。完整码只在创建响应中显示；丢失后可撤销并重建。默认不要求再填备注或经历确认弹窗。按钮提交期间防重复点击。

注册事务必须同时完成“条件消费仍有效且未用的邀请码 + 创建中心用户 + 记录使用者”，全部成功才提交。密码使用现有 Argon2 实现及既有参数，哈希计算放在占用写事务前；字段校验、Origin/CSRF 和限速复用现有认证结构。

注册即登录时，会话的数据库记录也应与注册事务一致提交；事务提交后若响应在网络中丢失，账号已经创建，应允许用新账号正常登录，不能再消费一次邀请码。

必须覆盖：无邀请码、错误码、过期、撤销、已用、重复用户名、两请求并发消费同一码。注册失败不能消耗码；并发最多一个账号成功；新用户不能访问创建者的数据或拿到其管理员权限。邀请码不得写日志、查询字符串、分析事件或示例仓库。

### 4.5 Obsidian 插件也取消手输配对码

插件不读取浏览器 Cookie，不收集中心密码。建议使用“打开系统浏览器登录 + 插件自动领设备 Token”的短期授权流程，复用原来的 Device/Token 与 SecretBridge。

一条可直接实现的流程（接口命名为建议）：

1. 插件点“登录账号”，调用 `POST /v1/auth/device/start`，只传设备名称。
2. 服务端创建 5 分钟有效的授权请求，返回随机 request_id、仅交给插件的高熵 poll_secret、KB 上的 browser_url、expires_at 和轮询间隔。数据库只存 poll_secret 哈希；browser_url 只含 request_id。
3. 插件打开 browser_url。页面走同一个中心登录；已登录就显示账号、设备名称及“登录此插件”按钮，明确是在授权设备。只有受 CSRF/Origin 保护的 POST 能批准，GET 不产生授权。
4. 插件按服务端间隔（建议 2–5 秒）向 `POST /v1/auth/device/poll` 提交 request_id + poll_secret。未批准返回 pending；过期/取消停止。
5. 批准时绑定中心用户及其本地用户，限制一条请求只能批准一次且不能换账号；领 Token 前再检查批准会话仍有效。成功轮询原子消费该请求并签发固定 desktop scopes 的本地 Device/Token，返回原有 user_id、device_id、token、expires_at。
6. 插件经 SecretBridge 保存，保留同账号原同步状态并开始同步；失败可重新点登录。令牌交付响应丢失时重新发起授权，不保存明文 Token 做无限重放。
7. 提供插件“退出/断开设备”操作，撤销当前设备 Token，清理本地凭据并停止同步，保留已经导入的笔记。

start/poll 有限速、过期清理、取消处理；仅知道浏览器 request_id 不能领 Token。poll_secret 和最终 Token 不出现在 URL、浏览器页面或日志。不要只把手输配对码改成“去网页复制 Token”。

同账号重新登录应保留现有 device_id（只允许出示仍有效旧设备凭据时复用），或明确完成现有 consumer_epoch 接管流程；过期旧 Token 不能单凭 device_id 恢复所有权。换账号时按 server + user + device 隔离/切换游标、待回执和本地索引，不能向 B 账号提交 A 的回执，也不能删除 A 已导入笔记。

切换发布后关闭 CLI 配对码新签发、Web 配对会话入口与配对交换接口，清除旧 kb_session 的认证路径；旧 desktop/phone Bearer 设备在映射正确且未过期/撤销时可以继续使用，避免同步突然中断。新建 Web/插件用户不再走旧配对路径。若存在真实在用的手机采集客户端，先盘点并保留其有效 Token；需要新增采集授权时复用浏览器流程且由服务端限定 phone scopes。

### 4.6 Atlas 的兼容边界

Atlas 当前可用 `TRAIN_AUTH_USERNAME` 限定访问者，而且其读取/写入的行程文件不是本轮要改造的多租户数据模型。开放中心注册后，**不能为了“共享登录”删除这项账号限制，让新用户看到用户本人的行程**。

本轮只要求既有 Atlas 账号仍能共用登录。保留其现有访问约束，核对线上是否已配置；其他用户在无权限时得到明确拒绝，不陷入登录循环。Atlas 对外开放多用户数据隔离是独立需求，不在本轮实现。

### 5.2 调用状态要从账本中分离

当前 `budget.create_operation / settle_operation / refund_operation` 同时改变操作状态；Worker 用 `reserved/sent` 判断中断发生在发送前还是发送后。删除函数时必须接回执行状态：

- 发送前有可持久化的操作记录，发送前后在短事务中更新状态；网络请求继续位于事务外。
- 成功、供应商明确失败、超时、租约丢失和旧来源版本各自结束或暂停正确任务。
- 已发送但结果未知仍标 `unknown_outcome`，避免进程重启无限重复调用；用户可按现有“重新加工”继续，文案不再要求先核对账单。
- 旧名称 reserved 可以在迁移中改成 prepared，也可暂保留并解释“调用待发送”；不能再触发资金预留。
- 不把历史 `sent/unknown_outcome` 批量认定为成功，也不在删账本时自动重发它们。

### 5.3 存量升级

先备份并在数据库副本上演练，再用新增 Alembic 迁移和一次性可重复执行的恢复步骤处理；不要修改已经发布的初始迁移文件。

1. 停止产生新计费记录，让新 API/Worker 不再依赖旧表列。API 与 Worker 同步升级，避免旧 Worker 继续写账。
2. 旧账本及计费列可先留作不再读取/写入的历史数据，避免本轮强制清空；无须为其保留业务 API。确需删表时必须另有备份和明确回滚方案。
3. 对旧 `waiting_budget` Item：排除已删除、过时来源、有在途/未知操作的条目；按当前原始材料、凭据与最新 source_revision 决定转 queued 或 waiting_key/needs_input。复用现有 enqueue 的唯一约束，不重复创建任务。
4. 保留已发布 Bundle，不把“恢复排队”变成删除原始材料或重建所有历史条目。
5. 迁移检查结束后应无仍等待金额预算的有效条目；保留历史事件可以，但新事件不再产生 usage/cost 字段。
