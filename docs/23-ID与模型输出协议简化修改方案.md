# 知识内容与引用体系重构方案

日期：2026-09-21  
状态：实施中；字段级契约与实施记录见 [docs/24](24-内容协议v3契约冻结与实施记录.md)。M0 契约与样本、M1 云端生成与阅读链路、M3 分享侧已落地并通过本机自动化验证；M2 插件与本地整理进行中；旧数据迁移只在开发库副本上端到端跑过，生产迁移与部署按当次授权执行。  
决策更新：按用户“可以改得大胆一些，整个重构都可以”的要求，本版替代此前以兼容旧输出结构为优先的方案。

## 1. 重构目标与主要决定

**取消模型生成的持久观点 ID，取消 Knowledge 必须经 Digest 才能追溯原文的中转关系，把“内容生成”和“系统身份管理”彻底分开。**

不再把旧 analysis.json、旧 evidence_map 和旧插件输出格式作为新架构的前提。服务端、Web、Obsidian 插件、本地整理与分享生成共同采用新的内容与引用契约；旧数据通过迁移转换，不长期维护两套生成逻辑。

最终效果：

- 模型写内容、选择证据，不编 c0001，不抄 UUID、来源版本和哈希。
- 摘录可以独立存在，不必强行绑定某个“核心观点编号”。
- 知识笔记中的依据直接跳到当时的原文，不强制先打开一份摘要快照。
- 新增、修改、合并观点时，不需要同时维护正文编号、观点变更数组和完整证据映射。
- 一般阅读看不到系统编号；新笔记文件名不再带长 item_id。
- 有效内容不因为可选摘录的单个错误全部作废；真正的来源错误仍需处理，不能以“简化”为由编造依据。
- 系统内部仍保留条目身份、不可变来源版本、同步回执和正文基线保护。

允许改变接口和内部文件格式，允许同步升级插件。改动集中在内容、引用、整理和阅读链路；用户隔离、凭据、来源适配、音频处理等已有基础能力继续复用，不借机重写。

本方案依据当前工作区代码阅读。没有统计生产错误样本，因此不承诺重构后成功率的具体百分比。

## 2. 哪些结构删除，哪些留下

| 当前结构 | 决定 | 替代方式 |
| --- | --- | --- |
| 模型生成 Digest claim_id | 删除 | 内容数组决定展示顺序，程序无需给每条新观点持久编号 |
| excerpts.claim_id 引用核心观点 | 删除 | 摘录作为独立的有来源内容块 |
| Knowledge 的持久 claim_id 与逐条沿用规则 | 新内容取消 | 以文档版本记录历史，以正文差异说明变化 |
| added/updated/retired_claims 三套模型输出 | 删除 | 插件计算前后文本差异，模型只说明实质变化与冲突 |
| 模型输出完整 evidence_map | 删除 | 模型选任务引用，程序形成文档级引用表 |
| Knowledge → Digest 观点 → 原文的强制两跳 | 删除 | Knowledge 内容块 → 固定版本原文 |
| 只有为了两跳引用才生成的 Digest 冻结快照 | 新流程不再要求 | 保留原文证据快照和知识文档历史；旧摘要快照不删除 |
| 模型回填 base_hash / revision / schema_version | 删除 | 调用上下文与保存程序负责 |
| 本地晋升五维度严格 JSON 与逐观点状态账本 | 从默认流程移除 | 按知识主题生成候选修改，说明价值、限制和冲突；用户看差异采纳 |
| 分享整合稿 sections.id / claims.id 等模型编号 | 删除 | 使用同一内容结构；下游需要锚点时由程序生成 |
| 条目、用户、设备、任务、文件、文档 ID | 保留 | 系统内部身份与持久关系 |
| Source 版本、片段位置、正文哈希、回执 | 保留 | 精确引用、编辑保护与同步正确性 |
| 每篇笔记的 kb_id 或等价文档身份 | 保留 | 笔记改名、移动后仍能识别 |
| 新笔记文件名的长 ID 后缀 | 删除 | frontmatter 身份 + 可重建的 ID→路径索引 |
| 原文附件目录中的内部 ID | 保留 | 用户通常不直接阅读，不为美观重做存储 |

这是功能取舍：新系统不再承诺“观点 c0007 在所有知识版本中始终是同一个对象”，也不提供逐观点的长期晋升状态。保留的是整篇知识的版本、每段内容的原文依据，以及可读的修改记录。这些足以支撑当前个人知识库的阅读、整理、采纳与回看。

如果用户只采纳部分内容，可在候选差异中选择段落或编辑候选稿；这些选择属于本次候选，不生成永久观点 ID。

## 3. 新架构：内容文档 + 原文引用

### 3.1 用户仍能理解的三层

保留 Source / Digest / Knowledge 的产品分工：

- Source：取得的原始材料及固定版本。
- Digest：一份来源的阅读提炼。
- Knowledge：围绕主题整理后的当前理解。

三层不再等于三层逐观点 ID 关系。Digest 是阅读与整理输入，不是所有知识引用的必经数据库实体。

分享整合稿也采用下面的内容结构，HTML 页面属于它的展示产物。

### 3.2 统一内容文档 ContentDocument v3

文档公共结构：

    {
      "format_version": "3.0",
      "document_id": "由程序提供",
      "kind": "digest",
      "revision": 1,
      "title": "内容接收与提炼",
      "summary": "先可靠保存，再进行提炼。",
      "sections": [
        {
          "heading": "主要判断",
          "blocks": [
            {
              "kind": "claim",
              "text": "内容接收和总结应分别记录处理结果。",
              "refs": ["e1"]
            },
            {
              "kind": "quote",
              "text": "采集与总结应该分开处理，避免混在一起。",
              "refs": ["e1"]
            },
            {
              "kind": "suggestion",
              "text": "可以分别统计两个阶段的失败原因。",
              "refs": []
            }
          ]
        }
      ],
      "references": {
        "e1": {
          "item_id": "由程序提供",
          "source_revision": 1,
          "segment_ids": ["s0001"],
          "source_text_hash": "由程序计算"
        }
      },
      "limitations": [],
      "provenance": {
        "input_documents": [],
        "recipe_version": "由程序提供"
      }
    }

说明：

- document_id、revision、references、provenance 由程序组装，模型不回填。
- kind 的文档类型为 digest / knowledge / synthesis。
- sections 和 blocks 不分配业务 ID，顺序由数组表达。
- refs 只是本篇文档内引用表的键，不是永久观点身份。
- references 中的 e1 由程序生成并固定在该文档版本内；它不能脱离 document_id + revision 单独使用。
- 单一 e 引用指向一份固定来源中的连续原文范围；不连续依据用多个引用。
- provenance 记录这次整理用了哪些文档，仅用于历史、失效判断与恢复，不是正文引用必须经过的一层。
- 知识文档的引用可以直接携带原有来源，加上本次新来源，无需保持原摘要的观点结构。
- 本地模型输出和 Knowledge 原文仍留在用户电脑，不因为采用公共格式而上传到云端。
- 复用现有 Bundle / StoredFile 保存云端 JSON 与 Markdown；不必为每个内容块新增数据库表。

### 3.3 内容块只有四种角色

| kind | 含义 | 校验与展示 |
| --- | --- | --- |
| claim | 来源主张、方法、归纳或综合结论 | 至少一个有效引用；有引用不代表语义已被证明 |
| quote | 逐字摘录 | 有引用，且在引用的连续原文范围内逐字出现 |
| suggestion | AI 提议、假设、候选启发 | 可以无引用；明确标为 AI 建议/待验证 |
| text | 标题下的导语、结构说明等 | 可无引用；不能用于把来源主张伪装成无需证据的内容 |

标题来自 section.heading；块内 text 支持必要的 Markdown，但不接受模型生成的 Obsidian 文件路径或内部链接。quote 保存纯摘录文字，由渲染器加引用样式。

不强制章节名称、不校验“必须有十二条观点”。单篇提炼提示词引导输出摘要、主要判断、原文摘录、方法与限制，材料没有的部分可以不生成；涉及 AI 对话时，可使用“决策过程”等自然章节保留上下文。

基础规则只检查必要字段、合理体积、引用有效性、摘录真实性与角色声明。不能通过四种角色本身自动证明语义正确，仍保留人工采纳和少量抽查。

## 4. 模型实际只看到什么

### 4.1 输入

程序将来源整理为阅读单元，以自然段为主，字幕按现有段落/时间组织。保留底层 segment_id，不把每条字幕编号全都暴露给模型。

    {
      "task": "提炼这份材料",
      "source": {"title": "示例文章", "coverage": "full_text"},
      "material": [
        {"ref": "R1", "text": "采集与总结应该分开处理，避免混在一起。"},
        {"ref": "R2", "text": "本地整理才决定是否晋升为长期知识。"}
      ]
    }

后台引用表把 R1 绑定到来源身份、版本和原文范围。输入中不需要 UUID、持久观点 ID、正文哈希或物理路径。

引用表规则：

1. R 编号是**程序分配的本次任务选项**，模型只能选择，不能自建。
2. 多材料统一分配，不会出现两篇材料的 s0001 互相覆盖。
3. 分块和修复沿用同一任务绑定，不能在中途把 R1 改成另一段。
4. 本次操作输入与引用表一起固定，重启后仍可恢复；完成组装后临时引用不再作为新的永久身份体系。
5. 阅读单元过长时按现有片段边界拆开，不能牺牲定位精度来减少编号。
6. 为局部阅读单元保留时间范围、段落位置等程序元数据，用户界面显示自然位置。

### 4.2 输出

所有内容生成任务使用相同的精简主体：

    {
      "title": "内容接收与提炼",
      "summary": "先可靠保存，再进行提炼。",
      "sections": [
        {
          "heading": "主要判断",
          "blocks": [
            {
              "kind": "claim",
              "text": "内容接收和总结应分开处理。",
              "refs": ["R1"]
            },
            {
              "kind": "quote",
              "text": "采集与总结应该分开处理，避免混在一起。",
              "refs": ["R1"]
            }
          ]
        }
      ],
      "limitations": []
    }

不再要求输出另外一份 claims、excerpts、evidence_map、段落 ID 或变更观点列表。内容与自己的依据放在一起，避免并行数组互相引用。

不同任务只增加真正必要的结果：

- 单篇提炼：只返回主体。
- 知识融合：增加 no_op、change_summary、conflicts；no_op 时无需重发整篇正文。
- 分享整合：可额外给出读者目标、可视化意图和材料采用说明，引用沿用同一套 R，不新建第二套 citation 编号语法。

### 4.3 程序组装

程序顺序执行：

1. 解析响应，检查基础类型与体积。
2. 对引用去首尾空白、精确去重；只接受本次给定的引用值。
3. 查表得到真实的来源范围；不模糊猜测 R99 应该是 R9。
4. quote 在给定相邻原文范围中匹配，最多规范化空白，不忽略文字本身。
5. 为引用到的来源范围生成文档局部 e 键，转换 refs。
6. 写入真实文档身份、来源版本、生成规则和输入记录。
7. 生成 Markdown、阅读视图和供后续处理使用的 ContentDocument。

引用表必须和实际文本一致。AI 纠错后的正文不能覆盖同一个“不可变来源版本”。本方案采用**新来源修订**，其元数据记录“机器纠错派生自哪个原版本”，未纠错原件继续保留。所有引用只指向已经固定的具体文本。source_text_hash 对固定规范化原文的 UTF-8 字节计算；写入、下载和迁移均使用同一规则。

纠错产生派生修订后，当前任务绑定该修订继续提炼，不能再因“出现新版本”重复触发同一轮纠错。派生修订按父修订、纠错规则版本和结果文本摘要去重；用户提交新正文仍走正常的新版本流程。

## 5. 云端提炼与长文本重构

### 5.1 移除旧输出协议

重写 templates.py、analysis.py 与 enrich.py 的生成边界。新流程直接产出 ContentDocument v3，不把新响应重新塞回旧 Schema 2.0。

原有分析校验器只保留在历史转换工具中；新主路径不再运行 claim_id 正则、摘录观点关联、旧 evidence_map 合并等规则。

云端产物使用 content.json，Bundle 清单明确登记格式。preview.md 由同一个新渲染器生成。网页与插件都读取新结构，不再从固定“核心观点与证据”文字中反向猜字段。

### 5.2 分块与汇总

1. 分块输入是本任务 R 引用中的子集。
2. 每块产出相同的 sections / blocks 候选；不分配最终文档 ID 或观点编号。
3. 每块先校验本块引用和摘录，只有有效候选进入汇总。
4. 汇总可合并和改写 claim，但不得新增候选之外的来源引用。
5. quote 必须沿用已经验证的原文与引用组合；模型不能把改写句子升级为逐字摘录。
6. 汇总修复必须带上完整候选和可用引用，而不是只带一个不包含候选的 source_data。
7. 每次逻辑操作只有一次修复额度，JSON 错误与引用错误共用，不逐层叠加重试。
8. 一块提取失败可以保存其他有效候选为“部分提炼”，明确指出未覆盖范围；不得把它发布为完整成功。失败块可单独重新生成后再汇总，任务记录中固定块输入与规则版本。
9. unknown_outcome 继续表示调用结果未知，不作为自动再次计费调用的理由。

### 5.3 失败按影响范围处理

| 错误 | 新行为 |
| --- | --- |
| 模型多返回了版本、UUID 等程序字段 | 忽略其值，程序自行填写，不请求修复 |
| 必填主体缺失、JSON 无法解析、输出截断 | 一次修复；仍失败则保留原始材料与诊断 |
| 某条 quote 不逐字匹配 | 一次修复后仍不匹配则不发布该摘录；保留其他已验证内容，说明“部分摘录未能核实” |
| 某条 claim 的所有引用无效 | 不作为有依据结论发布；可留在受控诊断草稿，不能自动改成 suggestion 掩盖失败 |
| claim 中混有有效和无效引用 | 修复后仍有错误则整条暂不发布，不能悄悄删掉可能关键的那份依据 |
| suggestion 无来源 | 允许，必须维持候选启发身份 |
| 有效内容只剩空架子 | 结果失败，不能靠一个 summary 假装完成 |
| 程序引用表或版本不一致 | 组装失败，按程序缺陷定位，不让模型修复内部身份 |

部分结果的发布规则：

- 增加明确的完整性元数据：complete / partial，附缺失阶段和受影响范围。
- 沿用加工成功/失败之外的现有状态体系时必须明确映射；若现有 API 无法表达 partial，就修改它，不能借用“完成”掩盖。
- Web、插件及本地整理都展示部分结果标识。本地默认只为完整且证据有效的材料自动准备融合；用户显式选择部分材料时，仅使用已验证的覆盖范围，并在候选中保留限制。
- 若被移除块影响全文 summary，程序不猜测如何修正摘要：清空生成摘要，显示由程序提供的部分结果说明；后续重新整理再生成完整摘要。
- 不把“少报错误”作为成功率提升；统计完整成功、部分可用、失败和修复调用次数。

以上部分发布用于新生成的阅读产物。知识融合的替换稿若引用校验失败，保留为待修复候选，不能通过删除错误块来自动覆盖现有知识正文；分享成品也必须完成整稿及公开引用检查后才能发布。

## 6. 本地整理改为“主题候选修改”

### 6.1 取消逐观点生命周期

不再为每个 c0001 维护晋升状态、五维评分与目标主题；也不再让模型重复返回相同的观点列表和证据链。

新的主流程：

    收到新材料
      → 本地检索相关主题
      → 选择目标主题或建议新主题
      → 模型生成主题修改候选
      → 程序计算差异、检查证据与基线
      → 用户采纳、部分采纳、编辑或跳过

保留“云端只做单篇提炼、本地维护主题知识”的边界。主题检索仍使用已有标题、别名和范围索引，不新增向量数据库。

目标选择的最小响应只需要：

    {"target": "T1", "reason": "为现有主题补充一个适用条件"}

T1 由本次候选主题列表提供。无匹配时返回新主题标题和范围建议；无有用增量时返回 keep_digest。不要求在这个阶段再生成内容证据映射。

### 6.2 融合输入与输出

融合输入包含：

- 当前主题正文、现有有效引用及其原文。
- 新材料的提炼内容、实际原文与可用任务引用。
- 用户锁定区域说明、本次整理目标。
- 标题与范围，避免无必要地扩展主题。

程序持有真实基线哈希和版本，模型不回填。

模型返回 ContentDocument 的内容主体，以及：

    {
      "no_op": false,
      "change_summary": "增加适用条件，保留尚未解决的分歧。",
      "conflicts": [
        {"topic": "适用范围", "description": "两份材料对条件的描述不同。"}
      ]
    }

正文可以自由重新组织。现有依据和新增依据都放入同一 R 引用表，正文块直接引用原文。旧来源能继续使用，不必重新通过某条 Digest 观点许可。

程序生成新增/删改的差异预览，不再要求模型输出 added_claims、updated_claims、retired_claims。模型没有可靠复现旧正文时，差异中会明确出现删除；默认仍需用户采纳，不能直接落盘。

“独立来源数量”只能按真实来源记录判断，不能按引用条数或模型自报“已交叉核验”推断。

### 6.3 部分采纳与用户编辑

候选以完整基线 + 候选文档保存。预览中的段落位置只是本候选的临时选择，不成为永久观点 ID。

- 用户可选择部分差异或编辑候选 Markdown。
- 选取后程序重新组装正文与引用，清除不再使用的引用。
- 编辑后含有逐字摘录的块重新做引用校验。
- 用户新写的观点可作为个人判断明确保存，不自动标成 AI 已核验的来源结论。
- 若编辑界面无法可靠保留结构，先提供“整篇候选可编辑、整篇采纳”，不要假装已完成可靠的逐段合并；部分采纳作为本阶段单独验收项。

### 6.4 保留必要的写入保护

1. 保存候选时固定主题基线、输入版本和引用表。
2. 采纳前重新读取当前主题正文；有人工或同步修改则候选过期，不能静默覆盖。
3. 写入时只替换管理区，保留人工区和未知 frontmatter。
4. 先保存主题历史、引用表与恢复记录，再提交正文。
5. 已存在的原文快照验证后复用；缺少所引用版本时不能拿最新原文冒充。
6. 重启恢复判断提交是否已发生，不能重复应用；本次候选有一个系统 ID 即可。
7. 回滚包括正文与引用表，不能只回滚 Markdown 或只回滚元数据。
8. 新引用直接指向固定原文，未迁移的旧引用仍使用旧快照，不覆写历史。
9. 正式写入知识前，将被引用的准确原文版本与定位索引保存在本地，校验文本摘要。不能依赖服务器临时保留期；仍被当前知识或保留的历史版本引用的原文不按普通缓存清理。引用缺失时暂缓采纳，不用标题或摘要补位。

现有全局 segment_id 合并覆盖和知识 claim_id 被误用为摘要锚点的问题，会随着删除该中转结构退出新路径；历史转换时仍需正确读取 digest_claim_id，不能把旧错链照搬成新直链。

## 7. 网页、Obsidian 文件名与分享

### 7.1 Web 阅读

routes_items.py 返回统一 content_document 与完整性状态，item-detail.js 按 sections / blocks 渲染，不再分别维护 key_points、excerpts、methods 等固定数组的展示代码。

- claim 显示自然文字与“查看原文”。
- quote 显示引用样式。
- suggestion 明确显示“AI 建议/待验证”。
- 来源按钮展示来源标题和段落/时间，不显示 R1、e1 或 s0001。
- 诊断入口保留详细错误，正常阅读不暴露内部协议字段。

改变接口后同步更新 contracts/openapi.json。不要只修改 JSON 而让旧网页拿到空字段后误显示“没有整理结果”。

### 7.2 Obsidian 阅读与文件命名

新文件名采用：

    01 Sources/2026/09/2026-09-21 文章标题.md
    02 Digests/2026/09/2026-09-21 文章标题.md
    03 Knowledge/主题标题.md

同目录同名冲突按明确规则追加“（2）”“（3）”。文件创建后路径登记到文档索引，不能每次同步根据当前目录重新猜序号。

- 文档真实身份放在 frontmatter 中，由程序维护。
- Source 和 Digest 都通过 ID→路径索引定位；索引丢失时扫描对应目录的 frontmatter 重建。
- 用户改名或移动文件后仍通过文档身份识别。
- 重复 kb_id 不能随意选一个覆盖，按真实身份冲突报告并保留两份文件。
- 源证据链接仍使用程序生成的稳定原文锚点，附件目录可以保留内部 ID。
- 不依靠展示标题作为数据库主键，不再通过 --item_id.md 后缀查找 Digest。
- 同步引擎、提交标记、恢复逻辑与本地整理的路径读取一起修改，不仅改 paths.ts。
- Markdown 是可阅读产物；机器回读优先使用同版本 content.json 与文档元数据，不通过显示文字猜出观点身份。

### 7.3 分享整合与 HTML

分享内容阶段复用 ContentDocument v3，取消 sec/k/claim 的独立模型编号体系；HTML 步骤接收已组装的内容与程序生成的公开引用清单。

公开引用、素材使用程序分配的短引用是必要的资源选择，不要求模型生成。保持以下边界：

- 页面可以列来源标题、允许公开的 URL 和已确认引用。
- 私人原文包、笔记内容、UUID/存储键不因为公开引用而自动公开。
- 私有来源没有公开 URL 时，可以显示允许公开的说明，不能生成指向私有 API 的失效链接或访问通道。
- 已发布作品使用固定版本资源，后续编辑产生新版本，不重编号历史页面。
- 复用现有 share-renderer 隔离构建和检查，内容协议重构不改变页面执行权限。
- 新内容协议建立新的会话规则版本/上下文 epoch，不能在既有缓存会话中无声改变固定 system 前缀。

## 8. 迁移旧数据，而不是永久包着旧结构

### 8.1 服务端历史 Analysis

提供可重复执行的迁移命令，先预览统计、再按条目提交：

1. 从指定旧 Bundle 读取 analysis.json、原文与原文版本。
2. 旧 key_points / methods 转为 claim 块，excerpts 转为 quote 块，insights 转为 suggestion 块，limitations 保留。
3. workflow 的问题、约束、决策、放弃方案与结果转换成自然章节，保留“提出/接受/否定/未知”含义，不能丢失对话状态。
4. 从旧 evidence_ids 解析真实原文，程序形成 v3 引用表。
5. 原文缺失或旧证据不成立时标记 unresolved，不编造来源。此类结果是迁移待处理，不进入完整成功内容集。
6. 写入新的 Bundle 版本；不修改旧 Bundle、manifest 或历史回执。
7. 记录输入摘要、转换器版本、新 Bundle 与迁移状态。相同输入再次执行不会重复生成。
8. 旧原始文件、旧产物作为历史保留；迁移结果经核对后，新主路径只读取 v3。

历史迁移不调用大模型，不借机重新总结私人材料。需要重新提炼的失败条目仍使用明确的重加工入口。

迁移读取原文必须绑定旧产物实际使用的 Bundle/文件摘要。若旧系统同一 source_revision 对应过不同的纠错文本，按实际固定文件分别建立派生修订；无法判断产物当时依据的是哪版文本时标记 unresolved，不能只取当前最新 segments.json。

### 8.2 本地 Knowledge 与旧证据

- 将旧 evidence_map 的每条来源展开为直接 Source 引用。多条来源分别保留，不能按相同 s0001 合并。
- 旧 Markdown 内容不经过 AI 重写；已有人工编辑、个人区、锁定区、未知 frontmatter 均保留。
- 正文与旧映射无法可靠对应时，不自动改写该主题；保留原文和旧链接，列入可读的迁移待处理报告，待人工处理或显式重新整理。
- 旧 Digest 冻结快照保持原路径与原文，既有引用仍能打开。
- 外部可能引用的旧 Knowledge 块锚点不能直接删除。该主题第一次改用新结构时，将相应旧观点原文与旧锚点保留在折叠的“历史引用”区，标明所属历史版本；新正文不再产生新的 c 编号。
- 旧摘要显示中的 [c0001] 只是文本时可在新渲染版本中移除；不能把它与真实 ^c0001 块锚点混为一谈。
- 旧已保存候选不强行转换到新融合规则：保留为旧候选归档供查看，新执行需要从当前材料生成 v3 候选。不得自动调用模型重做所有候选。

这部分需要一次性转换器和历史链接保留，不需要让新模型继续输出旧协议。

### 8.3 文件重命名

新文件立即使用可读文件名；旧文件纳入独立的本地迁移步骤：

1. 生成旧路径→新路径映射，检测同名和跨目录冲突。
2. 通过 Obsidian 提供的重命名能力操作，更新内部受管理链接与程序路径索引。
3. 结合实际 Vault 的“自动更新内部链接”设置核查用户链接；仅依赖设置不能宣称所有外部链接都已迁移。
4. 不确定能更新的旧路径保留为带跳转说明的兼容入口，不立即删除。
5. 旧路径兼容入口不能继续作为可写的同一文档副本，不能复制相同 kb_id 造成双写。
6. 对迁移范围内的笔记、索引和变更链接保存恢复记录，可按反向映射恢复。
7. 文件重命名失败不影响已保存原文，也不能发出导入成功回执。

新协议重构与文件改名都在本方案范围内，但应分别验收，便于定位内容问题和路径问题。

### 8.4 兼容层的退出

- 迁移期提供一个明确的旧数据转换/读取入口，不在业务代码各处散落 1.0/2.0/3.0 判断。
- 新写入只允许 v3。
- 已转完且没有待处理项的条目切换到 v3；未处理项明确显示“旧版内容”，不偷偷塞入新模型协议。
- 全量完成并核对后移除旧生成、旧校验与旧摘要中转写入路径。
- 历史文件和已发布链接可以长期保留，它们是历史数据，不代表继续维护两套模型协议。

## 10. 实施顺序与发布策略

这是一次目标一致的跨端重构。分里程碑验证工程结果，最终不保留旧协议作为新架构限制。

### M0：固定契约和迁移样本

- 固定 v3 JSON 契约、四类内容块、R→真实原文→文档引用的规则。
- 准备合成样本：短文、长字幕、多来源同号、对话、旧 Knowledge 与人工编辑。
- 统计本地或授权环境中待迁移产物类型，不读取无关用户资料。
- 确定完整/部分/失败状态与接口字段。

### M1：完整云端阅读链路

- 新提炼、分块、修复、部分结果、不可变来源修订。
- 新内容保存、API、Web 阅读、旧产物转换。
- 真实闭环验证，不能只写新提示词。

### M2：完整插件与本地整理链路

- 插件消费 v3，原文直链，主题候选，文档差异与写入保护。
- 新路径索引、可读文件名、本地历史和迁移恢复。
- 保留用户人工内容，确认回执和重复导入行为。

### M3：分享与旧路径退出

- 分享整合复用新内容结构，公开引用与构建正常。
- 执行已验证的迁移，清理不再使用的旧生成/校验代码。
- 完成文档更新与代表性人工验收。

实际编码可组织多 Agent：内容协议/服务端、插件/迁移、Web/分享分工。先固定共用契约和文件写入边界，再并行实施；由主 Agent 集成跨端检查。

发布要求：

- 先部署能识别新格式的消费者，再启用新写入；旧插件不能把未知格式当成空内容导入。
- 插件遇到不支持的新格式，应暂停该项导入并提示升级，不落盘空白摘要、不发送成功回执。
- 可以通过现有配置开关控制切换，但不新增长期按用户同时维护两套生成规则。
- M1 可在开发/验证环境独立运行；生产启用 v3 必须有可用的新插件和明确的旧客户端行为。
- 发布前停止接收新加工，完成或记录进行中的调用；结果未知调用沿用现有恢复机制，不能自动重发。
- 用户本次授权的是修改方案文档；实际部署、生产迁移和清理在实施任务中按当时授权执行。

## 11. 验收标准

### 内容与引用

- 模型输出中没有持久观点 ID、UUID、版本回填或完整证据映射。
- 任何新观点数量、顺序变化都不会触发观点 ID 格式失败。
- quote 不需要关联一个 key_point，也可独立保留。
- 两份材料都有 s0001，最终引用仍分别准确。
- 重新提炼 Digest 不改变旧 Knowledge 所引用的原文。
- AI 纠错后旧原文版本仍可读取，不能被新文本替换。
- 非法引用不能悄悄转成有效引用；摘录改写不能作为原话发布。
- 部分结果保留有效内容，清楚显示缺口，不能冒充完整成功。

### 本地与历史

- 取消模型哈希回填后，用户编辑仍能阻止过期候选覆盖正文。
- 多来源融合保留全部实际来源，直接跳到固定原文。
- 候选 no_op 不写入；重启恢复不重复应用。
- 旧证据转换不会把 knowledge claim_id 误当成 digest_claim_id。
- 旧引用锚点、旧摘要快照仍可访问。
- 新文件没有长 ID 后缀，改名、移动、同名冲突、索引重建均能正确同步。
- 旧文件迁移失败可恢复，不能出现两个可写的同 kb_id 文档。
- 人工区、未知 frontmatter、未纳入管理的笔记保持完整。
- 部分采纳若实现，验证选择后正文与引用一致；未实现必须明确说明。

### Web 与分享

- Web、Obsidian 均能展示 v3，正常阅读不显示裸内部编号。
- 旧客户端遇到未知格式不会产生空文件或错误回执。
- 分享 HTML 的引用清单正确，不公开私人来源包、内部路径或凭据。
- 页面修订不改变旧已发布版本。
- 旧数据迁移不额外调用模型。

### 验证方法与报告

- 复用 tests/integration/test_digest_schema_v2.py、test_m2.py、test_reading_view.py、test_source_edit.py、test_share_worker.py 等相关入口；迁移后重命名过时的契约测试。
- 增加真正覆盖来源版本、错误引用、部分结果、迁移恢复、路径变更和用户编辑保护的回归场景，不为简单渲染字段机械加测试。
- 插件实际提供 typecheck 与 build，当前 package.json 没有 test 脚本；采用真实可执行的纯逻辑测试入口并记录。
- 在临时合成 Vault 验证同步、迁移、旧链接、重命名和人工编辑，不直接用生产 Vault 做首次测试。
- 用少量授权的真实模型调用评估短文、长文、多来源与对话，不用模拟响应证明真实模型成功率。
- 报告完整成功、部分可用、失败、修复次数与原因。不要只报告“校验通过率变高”。
- 测试通过后只针对新增改动和未解决问题补验证，不重复跑无关全量检查。

## 12. 回退、成本与真实限制

### 回退

- 每个新云端产物写入新版本，旧产物保留；切换失败可停止 v3 新任务，不修改历史回执。
- 插件升级前保存相关 System 数据与笔记迁移清单；新格式写入后不能只换回旧插件继续编辑。
- 回退必须恢复一致的正文、引用表、索引和提交记录。存在后续人工修改时先比较并保留，不能直接覆盖备份。
- 迁移命令有预览、分项状态和可重入能力；不需要再造一套通用事务系统。
- 本方案不要求立即删除历史文件。真正清理只处理已证明不再被引用、且已有恢复依据的对象。

### 代价与收益

这是跨服务端、Web 和插件的中等至较大改造，工作量明显高于只修正 c0001 格式；不能称为改几条提示词即可完成。

换来的收益是：

1. 删除一整套没有必要让模型维护的观点身份和跨层关系。
2. 减少输出字段、互相回填和校验组合。
3. 缩短证据追溯路径，使阅读和实现都更直接。
4. 让有价值的部分结果可用，同时保留真实失败信息。
5. 后续内容形态变化不再要求扩展固定的观点/摘录/方法数组和对应 ID 关系。

仍然保留的限制：

- 结构正确、引用存在，不代表结论语义正确。
- 模型仍需选择少量任务引用，无法保证永远不选错。
- 新知识不再有跨版本永久观点编号，精确历史以文档版本和原文依据为准。
- 历史人工内容与旧映射不一致的条目需要明确处理，无法保证全部无损自动转换。
- 模型调用超时、输出截断和供应商差异仍需现有边界处理。
- 旧链接与新文件名需要实际 Vault 验证，不能只凭 JSON 测试宣布迁移成功。
