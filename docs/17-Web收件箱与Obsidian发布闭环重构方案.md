# 17 Web 收件箱与 Obsidian 发布闭环重构方案

> 文档状态：已实施（2026-09-15，P0–P4；见文末实施记录）  
> 编写日期：2026-09-15  
> 适用范围：Web 收件箱、条目阅读页、首次初始化、设置入口、面向 Web 的条目状态接口、Obsidian 发布回执展示  
> 不在本轮调整：登录页主体与统一账号流程、云端和本地知识整理的职责边界、既有可靠同步与不可变 Bundle 机制

## 1 结论与已确认决定

这次重构不是继续修补当前页面，而是重新定义 Web 产品的用户路径。页面只围绕一件事展开：用户把内容交给系统，系统完成提取、加工、整理，并在 Obsidian 真正写入后确认发布。

已经确认的产品决定如下。

1. 登录界面暂不调整。后续介绍网页放在登录首屏下方，向下滚动查看，不阻塞本轮重构。
2. 首页保留一个统一采集框。用户可以直接粘贴链接、文字或选择文件，不先选择来源类型。
3. “提取图片”和“提取音轨”不再常驻在空白采集框旁边，只在系统识别到相关内容且用户确实需要时出现。
4. 条目过程统一为四步：提取、加工、整理、发布。
5. 条目详情保留圆点连线式状态图，但重新设计视觉、动效、进度和状态语义。
6. ASR 不展示“已完成多少段、总共多少段”，只展示真实百分比；总量尚未确定时使用不带数字的等待动画，不伪造百分比。
7. “发布”只有在当前版本已经完整写入 Obsidian 且服务端收到回执后才能点亮。云端生成 Bundle 不再被称为已发布。
8. 首页只显示采集框和条目流。设置从顶部页签移除，改为右上角无边框齿轮入口。
9. 设置页暂不大改技术配置能力，但删除独立账号卡，并加入模型、Obsidian、可选平台三项首次初始化。
10. 条目详情只保留“整理结果”“原始内容”和“更多操作”三个用户概念；不再保留承接杂项的“管理”页签。
11. 允许调整底层 API，但优先复用现有可靠任务、Bundle、设备和回执能力，不为视觉重构重写已经验证的同步内核。
12. 所有提示、错误、状态和设置文案必须使用用户语言。`r2`、`r3` 等修订号和内部技术名词不进入默认界面；确有排障需要时，只能在用户主动展开的处理记录中配合白话解释展示。

## 2 第一性原理

### 2.1 用户目标

用户不是来管理流水线、版本号或任务队列的。用户只想知道四件事。

1. 我的内容是否已经被系统接收。
2. 系统现在正在做什么。
3. 是否需要我补充或处理问题。
4. 内容是否已经进入我的 Obsidian。

页面上出现的每一项信息都必须至少回答其中一个问题。不能回答的内部字段默认不显示。

### 2.2 页面原则

- 一个页面只有一个主要任务。
- 一个状态下最多只有一个主按钮。
- 系统能自动判断的事情不要求用户预先选择。
- 低频操作不常驻，放入“更多操作”。
- 状态先说用户能理解的结果，再提供可选技术详情。
- 等待不是错误。需要用户操作、系统失败和普通后台等待必须有明显区别。
- 不用动画伪造进度；只有可计算的阶段才显示百分比。
- 云端完成不等于进入本地知识库，“发布”必须由 Obsidian 写入回执证明。

### 2.3 产品心智模型

```text
随手丢进来
    ↓
服务器在后台处理
    ↓
有问题时只提示一个下一步
    ↓
Obsidian 上线后自动写入
    ↓
网页显示已发布
```

用户不需要理解 SourceRevision、BundleRevision、Job、consumer_epoch、manifest 或内部 pipeline_state。

### 2.4 用户语言契约

专业名词不是“显得高级”，而是把系统的理解成本转嫁给用户。所有用户可见文本都必须先回答：发生了什么、系统接下来会做什么、我是否需要操作。无法回答这三点的字段不应出现在提示框里。

这条规则覆盖所有界面文字，不只覆盖 Toast：

- 列表状态、详情状态、进度说明和空状态。
- Toast、确认框、弹窗、输入校验和页面级错误。
- 按钮、设置项、帮助文字、占位符和 Tooltip。
- 服务端返回给 Web 的错误文案。
- 首次初始化、平台授权和 Obsidian 设备状态。

默认界面禁止直接出现：

- `r2`、`r3`、SourceRevision、BundleRevision 等内部版本表达。
- Bundle、manifest、receipt、consumer_epoch、pipeline_state、Job 等实现名词。
- `unknown_outcome`、`waiting_key`、`needs_input` 等枚举值。
- bvid、cid、哈希、数据库主键、设备 ID、HTTP 状态码和异常类名。
- 未经处理的第三方接口报错、模型服务响应或 Worker 日志。

缩写和技术字段只有用户确实需要填写时才可以出现，并且先给中文含义。例如使用“模型服务密钥（API Key）”“服务地址”“B 站登录信息”；不要只写“API Key”“Endpoint”“SESSDATA”。语音识别在界面中统一叫“语音转写”，图片文字识别统一叫“识别图片中的文字”，Obsidian Vault 统一叫“Obsidian 知识库”。

#### 文案生成顺序

每条状态或错误按以下顺序表达：

1. 先说用户能感知的结果，例如“暂时没有读取到正文”。
2. 再说系统行为，例如“系统已保留这条链接”。
3. 只有需要用户介入时才给出一个明确动作，例如“补充内容”。
4. 不要求用户介入时，不加“请稍后重试”之类的无效指令。

文案不暴露内部对象，也不让用户为系统故障负责。对照示例：

| 内部信息或旧文案 | 默认界面文案 | 用户需要的操作 |
|---|---|---|
| `来源已更新至 r3，放弃发布旧结果` | 内容已经更新，系统会使用最新内容继续处理 | 无 |
| `现有提炼基于 r2，当前来源 r3` | 原始内容已经更新，需要重新整理 | 重新整理 |
| `Bundle 版本不存在` | 这份整理结果已经失效，需要重新整理 | 重新整理 |
| `consumer_epoch 过期` | 这台设备当前不会自动接收新内容 | 选择接收内容的设备 |
| `manifest 摘要不一致` | 这次下载的内容不完整，系统没有写入 Obsidian | 重新同步 |
| `unknown_outcome` | 暂时无法确认整理是否完成，系统正在核对结果 | 无 |
| `waiting_key` | 需要选择一个可用的整理模型 | 选择模型 |
| `needs_input` | 需要补充正文或字幕 | 补充内容 |
| `HTTP 422 / validation error: endpoint` | 服务地址格式不正确 | 修改服务地址 |

#### 技术信息的显示边界

普通用户不需要看到版本号。只有在“更多操作 → 查看处理记录 → 展开技术信息”后，才允许展示经过脱敏的内部记录。展开前先显示：

> 下面的信息用于排查问题，一般不需要处理。内容版本表示服务器保存的第几次修改，用来避免旧结果覆盖新内容。

即使进入技术信息，也优先写“内容版本 3”“整理结果版本 2”，不直接写 `r3`、`Bundle r2`。如果为了和日志或客服沟通必须保留原值，则在首次出现处解释：“`r3` 表示这条内容的第 3 次修订”。技术抽屉提供“复制技术信息”，但复制内容不自动出现在 Toast 或主页面。

#### 当前实现的首批整改点

重构时先切断以下内部信息穿透路径：

- `inbox.html` 的统一错误处理不能再直接 Toast `e.message`。
- 条目卡片和详情不能再直接渲染 `state_detail`。
- 来源变化提示不能再拼接 `r{source_revision}` 和 `r{digest_revision}`。
- 设置页默认层不再直接使用 Endpoint、SESSDATA 等字段名。
- Worker 中包含版本号的消息可以保留为日志，但不能作为用户文案返回。

代码评审时，任何新增的用户可见字符串都必须通过这份语言契约；不能靠发布前再集中“润色”。

## 3 新信息架构

```text
知识收件箱
├── 首次初始化
│   ├── 选择整理模型
│   ├── 连接 Obsidian
│   └── 可选连接内容平台
│
├── 首页
│   ├── 统一采集框
│   └── 条目流（时间倒序 + 需处理圆点标注，搜索可展开）
│
├── 条目详情
│   ├── 标题与当前状态
│   ├── 四阶段状态图
│   ├── 当前阶段说明或唯一主操作
│   ├── 整理结果
│   ├── 原始内容
│   └── 更多操作
│
└── 设置
    ├── 整理模型
    ├── Obsidian 与设备
    ├── 来源授权
    └── 高级设置
```

顶部不再显示“收件箱 / 设置”两个页签。左侧是产品名，右侧只有一个无边框齿轮和账号菜单。设置页使用浏览器路由或明确返回按钮进入，不与日常首页争夺导航层级。

## 4 首页设计

### 4.1 顶栏

桌面端：

```text
知识收件箱                                      ⚙   用户头像
```

移动端：

```text
知识收件箱                                           ⚙
```

齿轮按钮视觉上不带边框，只显示 20 至 22 px 的齿轮图标；实际点击区域保持至少 44 × 44 CSS px。Hover 只出现浅色圆形或圆角底，键盘聚焦保留清晰焦点环。

账号信息、退出登录和管理员入口放入账号菜单，不再在设置页使用独立账号卡。

### 4.2 统一采集框

默认状态只显示：

```text
┌──────────────────────────────────────────┐
│ 粘贴链接、文字，或添加文件……             │
│                                      ＋  │
└──────────────────────────────────────────┘
                                提交
```

交互规则：

- 粘贴一个 URL：直接识别为一个来源条目。
- 粘贴纯文字：生成一个文字条目。
- 选择音频：自动进入加工阶段，不再要求用户打开“提取音轨”。
- 选择普通文件：作为独立内容或附件处理，具体由文件类型决定。
- 输入框自动增高，但不超过首屏的合理高度。
- 支持 Ctrl 或 Command + Enter 提交。
- 提交后立即清空输入框，新条目出现在列表顶部并显示“已接收”。
- 上传较大音频时，采集框内展示上传百分比；上传完成后才进入四阶段流程。

不常驻显示：提取图片、提取音轨、来源类型、处理模型、归档策略、内容范围。

### 4.3 自动出现的上下文选项

只有识别到相关内容后才出现一行轻量建议，不使用强弹窗。

| 内容类型 | 自动行为 | 可选提示 |
|---|---|---|
| 普通网页或公众号 | 提取正文 | “同时保存正文图片” |
| B 站视频 | 优先使用已有字幕；无字幕时按用户设置决定是否 ASR | 无需显示“提取音轨” |
| 网页音频 | 自动识别音频候选 | 有多个候选时，在提交后条目详情中要求选择 |
| 本地音频文件 | 上传后自动转写 | 只展示上传进度和文件名 |
| 纯文字 | 直接作为原始内容 | 不显示额外选项 |

“同时保存正文图片”默认关闭，并且只对当前条目有效。用户选择后记住该用户偏好需要另行确认，本轮不默认记忆。

### 4.4 多链接和混合输入规则

统一采集框不能再静默把文字、备注和附件挂到“第一条”。规则必须可预测。

- 一个 URL：文字自动视为这一个 URL 的用户备注。
- 多个 URL：每个 URL 生成独立条目；提交按钮上方显示“将创建 N 条内容”。
- 多个 URL 加文字：明确显示“这段文字将作为 N 条内容的共同备注”。
- 多个 URL 加文件：文件生成独立条目，不任意绑定到第一个 URL。
- 多个音频：每个音频生成独立条目。
- 用户不需要进入额外向导；只有系统检测到歧义时才显示上述一行说明。

服务端可以继续接受现有 Capture 请求，前端按明确规则拆分；若未来需要批量撤销或批量查看，再新增 capture_batch，不在本轮提前建设。

### 4.5 条目流

首页取消九种内部状态下拉框和常驻平台 chips。条目按服务端 WorkflowView 的 `overall_state` 归入三组，组内仍按时间倒序（最新在最上），空组不显示标题：

| 分组 | 进入条件（`overall_state`） |
|---|---|
| 需要你处理 | `attention`、`failed` |
| 待发布 | `working`（提取中、整理中、等 Obsidian 上线、关了自动整理只等材料取走） |
| 已完成 | `published`（回执已到或原文已被下载走） |

「已完成」默认只露最新三条，其余折叠，组尾一个「展开其余 N 条 / 收起」按钮；展开状态只在当前页面会话内保持。条目卡片不再压红色小圆点（2026-09-19 决定：分组标题已经说明谁需要处理，圆点和它重复）。状态语义仍全部来自服务端，前端不做推断。

三个分组标题前各带一枚 6px 小色点作分类记号：需要你处理=红（`--bad`）、待发布=蓝（`--info`）、已完成=绿（`--ok`）；「搜索结果」那一组不属于三种状态，不给点。

没有条目时，采集框下只显示一句示例：“粘贴一条你刚看到的文章或视频链接。”

条目行只显示：

```text
标题或来源摘要                                  10:24
正在转写 63% · B 站
━━━━━━━━━━━━━━━━━━────
```

或者：

```text
标题或来源摘要                                  昨天
已下载到 Obsidian · 微信公众号
```

失败或需要补充时：

```text
标题或来源摘要                                  10:24
缺少可读取的正文                           补充内容
```

列表不显示版本号、Bundle、内部错误堆栈、转写段数、原始 pipeline_state 或永久彩色 badge。

### 4.6 搜索

首页默认不占一整行显示筛选器。条目流顶部只显示搜索图标，点击后搜索框从图标处向左展开（与图标同排，不推动下方条目）；有查询词时列表区只显示服务端搜索结果，清空或收起即回到完整时间流。

搜索必须由服务端覆盖整个用户收件箱，不能只搜索已经加载的前 20 条。`GET /v1/items` 增加 `search` 参数，并在标题、原始 URL、来源标签和可公开的状态说明中搜索。平台和用户状态作为可选二级过滤，不在首页常驻。

## 5 四阶段工作流

### 5.1 阶段定义

| 阶段 | 用户含义 | 典型工作 | 完成判定 |
|---|---|---|---|
| 提取 | 从来源取得原始材料 | 抓网页、取标题和正文、取字幕轨、保存上传内容 | 当前来源版本已经可靠落库 |
| 加工 | 把非文本材料转成可整理文本 | ASR、OCR、媒体预处理、必要的结构化转换 | 需要的加工产物已生成；不需要加工则不渲染此节点 |

“加工”是内部阶段名，界面不直接显示这个词：状态图节点按条目的实际处理方式动态出现。会用到 ASR 的条目（录音、网页音轨、B 站无字幕音轨转写）渲染「语音识别」节点（step 的 `label` 字段）；网页正文、B 站字幕在提取时已是文字，不渲染该节点，状态图三节点直达整理。未来 OCR 实装后，图片条目才出现「提取文字」节点。
| 整理 | 使用大模型生成单篇整理结果 | 摘要、观点、证据、方法和局限 | 当前来源版本对应的整理 Bundle 已生成 |
| 发布 | 把当前最新 Bundle 写入 Obsidian | 插件下载、校验、写 Source 和 Digest、提交回执 | 服务端收到当前 Bundle 版本的有效 receipt |

“发布”不再指服务端内部的 Bundle 生成。服务端生成成品但尚未收到 receipt 时，状态为“等待 Obsidian 下载”或“等待发布”。

### 5.2 阶段状态

每一步使用统一状态集合：

- `pending`：尚未开始。
- `running`：正在执行。
- `completed`：已经完成。
- `skipped`：该条目不需要此步骤；状态图画成空心圆圈里一道横线，连线照常通过。用户关闭「AI 自动整理」时的 `organize` 节点用它显示——关了自动整理不是需要处理的事，条目直接进入待发布。（语音识别节点按条目动态出现或不出现，不使用 skipped。）只开着「AI 自动纠错与分段」时该节点在任务执行期间显示 `running`（`OPTIMIZING_TEXT`「正在优化文字（纠错与分段）」），不冒充「正在整理」。
- `waiting`：系统正在等待外部条件，例如等待 Obsidian 上线。
- `attention`：需要用户操作，例如补充正文、连接 Obsidian、配置模型。
- `failed`：本阶段执行失败，可以重试或查看原因。

首页只使用四个聚合状态：

| 聚合状态 | 进入条件 | 首页分组 |
|---|---|---|
| `working` | 任一步为 running 或普通 waiting | 待发布 |
| `attention` | 任一步为 attention | 需要你处理 |
| `failed` | 当前步骤失败且没有自动重试 | 需要你处理 |
| `published` | 发布步骤 completed | 已完成 |

「需不需要你处理」只看**现在**的开关与材料状态，不追溯历史（2026-09-19 修 bug）：自动整理开着时，停在「等模型凭据」的条目是 `attention`（WAITING_MODEL），原文后来更新过也是（STALE_ORGANIZE）；用户把「AI 自动整理」关掉之后，整理这一步对他不存在，这些历史状态一律改按 `skipped`（AUTO_ORGANIZE_OFF）显示，条目落到待发布，被插件取走就是已完成。开关再打开时它们回到需要你处理。因此 `waiting_key` 同时是三种视图的候选状态，归属由聚合结果定，不能只按 `pipeline_state` 猜。手动点「重新加工」产生的等待同样服从这条规则——判断依据只有当前开关这一个。

### 5.3 用户文案

| 状态 | 首选文案 |
|---|---|
| 刚提交 | 已接收，准备提取 |
| 抓取网页 | 正在读取网页内容 |
| 等待 B 站授权 | 需要连接 B 站才能读取这条内容 |
| ASR 准备中 | 正在准备音频 |
| ASR 执行中 | 正在语音识别 63% |
| ASR 等待资源 | 等待服务器空闲后继续 |
| 大模型调用中 | 正在整理内容 |
| 没有模型 Key | 需要选择整理模型 |
| 云端成品已生成 | 等待 Obsidian 下载 |
| 没有桌面设备 | 连接 Obsidian 后自动发布 |
| 关闭自动整理（整理节点） | 自动整理已关闭，直接取用原文 |
| receipt 已收到 | 已下载到 Obsidian |
| 网页把当前版本原文下载走 | 原文已下载 |

终态只说发生了什么，不写「已发布」：材料到了本机就是「已下载」，是否再经 AI 整理由整理节点自己表达。

不把 `unknown_outcome`、`waiting_key`、`needs_input` 等内部枚举直接展示给用户。

### 5.4 ASR 百分比

ASR 百分比使用真实检查点计算：

```text
progress_percent = floor(done_chunks / chunk_count × 100)
```

约束：

- `chunk_count` 尚未确定时不显示 0%，使用不带数字的流动进度条。
- 有总量后显示整数百分比，不显示段数。
- 未成功前最大显示 99%，合并并发布加工结果成功后显示 100%。
- 暂停时冻结百分比，并把文案改为“等待服务器空闲后继续”。
- 重试不把已确认检查点倒退；如果底层确实重新开始，动画平滑重置但不伪装继续。
- 大模型整理无法提供可靠百分比，使用不确定进度动画，不虚构 30%、70% 等阶段数字。

## 6 视觉系统、状态图与动效

### 6.1 基本形态

保留圆点连线结构，阶段固定为：


状态图本身只展示阶段，不再在圆点下面挂“重新提取”“重新转写”“重新加工”等按钮。

### 6.2 视觉状态

- 未开始：空心圆、低对比度连线。
- 当前执行：强调色圆环，圆环缓慢旋转或呼吸；来向连线有轻微流动高光。
- 已完成：实心圆加勾，已完成连线为稳定成功色。
- 已跳过：浅色实心圆加短横或勾，视觉上表示已经通过，不制造流程断点。
- 等待：强调色或中性色圆环，不持续旋转；下方显示等待对象。
- 需要用户：琥珀色圆环加小感叹号，不使用激烈抖动。
- 失败：红色圆环加感叹号，停止动画，避免制造仍在执行的错觉。
- 已发布：最后一个节点完成时使用一次 180 至 240 ms 的缩放和淡入，不做持续庆祝动画。

### 6.3 当前阶段面板

状态图下方只有一个当前阶段面板：

```text

━━━━━━━━━━━━━━━━━━━━━━━━────────────
```


同一时间最多一个主按钮。辅助操作放在更多菜单。

### 6.4 动效规则

- 条目状态变化时只更新对应行，不整表闪烁。
- 进度条宽度使用 250 至 400 ms 缓动过渡。
- 当前步骤切换时，旧步骤勾选和新步骤激活按顺序完成，避免四个节点同时跳变。
- 活跃详情每 3 至 5 秒增量刷新；没有活跃任务时退回 30 秒；页面不可见时暂停。
- 所有动画遵守 `prefers-reduced-motion`，降级后仍能仅靠文字和图形区分状态。

### 6.5 全局视觉基线

当前页面难看的根因不只是颜色，而是所有模块都在争夺注意力：卡片套卡片、边框过多、按钮层级接近、状态颜色到处出现、标题和说明缺少稳定字阶。新界面采用“内容优先、状态克制、操作明确”的基线。

- 页面背景只承担分区，不用大面积渐变、装饰光斑或拟物纹理。
- 主内容最大宽度约 960 px，阅读正文最大宽度约 720 px；超宽屏不把文本拉成一整行。
- 使用 8 px 间距网格。移动端页边距 16 px，桌面端 24 至 32 px；区块之间优先用留白，不反复加分割卡片。
- 只保留一层主要容器。采集框可以是主卡片，条目列表不再让每一行都像独立仪表盘；详情正文不套多层边框。
- 圆角统一为少量等级，例如输入和按钮 10 px、主容器 16 px、圆形图标按钮 50%。不在相邻组件上混用大量半径。
- 阴影只用于浮层、菜单和需要悬浮感的采集框；普通条目使用背景和细分隔线建立层级。
- 字阶收敛为页面标题、区块标题、正文、辅助文字四级；正文保持舒适行高，状态信息不使用全大写或粗体堆叠。
- 全站只有一个品牌强调色。工作中、需要处理、失败和已完成分别使用蓝或品牌色、琥珀、红、绿，但状态不能只靠颜色表达，必须同时有图形或文字。
- 同一视区最多一个实心主按钮。次级操作使用文字按钮或弱化按钮，危险操作只在确认前使用红色。
- 图标统一使用同一套线性风格和描边粗细，不混用 Emoji、实心图标和不同来源的 SVG。齿轮无可见边框，但保留完整点击区域和焦点状态。
- 浅色与深色主题共用语义 token，不分别手写页面颜色；正文、辅助文字、禁用态和边框均满足可读对比。

建议 token 至少包含 `surface`、`surface-muted`、`text`、`text-muted`、`border`、`accent`、`success`、`attention`、`danger`、`focus-ring`，组件只能消费语义 token，不能在业务页面散落临时色值。

## 9 发布回执闭环

### 9.1 现有能力

当前代码已经具备可靠回执闭环，不需要重新发明一套插件协议：

- 服务端已有 `Receipt` 表，按用户、条目、Bundle 版本和设备唯一。
- 已有 `POST /v1/receipts`，验证设备、主要写入 epoch 和 manifest 摘要，并且幂等。
- Obsidian 插件在 Source 与 Digest 均完整写入并保存本地 commit 后调用 `sendReceipt`。
- 插件启动时会补发 `ack_sent=false` 的回执。
- 服务端已经用 receipt 参与 Bundle 保留期清理。

因此本轮工作重点是把现有 receipt 变成 Web 可查询的发布状态，并使第四阶段严格依赖它。

### 9.2 发布判定

对当前条目最新 `bundle_revision`：

```text
存在匹配 user_id + item_id + bundle_revision 的有效 receipt
且 receipt.manifest_sha256 与该 Bundle 一致
    => 发布 completed（已下载到 Obsidian）

否则用户在网页把该 bundle_revision 的原文下载走
   （items.original_download_bundle == 当前最新 Bundle）
    => 发布 completed（原文已下载）

否则 Bundle 已生成
    => 发布 waiting
```

历史版本有回执、但当前最新版本没有回执时，页面显示“新版本等待 Obsidian 下载”，不能沿用旧版本的“已下载”。网页下载同理按版本记账：下载之后原文又更新出新版本，这条回到待发布。

设备后来被撤销不抹掉历史发布事实，因为本地已写入的笔记不会被服务器撤回。新版本仍必须由当时有效的主要写入设备提交新回执。

### 9.3 发布等待状态

| 条件 | 发布阶段文案 | 聚合状态 |
|---|---|---|
| 没有可用 Bundle | 尚未到发布阶段 | 由前序阶段决定 |
| Bundle 已生成，无桌面设备 | 连接 Obsidian 后自动发布 | attention |
| Bundle 已生成，有设备，无当前回执 | 等待 Obsidian 下载 | working |
| 当前 Bundle receipt 已收到 | 已下载到 Obsidian | published |
| 当前 Bundle 的原文已在网页下载走 | 原文已下载 | published |

## 10 面向 Web 的 API 重构

### 10.1 总体策略

现有 `pipeline_state` 继续作为 Worker 内部兼容状态，第一阶段不强行迁移或删除。Web 不再直接解释它，而是使用服务端统一生成的 `workflow` 视图。

新增 `apps/server/kbserver/domain/workflow_view.py`，集中把 Item、Job、AsrRun、BundleRevision、Receipt、设备和用户设置转换为稳定的用户状态。列表页与详情页共用同一转换，不在 JavaScript 中再次手写状态映射。

这样可以大改 API 表达，同时保留已经通过恢复、幂等、版本冲突和回执测试的底层机制。

### 10.2 WorkflowView

`has_active_job` 表示该条目确实有任务在排队或执行（`queued/retry_wait/running`）。
列表轮询用它决定 4s 还是 30s：`overall_state` 为 `working` 也可能是「等待 Obsidian 下载」，
那时服务器没在干活，前台不需要高频拉取。

`GET /v1/items` 与 `GET /v1/items/{id}/reading` 增加：

```json
{
  "workflow": {
    "version": "1.0",
    "overall_state": "working",
    "current_stage": "process",
    "reason_code": "TRANSCRIBING",
    "message": "正在语音识别",
    "progress_percent": 63,
    "requires_user_action": false,
    "has_active_job": true,
    "primary_action": null,
    "available_actions": ["view_source", "cancel_process"],
    "steps": [
      {"id": "extract", "label": "提取", "status": "completed", "reason_code": "SOURCE_READY", "message": "已取得原始内容", "progress_percent": 100},
      {"id": "process", "label": "语音识别", "status": "running", "reason_code": "TRANSCRIBING", "message": "正在语音识别", "progress_percent": 63},
      {"id": "organize", "label": "整理", "status": "pending", "reason_code": "WAITING_FOR_PROCESS", "message": "等待语音识别完成", "progress_percent": null},
      {"id": "publish", "label": "发布", "status": "pending", "reason_code": "WAITING_FOR_ORGANIZE", "message": "等待整理完成", "progress_percent": null}
    ],
    "delivery": {
      "status": "not_ready",
      "bundle_revision": null,
      "received_at": null,
      "device_id": null,
      "device_name": null
    }
  }
}
```

字段原则：

- `reason_code` 是稳定的机器状态，前端不得直接显示。
- `label` 是阶段显示名，由服务端按条目的实际处理方式生成：「语音识别」节点只在会用到 ASR 的条目出现（否则该节点整体不渲染，而非置灰）；前端直接渲染，仅在缺失时回退到固定阶段名。
- `message` 是按 `reason_code` 生成、可直接展示的用户文案，不从 `state_detail`、异常字符串或第三方响应中透传，不包含版本号、密钥、内部对象名、异常堆栈或敏感信息。
- `progress_percent` 只有真实可计算时才返回整数，否则为 `null`。
- `available_actions` 由服务端按真实状态给出，前端不猜哪些操作可用。
- `primary_action` 使用稳定 action code，例如 `supplement`、`choose_model`、`connect_obsidian`、`retry`、`start_organize`；按钮文案仍由前端本地化。
- 默认 ItemOut 不返回可被误展示的 `technical_detail`。

### 10.3 用户文案与错误协议

当前页面的错误处理如果直接执行 `toast(prefix + e.message)`，就会让 FastAPI、Worker 和第三方服务的内部文本穿透到用户界面。重构后所有可预期错误使用稳定错误码和安全用户文案：

```json
{
  "error": {
    "code": "SOURCE_CHANGED",
    "user_message": "这条内容刚刚发生了变化，请刷新后再试一次。",
    "action": "refresh",
    "trace_id": "..."
  }
}
```

约束：

- `code` 供程序分支、日志关联和测试使用，绝不直接显示。
- `user_message` 由服务端受控映射生成，不能直接使用 `str(exc)`、`state_detail` 或第三方响应正文。
- `action` 只表达一个下一步；前端根据稳定 action code 生成按钮文案。
- `trace_id` 仅在“查看处理记录”中写作“问题编号”，供排查使用，不在 Toast 主文案中出现。
- 前端只显示 `user_message`；若响应不符合协议，统一降级为“刚才没有完成，请再试一次”，同时把经过脱敏的原始错误写入诊断日志。
- 表单错误必须落到具体字段旁，例如“请输入服务地址”，不能只弹“参数错误”或 `HTTP 422`。
- 后端日志继续保存足够的技术上下文，但密钥、Cookie 和私人内容仍要脱敏。

新增按需诊断接口：

```text
GET /v1/items/{id}/diagnostics
```

该接口只在用户主动打开“查看处理记录”时请求。返回结构分为 `summary`、`explanation` 和 `technical_records`：前两项使用用户语言，最后一项默认折叠并经过脱敏。版本号字段同时返回可解释标签，例如“内容版本 3”，不能要求前端直接拼接 `r3`。

### 10.4 批量查询要求

列表页计算 workflow 时必须批量查询：

- 当前页条目的最新 Job。
- 最新 AsrRun 与 `done_chunks/chunk_count`。
- 最新 BundleRevision。
- 当前 Bundle 对应 Receipt。
- 用户桌面设备摘要。

禁止为每个条目分别查询 ASR、Bundle 和 Receipt，避免重新引入 N+1。

### 10.5 列表接口

`GET /v1/items` 增加：

- `view=attention|working|published`
- `search=<text>`
- `source_type=<type>`，只作为展开搜索后的可选过滤

旧 `state=<pipeline_state>` 暂时保留兼容，但新页面不使用。

### 10.6 初始化接口

新增：

```text
GET   /v1/onboarding
PATCH /v1/onboarding
```

建议返回：

```json
{
  "completed": false,
  "model": {"completed": true, "profile_id": "...", "label": "deepseek-chat"},
  "obsidian": {"completed": false, "active_device": null},
  "platforms": {"completed": false, "optional": true, "bilibili_connected": false}
}
```

`completed` 不能只依赖一个前端 flag。服务端至少验证默认模型可用和桌面设备存在。`PATCH` 只记录用户主动跳过可选平台、完成引导或重新打开引导等偏好。

### 10.7 设备与发布摘要

现有 `GET /v1/devices` 可以扩展或新增只读摘要：

```json
{
  "connected": true,
  "active_device": {
    "device_id": "...",
    "name": "我的 Obsidian",
    "last_seen_at": "..."
  }
}
```

Web 只展示连接和回执状态，不读取 Vault 路径、Knowledge 内容、主题索引或本地整理结果。

### 10.8 回执 API

保留现有 `POST /v1/receipts` 协议与幂等语义。插件侧不需要新增第二套“已下载”请求。

可以把返回字段 `status="stored"` 在文档中明确解释为“服务端已接受本地写入回执”。Web 使用 Receipt 数据库记录，不依赖插件返回文案。

如果未来需要区分“文件下载完成”和“笔记写入完成”，再引入两个事件；本轮只认现有更强的语义：Source 和 Digest 均完整写入后才回执。界面文案因此统一说“已下载”，不说“已发布”。

网页侧另有一条完成路径：条目详情点「下载原文文件」时，前端在本地生成文件后调用

```text
POST /v1/items/{item_id}/source-download
```

把 `items.original_download_bundle` 记为当前最新 Bundle 版本。这条登记只影响 Web 状态视图的终态判定，不改动插件的增量事件与回执协议；原文随后更新出新 Bundle 时旧的下载不再让新版本完成。

## 11 前端工程结构

当前 `inbox.html` 同时包含页面结构、样式和大量业务脚本。重构时不引入 React、Vue 或额外构建链，使用原生 ES modules 拆分职责。

建议结构：

```text
web_static/
├── inbox.html
├── tokens.css
├── inbox.css
└── js/
    ├── api.js
    ├── app.js
    ├── capture.js
    ├── item-list.js
    ├── item-detail.js
    ├── workflow.js
    ├── onboarding.js
    └── settings.js
```

约束：

- `api.js` 只接受标准错误协议；禁止把异常对象、响应正文或 `e.message` 直接交给 Toast。
- `workflow.js` 只负责渲染服务端 WorkflowView，不重新推断业务状态。
- 条目增量更新按 item_id 做 DOM diff，保护滚动位置和输入内容。
- 动态操作使用事件委托，不生成内联 `onclick`。
- HTML 只保留骨架，不继续增长为新的两千行单文件。
- 共用按钮、弹窗、Toast、焦点和主题规则继续由 tokens 或公共组件样式维护。
- 用户文案集中维护，不在各事件处理函数中临时拼接版本号、状态枚举或后端详情。

## 14 验证与验收

### 14.1 状态接口

至少覆盖：

- 普通网页：提取完成，加工 skipped，整理完成，等待 receipt。
- 上传音频：ASR 0%、63%、100%，然后整理和发布。
- B 站已有字幕：提取取得字幕，加工按规则 skipped 或 completed，不显示 ASR 段数。
- 无字幕且 ASR 暂停：百分比冻结，文案为等待资源。
- 缺模型：整理 attention，唯一主操作是选择模型。
- 缺正文：提取或加工 attention，唯一主操作是补充内容。
- 当前 Bundle 无 receipt：发布 waiting。
- 当前 Bundle 有 receipt：发布 completed。
- 旧 Bundle 有 receipt、最新 Bundle 无 receipt：必须显示新版本等待发布。
- 多用户、多设备 receipt 不串用。

### 14.2 插件回执回归

复用既有验收，确认：

- Source 与 Digest 全部写入后才提交 receipt。
- 部分写入、冲突或哈希失败不提交 receipt。
- 响应丢失后补发幂等。
- 失去主要写入设备资格后不能提交新 receipt。
- Web 在 receipt 成功后下一次增量刷新中点亮发布。

### 14.3 页面验收

- 新用户登录后能直接理解第一步，初始化最多三步，平台连接可跳过。
- 首页首屏只有采集框、条目和右上齿轮，没有常驻技术开关。
- 粘贴一个链接到提交不需要选择来源或处理方式。
- 任意条目详情同一时间最多一个主按钮。
- 状态图始终为提取、加工、整理、发布四步。
- ASR 只显示百分比，不显示段数。
- 整理阶段不伪造百分比。
- 发布只在当前版本 receipt 到达后点亮。
- 390 px 宽度无横向滚动，四阶段标签不相互覆盖。
- 键盘可以操作采集、列表、页签、更多菜单和弹窗。
- 深色模式下文字、状态和进度条对比清晰。
- reduced motion 下没有持续动画，但状态含义不丢失。

### 14.4 用户语言验收

验收范围必须逐项覆盖 Toast、弹窗、Tooltip、空状态、列表、详情、初始化、设置和字段校验，不能只检查主页面标题。

- 默认界面全文不得出现 `r2/r3` 一类修订号、Bundle、manifest、receipt、consumer_epoch、pipeline_state、Job、bvid、cid 或原始枚举值。
- 默认界面不得显示 HTTP 状态码、Python/JavaScript 异常、数据库错误或第三方响应正文。
- 模型和平台确实要求技术字段时，先显示中文名称和用途，再把 API Key、Endpoint、SESSDATA 作为括号说明或手动连接内容。
- 每条错误都要说明发生了什么；只有需要用户介入时才出现一个可执行动作。
- 模拟来源在处理过程中更新，页面只说“内容已经更新，系统会使用最新内容继续处理”，不能出现修订号。
- 模拟旧整理结果失效、设备资格变化、内容校验失败、模型配置缺失和未知结果，逐条确认命中文案映射而不是透传异常。
- 让一名不了解本项目内部架构的体验者复述每条提示；如果必须解释某个词，先改文案，再考虑增加帮助说明。
- 主动展开处理记录后，版本信息必须先有白话用途说明；折叠技术区关闭后，主页面不残留技术文字。

可增加一项静态检查，扫描 `web_static` 中新出现的高风险词，但它只是兜底；最终仍需走查实际渲染，因为技术词可能来自接口动态返回。

### 14.5 第一性原理验收问题

在任何页面随机停下，第一次使用的人都应该能回答：

1. 我现在在哪里。
2. 这条内容现在发生了什么。
3. 系统是否还在工作。
4. 是否需要我做什么。
5. 下一步唯一应该点哪里。
6. 它是否已经进入 Obsidian。

其中任何一个问题需要阅读技术说明才能回答，就说明页面仍然没有完成这次重构。

未登录访问 `/inbox` 时不再只有一句品牌名和一个跳转按钮，而是一整屏产品说明页。

- 内容顺序：首屏花冠 → 诗 → 怎么用（拾取 / 积攒 / 成形 + 四条底线）→ 结尾入口。文案只写已经实现的能力，不写未上线的部分。
- 动效清单：花瓣自内向外逐层绽开、光晕亮一次后极慢呼吸、金尘画布（随指针与滚动轻微视差）、正文逐行淡入落定、末句「金蔷薇」背光亮起并落一次金粉、花茎随滚动生长并点亮三个节点、顶栏发丝线兼作阅读进度、一开始往上滑顶栏那一整行就慢慢缩成一颗居中悬着的描金胶囊。全部只用 `transform`/`opacity`/`filter`，不改宽高与边距——唯一例外是顶栏那条栏缩成胶囊时改的是它自己那层 `::before` 的 `inset` 与圆角，那是绝对定位的独立一层，推不到正文。`prefers-reduced-motion` 下画布只画一帧、花茎直接满长、正文直接可见、花冠停在终态、顶栏那行照样收拢但不再滑。
  - 标题行→胶囊（2026-09-19）：顶栏 `.land-pill` 平时通宽摊在内容盒两端（`.land-mark` 品牌在左、`.land-ends` 入口组在右），`landing.js` 的 `topBar()` 只看滚了多少——一开始往上滑就挂 `.capsule`（`y > 24` 挂、`y <= 8` 摘，这一档迟滞带既躲开回弹与橡皮筋误触发），不等首屏那行字滚出去。**收拢的是那条栏本身，不是另起一颗胶囊**：`.land-top::before` 一层到底，平时 `inset:0` 通宽、只有下沿一条金色发丝分隔线，挂上 `.capsule` 时同一段 `.8s` 里 `top/bottom` 各让 6px、`left/right` 收到 `calc((100% - var(--pw)) / 2)`、`border-radius` 长出胶囊、三条透明边显成描金圈、底色从 .74 压到 .46 变玻璃。两组文字各按 `translateX(±--g)` 往里走，`--g = (顶栏内容盒宽 - 那一行按内容宽排一次的原生宽) / 2`，所以栏的两端与字的落点始终对得上（1280 实测栏 439.3–795.7、字 463–772，同为 617.5 正中）。`--g` 与 `--w`（原生宽，`--pw = --w + 48`，即那一行两侧各留 24px；窄屏收到各 18px。品牌与入口之间是 `.land-ends` 的 `margin-left: clamp(56px, 11vw, 132px)`——**胶囊要更宽是加这段中间留白，不是把两侧糊厚**（用户明确纠正过一次），它算在原生宽里，所以栏跟着一起变宽）写在 `#landTop` 上让栏和内容共用，由 `.land-pill.measure`（`width:max-content`）在同一拍里量出来、中间不绘制；换值那一下必须挂 `.notrans` + 强制回流，否则刷新时会看见整行从中间弹开。视图还 `hidden` 时矩形全是 0，先按 `w || c` 跳过，否则一进页面就凭空吸出胶囊。内嵌宋体落定后品牌字会变宽，`document.fonts.ready` 要再量一次。
  - 两个坑：① `inbox.css` 里给收件箱顶栏写的裸 `header` 规则（暖黑底 + 金色发丝线 + `backdrop-filter`）会漏到 `.land-top` 上，说明页这一行必须显式把 `background`/`border-bottom`/`backdrop-filter` 按回透明，底衬全部由它自己的 `::before` 承担，否则通宽暗带会一直留在屏幕上。② 玻璃那颗要 `backdrop-filter: blur(14px)` + 半透明底色，正文从底下透上来一点又被磨掉；早先版本是「底衬淡出 + 另起一颗淡入」两层交接，`backdrop-filter` 本身没法过渡（实测 `opacity:0` 会把模糊一起淡掉，条纹底逐像素相同），但两层之间总归会露一下底，现在改成同一条栏形变就没这个问题了。阅读进度线仍跟着从通宽缩到 `--w`，上下不动。
- 主视觉换成鎏金稿（`design/golden-rose-home/golden-rose-gilded.svg`）：说明页与收件箱首页各内联一份，id 前缀分别是 `lg` / `gd`（同页两份必须不同名），都不带 `<style>`，动画规则只在 `landing.css` / `inbox.css` 里。
  - 说明页那朵是常驻循环：入场逐层绽一遍，之后每层按 `--i` 错开，以 13s 一轮向外张开约 2%、微拧约 1.2°（`--dir` 让相邻两层反向）再落回。这一份去掉了 `feTurbulence` 铸造磨砂——噪点在被动画改动的子树里会每帧重算，首屏常年循环，留着会掉帧；也去掉了掠过花冠的窄高光，来回扫的光带被判定为多余。花心与方向光不属于任何一层花瓣，得单独跟着 `opacity` 显形，否则还没绽开就会先在原地摆一块褐色饼子。
  - 首页那朵平时完全静止。提交时 `capture.js` 从发送钮撒 32 粒金粉，沿弧线收进瓣圈（落点半径 `tr.width * .3`，压在看得见的瓣内，不撒到花外的黑底上；粒子本体只有 1.8–4px，近白到暖金四档，亮度靠 `.gold-spark` 的两层 `box-shadow` 撑——粉要细才像粉，大了就是光斑），约 0.76s 粉基本落定才给 `svg.rose` 挂 `.play`。撒粉前先等版面落定：手机上键盘把整页顶起来，点发送后键盘收起、页面往下回弹两三百毫秒，那一刻量到的花冠是「被顶着」时的位置，金粉就会落在花的上方；`layoutSettled()` 轮询视口尺寸与滚动，连续 120ms 不变（最多 520ms）才按落定后的位置放动画。点亮只有两层、都不扫过画面：花瓣一层走 `mix-blend-mode: screen` 加光（掩膜在 `#gdSil` 轮廓内，只亮花瓣、不在背景留方块，亮心偏左上与全图方向光一致——正中心对称的亮像灯，偏一点才像被点亮），花外再亮一圈光晕。两层刻意错开半拍：花瓣 `litBloom` 2s、约 0.6s 涌到顶（峰值 .42）、留住一会儿再用一秒多落回；光晕 `haloBloom` 2.4s、晚 120ms 跟上并一路往外胀（.95→1.08），于是「花先亮、光再漫开」。底衬那圈只轻轻胀 5%，摇曳放慢到 2.6s、幅度收到 1.1°。光晕比 viewBox 宽，所以 `.rose` 要 `overflow: visible`，否则花外那圈光会被方框切平。磨砂只留在这份，且点亮两层不带磨砂。原先那道斜掠的流光带和自下而上的光带按用户要求删掉了——「亮条扫过去」不等于点亮。
  - `.plant` 自身不能带 `transform` 属性（位移写内层那个 `g`）：摇曳动画的 `rotate()` 会覆写同名属性，把整朵花转出 viewBox——这就是之前提交时花冠消失约两秒的成因。
- 首屏恒为一整屏：`.land-hero` 用 `height: 100svh` 而不是 `dvh`（手机地址栏收起会改 dvh，首屏跟着变高就是一次整页跳动），花冠与字号按 `svh` 收，`@media (max-height: 620px)` 再压一档，保证横放手机也在一屏内；空的 `#loginError` 用 `:empty` 收起并改成浮层，否则它会把首屏整体下推 66px。走查过 1920/1440/1366/1280/1024 与 390/360/768/844x390 共八档，`heroH == 视口高`、内容不溢出、诗恰好从第二屏开始。
- 边界：不引入构建步骤与新依赖，纯静态 CSS + 原生 ES module；`landing.css` 中可能与收件箱撞名的类（`.rv`/`.kicker`/`.prose`/`.stem`/`.node`/`.steps`…）一律限定在 `.landing` 之下，收件箱界面不受影响。
