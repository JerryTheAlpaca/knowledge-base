# B 站播放音频流 ASR 实施交接方案

日期：2026-09-09，v2。状态：可交给执行 Agent 的待实施方案；本轮只修改文档，未安装模型、未修改业务代码、未连接生产服务器实测。

约束已由用户确认：服务器共 2 核 2GB，运行其他服务；**知识库 API、Worker 与 ASR 合计只能使用约 1GB 内存**，不是给 ASR 单独 1GB。允许长时间排队，对单条完成时效没有要求；按用户补充需求，默认仅在服务器空闲时启动 ASR 工作片段。内容以中文 B 站视频为主，通常约 20 分钟。

## 1. 已确定的实施决策

用户已经确定模型顺序与音频路径，执行 Agent 按以下决策实现，不再重新进行开放式模型选型：

1. 主模型：`sherpa-onnx-dolphin-base-ctc-multi-lang-int8-2025-04-02`。
2. Dolphin 实际效果不达标时，对相同样本尝试 `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17`。一次只加载一个模型；不是每条都跑两个模型。
3. **直接读取播放器使用的音频流**：解析当前分 P 的播放接口 → 选独立音频流 → 受限 HTTP 读取到本次准备的临时文件 → FFmpeg 解码成短 PCM/WAV 段。不启动网页播放器、不录屏/录系统声音、不取视频画面，也不以下载完整视频文件为前置条件（独立音频流本身会整条取回，见 §5.2）。
4. 复用现有 Worker，整套 API + Worker + 子进程约 1GB；只有服务器空闲才执行音频准备与转写，繁忙时保存进度并让出资源。

两种指定模型在本预算下均为**待验证可行性**，不能因模型体积小就声称已能稳定运行。它们使用离线识别接口；“网络流式读取”不等于模型支持原生流式推理，本实现是离线模型逐短段识别。

这个约束下的关键不是“等得起就什么模型都能跑”：等待能换取吞吐，但不能解决模型工作集放不进内存，也不能改善模型本身的识别错误。应同时满足三个条件：

1. 服务器能取得当前视频、当前分 P 对应的音频；ASR 不能解决音频本身拿不到的问题。
2. Worker 与识别子进程的合计内存峰值能稳定低于 640MiB。
3. 用户常看内容中，Dolphin 或指定备用模型的漏字、术语和数字错误在可接受范围内。

执行时先做模型/音频流小试，通过后直接继续完成业务闭环，无需在正常阶段反复询问是否继续。若内存超限，先在同一模型下缩短片段并复测；仍不通过则记录资源阻塞，不自动换其他模型、调用收费 ASR 或扩大内存。Dolphin 的内容质量不达标才按第 8 节试备用模型；二者都不通过时保留补充材料路径。缺少生产权限/真实样本时继续完成本地实现和可运行探测工具，明确哪些验收待补齐。

本方案是对旧版“首版不做 ASR”的新增评估，并不代表当前系统已开启 ASR。已有字幕仍优先；不扩展到 OCR、说话人分离、视频理解或本地大语言模型。

| 顺序 | 固定制品 | 已核实依据 |
| --- | --- | --- |
| 主模型 | `sherpa-onnx-dolphin-base-ctc-multi-lang-int8-2025-04-02` | 官方目录显示 `model.int8.onnx` 约 99M；单线程 CLI 使用 `--dolphin-model`；示例输出包含 tokens/timestamps |
| 备用 | `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17` | 官方提供同名发布压缩包；使用 `--sense-voice-model`；可启用 ITN |

[Dolphin 官方文档](https://k2-fsa.github.io/sherpa/onnx/Dolphin/pretrained.html)、[Dolphin 模型包](https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-dolphin-base-ctc-multi-lang-int8-2025-04-02.tar.bz2)、[SenseVoice 官方文档](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)、[SenseVoice 模型包](https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17.tar.bz2)。官方示例的 RTF 不代表本服务器性能。

优先使用 sherpa-onnx 原生 `sherpa-onnx-offline` 子进程，CPU provider、1 线程、greedy_search；原生运行时与 ONNX Runtime 一起固定版本，模型只读挂载。用程序解析 CLI 的结构化识别结果并校验，不依赖 stderr 中的性能文本。若固定版本 CLI 无稳定机器输出，可使用其 C API 写最小 JSON runner；不默认引入 PyTorch/FunASR 或常驻 Python ASR 服务。Dolphin 不套用 Whisper 的语言/beam 参数；SenseVoice 使用 `use_itn=1` 时在 recipe 中记录，并保留原始模型输出。

不要静默替换同名模型、转用 2025 年粤语专项 SenseVoice 或 Whisper。部署制品记录运行时版本、模型包/模型文件/tokens 的 SHA-256、架构、依赖版本。下载压缩包后检查展开路径仅位于模型目录。模型包先在构建环境准备，生产不临时转换模型。

## 3. 内存、CPU 与吞吐预算

### 3.1 沿用现有两个服务，共用 Worker 预算

仓库 `deploy/docker-compose.yml` 当前配置为 API 256MiB、Worker 640MiB，合计上限 896MiB（约 0.94GB）。这是本地配置，尚未核对生产实际容器参数；它也不代表当前实际占用。

| 部分 | 建议硬上限 | 运行方式 |
| --- | --- | --- |
| API | 256MiB | 继续处理采集、浏览、投递 |
| Worker 与全部子进程 | 合计 640MiB | 音频流读取+解码作为准备阶段；准备与 ASR、普通加工互斥 |
| 合计 | 896MiB | 为约 1GB 总额度留下少量余量 |

不新开常驻 Python ASR 服务，不额外增加一份模型内存，也不把识别放进 API。ASR 子进程必须留在 Worker 的同一容器/cgroup 中，否则上述合计约束失效。模型卸载通过子进程退出保证，不依赖 Python 垃圾回收。

试验目标：Worker cgroup 全流程峰值尽量不超过 **550MiB**，API 不超过原有 256MiB；550MiB 是设计验收线，不是推测出来的模型占用。不能只测 CLI 的 RSS：父进程、解码器、文件缓存及模型冷加载都要计入。普通 LLM 加工后的父进程内存可能不立即回落，要覆盖“先加工、再识别”的顺序测试。

资源控制建议在实施时追加到现有服务配置：

```yaml
# 配置片段，当前尚未应用；保留原有其他字段。
api:
  mem_limit: 256m
  memswap_limit: 256m
worker:
  mem_limit: 640m
  memswap_limit: 640m
  cpus: "0.75"
```

ASR、FFmpeg 和底层计算库均限制为 1 线程；Worker 的 0.75 CPU 是初始配额，待业务负载实测调整。单线程不等于不会占满一个核，配额才负责限制总 CPU 时间。`memswap_limit` 等于内存上限用于禁止该容器通过 swap 超出本次物理内存评估，不把 swap 当正常运行依赖。[Docker 资源限制说明](https://docs.docker.com/engine/containers/resource_constraints/)、[Compose 服务参数](https://docs.docker.com/reference/compose-file/services/)。

这组限制只约束知识库；其他服务仍需在宿主机留出足够内存。生产验收要看宿主机 `MemAvailable`、OOM、swap 和其他应用响应，不能仅凭两个容器的上限断言整机安全。

### 3.2 时间预算只作情景计算

定义有效 RTF = 一条任务的实际处理时间 / 音频时长，包含反复加载模型、切段、解码和转写，不含排队；不要用音频长度直接冒充处理时间。

假设每天 10 条、每条 20 分钟，且全部需要 ASR：

| 实测有效 RTF 假设 | 单条处理时间 | 每日 ASR 总处理时间 |
| --- | --- | --- |
| 1 | 20 分钟 | 3 小时 20 分钟 |
| 3 | 60 分钟 | 10 小时 |
| 5 | 100 分钟 | 16 小时 40 分钟 |
| 8 | 160 分钟 | 26 小时 40 分钟，会持续积压 |

以上是算术场景，**不是速度预测**。每天 5 条则减半；只有一部分无字幕则乘以该比例；多人使用必须累加所有人的音频分钟数。实际吞吐还要扣除普通任务和维护时间。即使不要求时效，也应满足长期输入小于处理能力；试点要求日处理时间不超过实际可用处理时段的 70%，预留波动空间。

## 4. 业务流程

```text
采集并保存链接/备注
  → 已上传文字或字幕：沿用当前处理
  → 探测当前 BV / P / cid 的平台字幕
      → 有可靠字幕：沿用当前字幕处理
      → 确认 no_track 且已开启 ASR：排入音频准备任务
          → 读取该分 P 的播放音频流，落到临时文件后经 FFmpeg 生成短 WAV 段
          → 解码分段，每次转写一段并保存检查点
          → 完整合并，生成 ASR 来源版本
          → 原有云端 LLM 加工 → Bundle → Obsidian
      → 登录要求/风控/未知错误：保留对应原因，有限重试或补充材料
```

全局部署开关默认关闭，验收后开启；用户设置“无字幕时自动转写”只需一次选择，开启后不逐条确认。不自动重跑全部历史待补充条目，历史条目可单条触发。

`login_required`、`blocked`、`network_error`、`unconfirmed` 与 `no_track` 继续区分。有字幕但下载失败的条目可以提供手动“尝试音频转写”，但只有音频访问成功才继续，并保留原字幕失败原因。不把所有错误都转成“无字幕”。

界面显示“等待转写”“正在转写，已完成 X/Y 段”“转写完成，等待整理”。按已处理的音频秒数显示进度，不承诺完成时间。排队时用户照常关闭电脑；API 正常接收新内容，普通后台任务最多等待当前识别段结束。识别结果统一标注“机器转写，未经人工校对”。

## 5. 直接读取播放音频流的确定实现

### 5.1 解析当前分 P 的音频流

先在服务器验证 3–5 个确实没有字幕轨的日常视频，至少包含多 P 的 P2。取得元数据、明确 BV/aid/cid/P，再拿当前分 P 的音频流，不下载合集。

新增 `extractors/bilibili_audio.py`，复用当前 `bilibili.py` 的短链展开、`resolve_video_part`、WBI 签名和按用户凭据获取机制。以锁定版本 [yt-dlp B 站源码](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/bilibili.py) 为接口实现参考：当前路径为 `/x/player/wbi/playurl`，带 bvid/cid 及 WBI 签名，读取 `data.dash.audio` 的 `baseUrl/base_url`、备选 URL、codecs、bandwidth 和流 ID。参数按目标服务器探测结果固定，不能把内部接口当长期稳定合同，也不能直接把字幕接口 `/wbi/v2` 当播放接口。

优先普通 AAC/MP4 独立音频，选择足以识别且可解码的较低带宽音轨；不取 Dolby/FLAC，不访问 `dash.video` 或混合音视频 `durl` 作为隐藏备用。音频表示中的 ID 不是 cid；关联来自本次 bvid/cid 请求及对应元数据，不能声称单看 CDN 地址就证明归属。拒绝试看截断被当作完整视频，校验接口时长、解码时长和原视频时长；错误内容的归属还要通过真实样本抽听核对。

优先独立音频流，不取视频画面；没有独立音频格式时，首轮如实报不支持，避免悄悄下载大视频。仅使用当前用户自己的授权访问状态；保留现有 WBI/buvid3 处理，不照搬已过时的仅 SESSDATA 请求链路。Cookie 只按已核实的站点需求发送，不能无差别带给媒体 CDN，不记录临时签名 URL 和凭据。

如果服务器遇到平台风控、需登录、内容下架或没有可访问音频，ASR 仍然无法工作。保留链接并支持现有字幕/文字补充；音频上传入口属于后续可选功能，本轮不必同时建设。

### 5.2 HTTP → 本次 attempt 的临时文件 → FFmpeg → 磁盘短段

初始参数：单条最长 60 分钟、压缩音频最多 128MiB、同一时刻只准备一条音频；超过限制明确显示原因。排队项目只存元数据，到执行时才取音频，避免大量缓存与地址过期。

远程输入先用 `stream_to_sink` 整条写进本次 attempt 目录的临时文件，再由 FFmpeg 读取该文件解码；不把响应体读成一次性 `response.content`，也不让 FFmpeg 自己联网。输出 16kHz、单声道、16-bit PCM 的短 WAV 段，写入磁盘；临时目录不挂 tmpfs。20 分钟 PCM 总量约 38.4MB，60 分钟约 115.2MB，内存只持有有界 I/O 缓冲和当前片段。FFmpeg 不使用 `-re`，无需真实播放 20 分钟才取得 20 分钟音频。

先落盘而不是直连 stdin 管道，是因为管道输入不可 seek：moov 原子在尾部的常见 M4A 会被判成无法解码，而这一类失败按 §5.3 是终态、不重试——对用户就是「这条网页音频转不了」。代价是多一份压缩音频的磁盘占用（约为 PCM 的三分之一），以及下载期间不能同时解码；临时文件在解码产物齐全后立即删除，不跨本次准备存活。

现有 `security/safe_fetch.py` 返回完整响应体，不能直接用它读取长音频。抽出/复用其中的域名、DNS/IP 和重定向规则，新增窄用途 `stream_to_sink` 接口；确认实际连接目标与已校验地址一致，不能将现有 DNS 预检查当作已实现连接绑定。逐跳校验、限制字节数、读取超时与总时长，支持取消。不得只预检 URL 然后把远程 URL 交给 FFmpeg 自己联网。FFmpeg 只允许本地 file 协议，禁用非必要网络协议；必要的格式探测依赖以固定版本实测为准。stderr 持续消费并截断/脱敏，避免日志积累。[FFmpeg 协议说明](https://ffmpeg.org/ffmpeg-protocols.html)。

下载与解码分两步串行，所以下载阶段按字节回调续租与让出，解码阶段改为轮询子进程；两段都不加载 ASR。一次准备完整条目的短段清单，然后退出解码器；ASR 每次仅处理一个约 **20 秒**片段。初始硬切 20 秒，相邻识别输入额外带约 1 秒上下文；可从相邻磁盘 PCM 段拼出，最多同时读取两个小段。若内存峰值过高，先改 10 秒并记录 recipe；分段不足不能靠增大整个服务限额解决。VAD 若确有必要再加入独立预处理，不作为首版新增常驻模型。

每段记住原视频绝对起止时间；合并时只处理相邻重叠边界，禁止按相同文本全局去重。声音真实重复应保留。无对白、音乐和低音量段必须列入验收，避免静音幻觉或误删轻声内容。硬切造成的词语缺失须通过样本检查，不只验证文件生成成功。

临时区建议先留 1GiB 磁盘余量；只允许一个有 PCM 工作集的活动 ASR 条目，完成/取消/过期后再准备下一条，不让轮转把每条都预缓存。发布成功后清理本任务 PCM；可重试失败保留不超过 24 小时，活动租约文件不清理。清理按任务 ID 与实际文件引用判断，不泛删目录。永久保留用户原始提交、模型原始输出、分段结果与处理清单；**音频仅为临时输入，清理后不能离线重新听原音频**，在来源元数据中如实说明。

### 5.3 音频流中断、过期与可恢复性

- 音频流访问仍会传输音频数据；“直接读取”不能免除访问权限或平台风控。401/403、登录失效、无独立流、网络中断分别记录，不能统一标 no_track。
- 候选主地址失败时只尝试同一音轨的已校验备选地址；地址过期可重新解析同一 bvid/cid 一次。重复失败进入有限退避，不在内部无限重连。
- **不做任意字节 Range 断点**：解码侧不靠字节位置或秒数猜测 MP4 初始化信息（首版即已确定）；下载侧同样不续传——签名地址每次重新解析，备选地址也可能是另一个对象，把两次获取的字节按偏移拼进同一份输入有把两段不同音频缝在一起的风险。准备阶段被暂停/中断时，关闭 HTTP 与 FFmpeg，下次重新取得地址并从开头读取；完整准备成功并提交清单后，转写恢复不再需要网络。允许准备重做以降低实现复杂度。
- 失败准备使用独立 attempt 目录，不能混用两次获取的 PCM；新一轮准备成功前不认定片段完整。**被取代的 attempt 必须回收**：一轮新准备开始前清掉同工作目录下的旧 attempt，终态失败清掉整个工作目录，取消/清理前进程被杀等遗留由 `ASR_TMP_TTL_HOURS` 兜住（一整套 16k PCM 约 115MB/小时，不回收会随失败次数累积到写满盘）。原子提交完整片段清单与摘要后才进入 ASR，EOF/FFmpeg 成功退出/总时长覆盖三项都通过才提交。输入已整条落盘、可 seek，因此 `audio_stream_unsupported` 只表示容器或编码本身解不了，不再是「管道不可 seek」的误判。
- 128MiB 压缩输入限制按每次准备计算，重试次数和累计传输量也记录；按识别秒数汇报转写进度，准备时单独显示“正在读取音频”。静默截断、空流或超时保留原始链接，不能发布完整文字稿。

这一路径的取舍明确：压缩输入只在本次准备期间落成临时文件，解码完成即删除，不作为归档产物保留；转写可按段续跑，但准备阶段中断需要整条重读。正常准备速度由网络、解码与 CPU 配额决定，不把播放器 UI 的 1 倍速当限制。

## 6. 接入现有队列与恢复机制

### 6.1 最小实现结构

复用 SQLite `jobs`，增加 `asr_prepare` 与 `asr_transcribe` 两个 stage。不增加 Redis、Celery 或第二个 Worker 副本。新增一个 ASR 执行模块和一个音频获取模块即可；各模块通过本地文件路径、片段时间及结构化结果衔接。

增加任务级检查点记录 `AsrRun`：绑定 `user_id/item_id/source_revision/recipe_hash`，保存 PCM 清单摘要、模型摘要、阶段、`next_chunk_index`、分段数、失败计数和受控工作目录。唯一键为 `(user_id,item_id,source_revision,recipe_hash)`，用 Alembic 迁移创建。逐段输出以临时文件写入后原子改名，再在短事务中更新检查点；恢复时校验文件摘要，失败仅重做未提交的段。处理清单一经提交不可变，切换模型创建新 recipe/run，不能混合两种模型输出后当作同一次识别。

一次 `asr_transcribe` 领取只识别一段。成功后释放子进程、更新进度，把同一逻辑任务重新排队；完成全部段才发布。**正常切段让出任务不能消耗失败重试额度**：当前 `claim_job` 每次领取都会增加 `attempt`，必须区分本段失败重试和正常推进，推进成功后清零或改为单独失败计数。

默认普通任务优先，只有满足下节的整机空闲门槛才领取 ASR 工作片段。ASR 条目按入队顺序执行，一个有 PCM 的活动条目完成后再准备下一条；同一条目的片段之间让出给普通任务。普通任务持续到达或服务器长期不空闲时，允许 ASR 持续排队，不能为了防止排队而强行越过空闲门槛。`claim_job` 必须先按可执行 stage 过滤再领取，不能先抢到 ASR 任务后反复退回导致普通任务饥饿。

### 6.2 默认仅在服务器空闲时运行

“空闲”不是只看知识库有没有任务，也不是固定凌晨运行。其他服务也在这台机器上，必须观察宿主机整体负载。建议初始策略如下，阈值为可调整的工程初值，部署前以基线校准：

| 信号 | 开始下一段的条件 | 运行中变忙的处理 |
| --- | --- | --- |
| 宿主机 CPU | **除本容器以外**的整机忙碌比例最近 60 秒平均低于 60%，高 iowait/steal 不视为空闲 | 除本容器以外高于 80% 持续 20 秒，终止当前识别子进程，保留已完成段 |
| 宿主机内存 | `MemAvailable` 大于识别新增峰值实测值 + 256MiB；未测前按至少 800MiB 起步 | `MemAvailable` 连续两次 5 秒采样低于 256MiB，提前终止当前段并释放模型 |
| 普通知识库任务 | 无到期的 extract/enrich 任务，且无普通任务正在执行 | 新普通任务到达时结束当前段后优先处理；若要更快让出，可取消当前段，下次重算 |
| 容器额度 | Worker 仍有足够空间容纳实测 ASR 工作集 | 始终受 640MiB 硬限额约束，宿主机空闲不放宽限额 |

Worker 容器的 0.75 CPU 配额在 2 核整机上正好约占 37.5% 总算力，`docker stats` 实测也确实是贴着这个配额跑满。因此**忙碌比例必须先扣掉本容器自己那份**再和阈值比：否则 ASR 每跑一段，就把自己在 60 秒滑动平均里留下的用量当成「服务器忙」，把下一段的开工许可破坏掉——2026-09-19 线上实测正是这样，整机忙碌 40%（其中 iowait 只有 0.4%，磁盘并不忙）而开工线是 25%，结果每段识别本身 6 秒、却要空等 180–320 秒才轮到一次。本容器用量从 `/sys/fs/cgroup/cpu.stat` 的 `usage_usec` 读（cgroup v1 退回 `cpuacct.usage`），读不到时什么都不扣，退回旧口径宁可保守。真正封顶「不许挤坏邻居」的是 cpus 配额本身，门禁只负责在邻居确实忙时让路。`load average` 可作为辅助信息，但不能单独代表 CPU 是否空闲。识别时优先使用低 CPU/IO 调度优先级，资源硬限额继续生效。

启动前连续满足空闲条件 60 秒；运行时约每 5 秒检查一次；因资源忙碌让出后至少冷却 2 分钟，并重新满足连续空闲条件才继续。父进程使用短轮询，同时检查取消和续租，不长时间阻塞主循环。

**准备阶段（`asr_prepare`）按 I/O 密集对待，用另一套准入**：它是一条连接加一个 FFmpeg 解码线程，不是抢 CPU 的那一步，让它也等满连续 60 秒空闲窗口只会把远程音频的读取再推后一分钟。准备阶段保留「无到期的普通任务、且无普通任务正在执行」和内存下限两项——Worker 单进程同步执行，一旦领取就要跑到结束，普通任务条件它是唯一屏障；内存仍要让，因为解码产物落在盘上。去掉的是 CPU 忙碌比、连续空闲窗口和忙碌冷却期，运行中的让出检查也只保留内存一项：一次 CPU 抖动作废一条已在飞的下载，代价是整条重下加冷却，比它省下的 CPU 大得多。识别阶段仍走上面完整的空闲准入。

**不要用 SIGSTOP 挂起模型进程作为内存让出手段**：暂停 CPU 仍占内存。转写阶段结束当前子进程，下次只重算未提交的约 20 秒片段；准备阶段按 §5.3 从开头重新读流。正常因忙碌暂停不算错误，不消耗失败重试次数。父 Worker 在暂停后仍可处理普通任务。

Linux 下可从宿主机视角的 `/proc/stat`、`/proc/meminfo` 与适用的压力指标读取整机信息；容器实际暴露范围要验证，不能把容器 CPU 百分比误认作宿主机百分比。必要时只读挂载所需指标，不挂载 Docker socket。cgroup 用量与整机指标分别判断。指标不可用时保持排队并显示原因，不猜测服务器空闲。

界面增加“等待服务器空闲”和“服务器繁忙，已暂停，完成 X/Y 段”；电脑关机不影响队列。初版不需要预估剩余时间，也不默认每日通知。可以另加可选运行时段，例如只允许夜间启动，但时间窗不能替代实时资源判断。

空闲时间少时任务会积压：吞吐评估应使用实际获得的空闲窗口，并计入被中断段的重算开销。例如每天仅有 4 小时可用，200 分钟音频的有效 RTF 就需低于约 1.2 才勉强清空，考虑 30% 余量则需约 0.84 以下。这仍是容量计算，不是本机模型速度预测。

### 6.3 租约、事务与旧结果保护

当前任务租约默认 120 秒，过期恢复主要在 Worker 启动时调用。ASR 可能一段就超过这个时间，因此实施时必须：

- 在 `prepare → 执行 → finish` 三段中分离事务；下载、FFmpeg、ASR 执行期间不持有长数据库事务。
- 父进程等待子进程时每约 20 秒续租；续租更新以任务 ID、`lease_token` 和 running 状态为条件。续租失败要终止子进程，不能继续提交。
- 在 Worker 正常循环中周期恢复过期租约，不能只依赖重启。恢复与任务完成均按租约条件更新，避免误接管有效任务。
- **领取任务后拿不到上下文时，要把任务判成终态再返回**：条目已删除、来源版本或 run 记录不在等场合若只静默返回，任务会一直停在 running，120 秒后被周期恢复重新入队、再被领取、再静默返回，形成没有进展也没有报错的死循环（线上一个已删除条目的 `asr_prepare` 因此空转 6000 多次）。租约已不属于本次执行的场合不适用——那种情况必须由接管方定结果，否则两个 attempt 会互相把对方的任务写成终态。
- 发布前同时验证当前用户、未删除状态、输入 source_revision 和租约；用户补充字幕后旧 ASR 不能覆盖新材料。取消/删除要终止当前子进程树，检查点不再推进。
- 子进程超时、取消、Worker 退出时必须回收整个子进程组，避免孤儿进程继续吃内存。单段初始超时可设 15 分钟，再根据实测 RTF 调整。
- OOM 要结合容器/cgroup 事件确认，不把所有退出码 137 都说成内存不足；同参数 OOM 不无限重试，记录资源不足并暂停该任务。API 与既有材料仍可用。

模型不在 2GB 生产主机上转换/量化或并行编译。预先在开发/构建环境产出匹配目标 CPU 架构的二进制与量化权重，锁定工具版本/commit、模型 SHA-256、FFmpeg 和下载器版本，再部署只读模型文件。

## 7. 结果、证据与质量处理

每条至少保留 `asr_raw.json`（模型原始分段输出）、`segments.json`、`transcript.srt`、`normalized.md`、`asr_manifest.json`。复用现有不可变来源版本和 Bundle 投递，保持 Obsidian 的人工编辑保护。

元数据应包含：`source=asr`、`engine=sherpa-onnx`、完整模型 ID 与 SHA-256、运行时版本、量化类型、语言、BV/P/cid、音频时长、PCM 清单摘要、分段参数、执行时间、`timestamp_kind=estimated`、`audio_retained=false`、`acquisition=player_audio_stream`、处理范围和异常区间。`audio_retained=false` 指长期交付不保留音频，临时文件是否还在由内部任务记录描述。没有保存完整压缩音频就不伪造其文件摘要。不能把生成的 JSON 标成“平台原始字幕”，也不能沿用平台字幕分支的 `original_media_retained=true`。

片段 ID 与时间用于回看原视频；ASR 时间是估计定位，不能宣称逐字精确。Dolphin 结果如有 token 时间，保留原值并转换为视频绝对时间；不要假定每个 token 都有结束时间。统一 SRT 可按短段/可靠词段输出；若模型输出没有细粒度时间，使用切段时间并标明粗粒度，不能凭文字长度伪造逐字时间。加入重叠上下文后，模型时间必须加输入实际起点，再按本片段所属区间处理边界重复。

完整执行只表示全部计划音频已处理，不表示每一句都听对；记录 `processed_audio_seconds`、静音跳过区间与失败区间。存在失败段则标部分转写，不生成“完整视频全文”的描述。全片无有效语音进入待补充，不用标题生成正文。

原始 ASR 文本不可被 LLM 润色覆盖。AI 可生成独立整理结果，遇到人名、术语、数字和否定词不确定时不能声称已校正；疑似错字仍可回到原稿与时间定位。音频里没说出的公式、画面文字、代码和图表不属于 ASR 能恢复的内容。

## 8. 实施步骤与验收

### 第一步：用真实资源额度验证模型，不先做完整业务

1. 核对目标架构、CPU 指令集、容器实际限额、宿主机空闲内存和现有服务负载。记录空闲及正常加工时的基线。
2. 在与生产一致的 256MiB API + 640MiB Worker 配额下，将指定 Dolphin INT8 作为真实 Worker 子进程运行。测试 20 秒单段冷启动，以及 20 分钟整条分段执行；先不新建生产批量任务。
3. 从常看视频选 8–10 条，包括普通话讲解、术语/数字、中英混说、背景音乐、长静音、多 P 与一条较长视频。至少 3 条从目标服务器成功取得音频，不能只用本地 WAV 证明整个链路可行。
4. 每条抽取开头、中间、结尾各约 30–60 秒人工对照；检查关键观点、数字、否定词、漏句和静音幻觉。若计算 CER，需人工参考文本并固定标点/繁简归一规则，报告样本分母，不用“感觉流畅”当准确率。
5. Dolphin 通过则保持默认，不跑备用模型。质量不通过的触发：固定样本出现明显整句漏识、重复幻觉、关键数字/否定词错误改变原意，或人工指出不可用；把失败音频区间与原输出写入报告，再用指定 SenseVoice 在同一组样本/同等资源限额复测。无人工参考时只报告未验证，不用 ASR 自评分代替质量验收。
6. 备用模型若质量通过且资源通过，可将部署默认切换为 SenseVoice，报告对照证据；不要靠文本长度或语言模型“看起来流畅”自动切换。上线后单条支持 `retry_model=sense_voice` 手动重试，默认不双跑。切换后从该条完整 PCM 清单重新识别生成独立版本，输入已清理则按 §5 重新取流。两者均不通过时不扩展模型清单。

CLI 探测片段如下，仅供实现验证，**本轮未执行**。假设已将指定模型包展开到 `/opt/models/`，固定运行时位于 `/opt/sherpa/bin/`，并已通过音频流准备生成单段 WAV：

# 仅在 Dolphin 质量不通过时执行同样样本的备用模型对照。
/usr/bin/time -v /opt/sherpa/bin/sherpa-onnx-offline \

参数以锁定版本 `--help` 为准，模型参数依据 §2 官方示例。单进程 `/usr/bin/time -v` 仅作辅助；主要记录 Worker cgroup 的峰值、OOM 事件，以及 API 与宿主机指标。不能只跑此命令后宣布满足 1GB 合计限制。

### 第三步：上线门槛与回退

- 目标负载下 Worker 全流程峰值 ≤550MiB，API 在 256MiB 内，无 OOM、无持续 swap，宿主机仍有余量。若峰值只是刚好卡在 640MiB，不作为稳定通过。
- 普通采集与浏览在识别期间可用；同环境 API P95 与无 ASR 基线比较，暂以增幅不超过 20% 为目标，轻负载样本不足时明确其局限。通过受控的 CPU/内存负载验证空闲启动、忙碌让出、冷却恢复，并确认未提交片段重算不会重复发布；不要在生产主机直接进行内存耗尽测试。
- 日到达音频量能够被实测处理能力覆盖并保留 30% 时间余量；试点连续运行至少 48 小时观察积压，而非仅跑一条。
- 检查当前 BV/P/cid、分段边界、静音、原始输出保留、ASR 标记及人工修改保护。
- 针对中途杀进程、重启、租约失效、用户补充字幕、条目删除做恢复验证：不重复发布、不发布旧结果、不留下常驻子进程，不跨用户读凭据或音频。
- 质量评估无关键观点被漏掉或反转的明显问题；术语和数字错误单独列出，由真实样本决定是否适合知识摄入，不承诺通用准确率。

关闭 ASR 开关即可停止新增任务；已有任务在当前片段后暂停，模型进程退出。保留已发布文字稿和原有字幕路径；不卸载数据库、不删用户材料。模型或音频获取不通过时回到待补充，并给出具体原因。

## 9. 执行 Agent 的接口、配置与交付契约

以下均为本次新增契约，不表示代码已经存在。按现有项目风格实现；如有等价接口可复用，保持语义并同步 contracts，避免新增重复入口。

### 9.1 最小内部契约

| 接口/对象 | 输入 | 输出与边界 |
| --- | --- | --- |
| `resolve_audio_stream` | 当前用户授权状态、VideoRef、已解析的 page/cid | 音轨 ID、codec、duration、临时主/备地址；地址仅存在本次执行内存中 |
| `stream_to_sink` | 受控 URL/headers、字节上限、取消回调、sink | 字节计数/状态；按块写入，异常即关闭连接，不持有完整响应 |
| `prepare_audio` | 不可变输入定位、工作目录、租约上下文 | 完整 PCM 片段清单及摘要；未完整成功不得作为转写输入 |
| `transcribe_chunk` | 模型制品、一个本地 WAV、输入绝对起点 | 原始 JSON、规范文本、可选 token 时间；不访问网络、不持有凭据 |
| `finish_asr` | run/租约、全部已提交结果 | 校验输入仍有效后新增来源版本、Bundle，并排入 enrich |

准备清单以实际输出采样数/采样率计算时间，不仅用“段序号 × 20 秒”；含核心区间、带上下文的输入区间、WAV SHA-256、bytes。读流失败不留下伪造的完整清单。`recipe_hash` 至少包含模型/运行时摘要、ITN/解码参数、切段与重叠参数、归一化版本。

### 9.2 用户接口与状态

- 新增 `GET/PUT /v1/asr-settings`，使用当前用户与已有 `profiles:manage` 权限，保存 `auto_when_no_track`，默认 false；GET 另返回只读 `deployment_enabled` 与可用模型别名。偏好单独建简单用户设置记录，不存进加密凭据字段。
- 新增 `POST /v1/items/{item_id}/asr`：默认选择部署主模型；可选 `retry_model: "sense_voice"` 触发用户指定的备用重试。用户只能传模型别名，不能传路径/下载 URL/执行参数。仅接受该用户未删除的 B 站条目；按输入版本与 recipe 幂等，返回 run ID 与排队状态，重复点击不重复创建任务。
- 新增 `GET /v1/items/{item_id}/asr` 返回该条当前任务的阶段、完成段数、总段数、模型 ID、暂停/失败原因，不暴露服务器路径或签名 URL。
- 新增 `POST /v1/items/{item_id}/asr/cancel` 取消该用户任务，终止子进程并保留原有笔记。关闭用户自动开关停止后续自动入队；已有任务使用取消入口控制。全局开关关闭暂停所有 ASR 执行。
- `AsrRun.state` 使用 `queued/preparing/transcribing/paused/succeeded/failed/cancelled`；`pause_reason` 区分 idle_wait/resource_busy/disabled。展示状态由持久化记录产生，不依靠内存里的轮询进度。
- Item 主状态优先复用现有 queued/extracting/needs_input 等约定，以 `state_detail` 和事件携带 ASR 阶段，避免客户端未知状态破坏旧流程。规范中若需要新增枚举，服务端、Web、插件与 OpenAPI 同步更新。
- `no_track` 且部署/用户开关均开启才自动进入新路径；字幕登录错误不自动触发。手动 ASR 在字幕失败后仍独立验证音频可访问性，不被 `_extract_bilibili` 旧的字幕凭据错误分支直接短路。
